## 一、本周要打通什么

**这一周开始，代码要驱动真实的东西。**

```
键盘 / launch 参数 / yaml
      ↓
Action Client ──goal──> Action Server（串口驱动节点）
      ↑                      │  ① 校验 pwm 是否落在 pwm_min~pwm_max
      │  feedback / result   │  ② 拼 ASCII 指令
      └──────────────────────┤
                             ↓
                    ServoCommand（自定义 msg，内部调试总线）
                             ↓
                  "#001P1700T1000!"  → write + flush
                             ↓  串口 115200 8-N-1
                  USB 转 TTL → 24 路舵机控制板
                             ↓  半双工总线（同一根线，靠 ID 区分）
                    总线舵机 → 打印件结构 → 关节真的转起来
```

这条链和第 2 周那条（视觉 → 战术 → 底盘）是**同一个思路**，只是最后一环从「小乌龟仿真」换成了「真舵机」，并且接口从话题升级成了 Action。

### 1.1 四关的顺序有依赖，不能换

新舵机到手，工程上的标准动作**不是「先装起来再说」**，而是：

```
单点点亮  →  单点自动化  →  复制到整机
```

**为什么不先装整机**：装好之后「舵机不动」有六种可能（代码、串口权限、波特率、结构卡死、电压不够、ID 搞错），混在一个现象里分不清是谁的错。

| 关卡                | 任务       | 在什么场景做            | 通过标准                                  | 不过会怎样           |
| ----------------- | -------- | ----------------- | ------------------------------------- | --------------- |
| **一 · 点亮一个**      | 任务 1（15） | 桌面，**1 个舵机，不装结构** | 串口能通、舵机听指令、全部舵机标定 1500                | 后面全是瞎猜          |
| **二 · 让 ROS2 接管** | 任务 2（50） | 桌面，**还是那 1 个舵机**  | Action 能转、能反馈、能取消；一条 launch 全起来；参数全外置 | 装配后分不清是代码还是机械问题 |
| **三 · 复制到整机**     | 任务 3（25） | 装进结构，**全部**舵机     | 整机上电，逐个控制正常，多舵机动作组不乱                  | 整机瘫，且查不出原因      |
| **四 · 交付**        | 任务 4（10） | 整机                | 完整下电演示                                | **整周不通过**       |

> 📌 **任务 1 和任务 2 用的是同一套桌面最小系统**，可以在实验室一次性做完，**再去装配**。不需要拆装两次。

## 二、开工前

### 2.1 软件环境（去实验室之前弄好）

1. **装串口库**（不做这步，`import` 就崩）：

```bash
sudo apt install python3-serial -y
python3 -c "import serial; print(serial.__version__)"
```

1. **把自己加进 `dialout` 组**（否则打开串口报 `Permission denied`）：

```bash
sudo usermod -aG dialout $USER
```

> ⚠️ **改完必须重新登录（或重启）才生效。**

1. **确认这套工具在**（缺了就装，别到现场才发现）：

```bash
ros2 --version          # 应有输出
ros2 bag --help         # bag 录制工具，Humble 自带
ros2 action list -t     # Action 调试用
colcon build --help     # 编译（这次你必须自己 build，不再是纯 python 脚本）
```

> 📌 **本周第一次要 `colcon build`。** 前两周改完 python 直接 `ros2 run` 就能跑，这次自定义 msg / action 必须编译，**改一次 msg 就要重新 build 一次**。

### 2.2 物料与工具

| 物料           | 核对要点                        |
| ------------ | --------------------------- |
| 总线舵机         | **记下每个舵机的 ID**，任务 1 第一件事就是扫 |
| 地瓜派板卡        | 上位机，跑 ROS2；确认能开机、能连网        |
| 电池 + 充电器     | **量电压**、看有无鼓包               |
| 3D 打印结构件     | 清点件数，缺件当场报                  |
| USB 转 TTL 模块 | 认芯片（CH340 / CP2102），装驱动时要用  |
| 24 路舵机控制板    | 确认通道数够                      |
| 杜邦线 / 电源线    | 宁可多拿，别中途缺线                  |

### 2.3 三条安全底线

**写错一行代码的后果不再是「报错」，而是「冒烟」。**

1. **上电前必须用万用表量电池电压**，落在 **5–8.4V** 才允许接板。超了就换电池，**不要"试一下"**。
2. **电源正负不能接反，地线必须连**。反接上电瞬间舵机就废，没有第二次机会。
3. **听到持续「嗡嗡」声立刻回中位**。那是堵转——舵机转到结构限位还在发力，力全变成热量，三分钟内能烧穿。

## 三、任务 1：点亮一个舵机　（15 分）

> 舵机还没装进结构，此时转错了顶多撞空气，不会打齿、不会顶裂打印件。

### 1.1 目标：只接 1 个舵机的最小系统

```
电脑 ──USB──> USB 转 TTL ──> 24 路控制板 ──> 1 个舵机
                                ↑
                            电池（先量电压）
```

**先只接一个。** 不要一上来把 6 个舵机全插上——ID 冲突、通道接错、供电不足，三个问题一起来你查不动。

### 1.2 接线（三根线，别接反）

| 线色        | 含义            | 注意            |
| --------- | ------------- | ------------- |
| **橙 / 白** | 信号（串口数据）      | 接控制板通道信号脚     |
| **红**     | 正极，**5–8.4V** | **绝对不能接 12V** |
| **棕 / 黑** | 负极 / GND      | 接电源负          |

**必须共地**：板卡、控制板、电池负极连在一起。只接信号不接地，数据一定收不到。

### 1.3 串口四个参数

| 参数      | 是什么               | 本周取值       |
| ------- | ----------------- | ---------- |
| **波特率** | 每秒传多少位，**双方必须一致** | **115200** |
| **数据位** | 一个字符用几位           | 8          |
| **停止位** | 一帧的结尾标志           | 1          |
| **校验位** | 简单查错              | 无（N）       |

写作 `115200 8-N-1`。**波特率不对 = 收到一堆乱码。**

> ⚠️ 这三项（波特率 115200、设备名、限位区间）从任务 1 起你就在用，**但任务 2 里它们一个都不许写死在代码里**。先用着，等下再说。

### 1.4 找到串口设备

```bash
ls -l /dev/ttyUSB*        # 插上后应出现 ttyUSB0，属主组应为 dialout
dmesg | tail -20          # 看内核认成了哪个口
```

### 1.5 扫 ID、验证指令

指令是 ASCII 字符串，`#`\** 开头、**`!`** 结尾\*\*，ID 固定 **3 位补零**：

| 功能   | 指令                | 说明                        |
| ---- | ----------------- | ------------------------- |
| 读 ID | `#001PID!`        | 返回当前舵机 ID                 |
| 读位置  | `#001PRAD!`       | 读回当前 PWM 位置               |
| 恢复扭力 | `#001PULR!`       | **要它动之前必须先发这条**           |
| 转角度  | `#001P1500T1000!` | 1 号 → PWM 1500，耗时 1000 ms |
| 卸力   | `#001PULK!`       | 断电前必发，防堵转发热               |

**验证顺序**：

```
① #001PID!        → 有回显 = 链路通了
② #001PULR!       → 恢复扭力（不发这步，下一步舵机纹丝不动）
③ #001P1500T1000! → 舵机应平滑转 1 秒到位（不是猛跳）
④ #001PRAD!       → 读回 1500 左右，证明真到位
```

用一个舵机把这四步跑通，**再**把每个舵机的 ID 和位置都扫一遍并记下来。

> 用串口助手（SSCOM / XCOM / minicom）手动发可以，用 Python 写几行 `serial.Serial(...).write(b"#001PID!\r\n")` 也可以。**只要求跑通。**

### 1.6 标定中立位

舵机的「中立位」= PWM **1500**。**在装舵臂之前**，把每个舵机单独发到 1500，**再**把舵臂装上去并对准结构的基准位置。

**为什么必须在装结构之前**：

- 舵机的绝对零点是出厂随机的（不同舵机之间可能差几十度）；
- 你先装结构再标定，等于在一个错的角度上定义了整机的「正前方」；
- 后果是后面所有动作都偏，**而且没法靠软件补**——你根本不知道偏了多少。

**每个舵机都要做一遍。**

### 1.7 完成标准

- [ ] 最小系统接线正确，**上电前量过电压**，上电无异常（无冒烟、无异味、无发烫）；
- [ ] 打开串口**不需要 `sudo`**；
- [ ] `#001PID!` 有回显；`#001PULR!` + `#001P1500T1000!` 后舵机**平滑到位**；
- [ ] `#001PRAD!` 读回值与指令一致；
- [ ] **所有**舵机都已标定到 1500；
- [ ] 能讲清：为什么必须先 `PULR`？为什么指令要 `!` 结尾？波特率错了会看到什么？

**材料（截图带姓名 + 时间戳）**：`ls -l /dev/ttyUSB*` / `#001PID!` 回显 / 舵机转动录屏 / `#001PRAD!` 读回值 / 万用表电压读数 / 物料登记表。

> 任务 1 **不用交代码**，用串口助手手动发指令跑通也算，交截图和记录就行。

## 四、任务 2：让 ROS2 接管这个舵机　（50 分，核心）

> 现在要验证的是**软件**。此时舵机仍然**没装进结构**，所以如果它不动，只可能是代码问题。
>
> 这一关是全文档最重的一关，占 50 分。**按 2.1 → 2.7 的顺序做，每一步做完先自己验一遍再往下。**

### 2.0 你要造的东西长什么样

```
┌─────────────────────────┐        ┌──────────────────────────────────┐
│  cquick_servo           │        │  cquick_servo_interfaces         │
│  ├─ servo_driver.py     │──依赖──>│  ├─ msg/ServoCommand.msg        │
│  │   = Action Server    │        │  └─ action/MoveServo.action     │
│  ├─ move_client.py      │        │                                  │
│  │   = Action Client    │        │  （纯 CMake 包，只放接口定义）    │
│  ├─ launch/servo.launch.py       └──────────────────────────────────┘
│  └─ config/servo_params.yaml
└─────────────────────────┘
```

**两个包，不是一个。** 接口定义单独成包，是 ROS 的通行做法 —— 后面视觉组、算法组要用你的舵机接口，只装接口包就行。

| 包名                        | 构建类型           | 里面有什么                                            |
| ------------------------- | -------------- | ------------------------------------------------ |
| `cquick_servo_interfaces` | `ament_cmake`  | `msg/ServoCommand.msg`、`action/MoveServo.action` |
| `cquick_servo`            | `ament_python` | 驱动节点、客户端节点、launch、config                         |

### 2.1 第一步 · 建包 + 自定义接口

两个包：一个 CMake 包只放接口定义，一个 python 包放节点。建包就 `ros2 pkg create` 一条命令，参数 `--help` 里都写着，自查。

**`msg/ServoCommand.msg`** —— 替代 `std_msgs`，一条指令该有的信息一次说全。下面三个字段是**下限**，想加可以加：

| 字段            | 类型       | 含义                           |
| ------------- | -------- | ---------------------------- |
| `id`          | `uint8`  | 舵机 ID，1~254                  |
| `pwm`         | `uint16` | 目标 PWM。**这是电气极限范围，不是你的安全范围** |
| `duration_ms` | `uint16` | 从当前位置走到目标用多久，单位 ms           |

**`action/MoveServo.action`** —— 三段，字段怎么切你自己定，但这三件事必须表达得出来：

| 段            | 必须能说清什么                                             |
| ------------ | --------------------------------------------------- |
| **Goal**     | 一条完整的指令（可以直接嵌套上面那个 msg，也可以把字段摊平）                    |
| **Result**   | 到底成没成、最终 `PRAD` 读回多少、失败原因一句话说清（超限 / 取消 / 串口错 / 没到位） |
| **Feedback** | 当前 PWM 是多少、进度到几成（0~1）                               |

**接口包有三处必须改对**，少一处就编不出接口：

1. **依赖**：既要在编译期生成接口，也要在运行期能加载 —— `package.xml` 里对应的两个 rosidl 依赖都得声明；
2. **分组声明**：`package.xml` 里要把这个包标进 `rosidl_interface_packages` 组（`member_of_group` 那一项）。不写这项，别的包**引用不到**你的接口，而且报的错跟这个八竿子打不着，够你查一晚上；
3. **CMakeLists**：先找到接口生成器，再把 `msg/`、`action/` 两个文件都列进去生成，最后导出运行时依赖。

**编完自己验**：`ros2 interface show` 能把两个接口的字段打出来，这关才算过。打不出来就别往下走 —— 后面的报错全是假的。

### 2.2 第二步 · 串口驱动节点：**全部参数化**

**这一版最容易被扣分的地方：代码里出现一个硬编码。**

下面这些值**一个都不许**直接写在 `.py` 里，必须来自参数：

| 参数名                   | 类型     | 默认值             | 说明                  |
| --------------------- | ------ | --------------- | ------------------- |
| `port`                | string | `/dev/ttyUSB0`  | 串口设备名               |
| `baudrate`            | int    | `115200`        | 波特率                 |
| `pwm_min`             | int    | `900`           | 安全下限（结构实测）          |
| `pwm_max`             | int    | `2100`          | 安全上限（结构实测）          |
| `default_duration_ms` | int    | `800`           | 客户端没给 duration 时用   |
| `servo_ids`           | int[]  | `[1,2,3,4,5,6]` | 本机有哪些舵机，用来拒绝不存在的 ID |
| `startup_reset`       | bool   | `true`          | 启动时是否全部回中位          |

**怎么算做到了**：这些名字在代码里只应该出现在两处 —— 声明参数、读参数。

开串口、判限位、拼指令这些地方一律走读出来的值，不许再写一遍字面量。评审会在你的驱动代码里 `grep` 一遍，出现就算没做到。

> 允许保留的只有**协议常量**：`#`、`!`、ID 补 3 位、`P`/`T`/`PID`/`PRAD`/`PULR`/`PULK` 这些指令字。这些是协议本身，不是配置。

**参数放在哪**：`config/` 下的 yaml 里，用 `ros__parameters` 把上面七个一次写全。

> ⚠️ yaml 最外层那个 key 必须等于**节点名**。写错了**不报错、不警告**，参数一个都不加载，然后你会以为是代码问题查到半夜。


### 2.3 第三步 · Action 服务端（核心）

驱动节点对外**只暴露 Action**，不用话题、不用服务当控制口。

**四个回调一个都不能少**：

| 回调                                              | 你要做什么                                                                                 |
| ----------------------------------------------- | ------------------------------------------------------------------------------------- |
| `handle_accepted_callback` / `execute_callback` | 收到 goal → 校验 → 发串口 → 循环发 feedback → 返回 result                                         |
| `goal_callback`                                 | **发指令之前**就判断：pwm 超限 / ID 不在 `servo_ids` / duration 非法 → 直接 `GoalResponse.REJECT`      |
| `cancel_callback`                               | 返回 `CancelResponse.ACCEPT`                                                            |
| `execute_callback` 里循环检查 `is_cancel_requested`  | 收到取消 → 立刻停发、回中位、`goal_handle.canceled()`，result 里 `success=False, message='canceled'` |

> 服务端构造时上面四个回调都要接上；如果你照着最简教程写，`Ctrl+C` 大概率先失效 —— 先想清楚回调跑在哪个线程里，再动代码。

**反馈频率**：至少 **5 Hz**（每 200 ms 一次），转 1 秒的动作你至少要看到 5 条 feedback。

**读回校验**：动作走完，发 `#xxxPRAD!` 读一次实际位置。与你发的目标差超过 ±30，就算没到位 —— `success=False` 并在 `message` 里写清差了多少。

**启动顺序别搞反**：上电后第一次动作之前必须先 `PULR`（恢复扭力），否则舵机纹丝不动 —— 任务 1 已经踩过了，这次要写进代码里，不能靠手动补。

### 2.4 第四步 · Action 客户端

输入方式自选（读键盘 / 定时器轮播 / 从参数读一串目标值），**必须能指定 id 和 pwm**，并且：

- 要**发 goal**，不要直接调底层函数；
- 收到 feedback 要打印：`id=1 pwm=1620 progress=0.62`；
- 收到 result 要打印成功/失败原因。

**验收方式**：评审不碰你的客户端，直接用 `ros2 action send_goal` 从命令行打一条 goal 进去，加 `--feedback` 看反馈滚不滚、最后出不出 result。

这条命令既是考题也是标尺：**你的 goal 字段设计得好不好，命令行拼一下就知道**。要拼一大串还总拼错，说明字段切得不顺手，回去改字段，别改命令。

### 2.5 第五步 · launch 一键启动

**验收标准就一句话：不许再出现「开两个终端各跑一个节点」。**

```bash
ros2 launch cquick_servo servo.launch.py
```

一条命令，驱动节点起来、参数从 yaml 加载、该起的辅助节点全起。

launch 文件怎么写随你，但下面三件事必须做到：

1. **参数从 yaml 读** —— 路径要用包里查出来，**不许写相对路径**（相对路径在别人的机器上必挂）；
2. **launch 参数能覆盖 yaml**：`ros2 launch ... port:=/dev/ttyUSB1` 这种写法要真的换端口；
3. **有条件启动**：客户端默认不起，加个开关参数（`demo:=true` 之类）才起。

> `launch/` 和 `config/` **默认不会**被装进 install 里，得在 `setup.py` 的 `data_files` 里显式加进去。加了之后**必须重新 `colcon build`**，不然 install 里还是旧文件，你会对着空气改半天，还以为是 launch 写错了。

### 2.6 第六步 · 运行时改参数，**当帧生效**

要求：改限位不用改代码、不用重编译、不用重启节点。

```bash
ros2 param set /servo_driver pwm_max 1600
```

执行完，**下一帧就按 1600 判断**。

**必须提交的演示脚本（录屏按这个顺序演）**：

```text
① ros2 param get /servo_driver pwm_max            → 2100
② ros2 action send_goal ... pwm=1700              → 成功，舵机转到 1700
③ ros2 param set /servo_driver pwm_max 1600       → Set parameters successful
④ ros2 action send_goal ... pwm=1700              → 被拒！goal rejected，日志打原因
⑤ ros2 param set /servo_driver pwm_max 100000     → 被拒！Set parameters failed: 超出 500~2500
⑥ ros2 param set /servo_driver pwm_max 2100       → 恢复，再发 1700 → 成功
```

**第 ④ 步是关键**：改完参数**不重启**，行为立刻变了。做不到这一步，2.6 就是没做。

**还必须做参数校验**（不然 ⑤ 那步会被人一把改坏）：界外的值（`pwm_max` 超出 500~2500、不认识的波特率）、以及 `pwm_min ≥ pwm_max` 这种互相打架的组合，都要能拒掉，拒的时候给一句能看懂的理由。rclpy 里做这件事的地方叫**参数设置回调** —— 只有注册了它你才有权力拒绝，不注册就什么值都进得去。

> 1. **回调返回 `successful=True` 之后，值才会真的写进去**；返回 False 则整个 set 被拒，参数保持原样。
> 2. **校验通过后，判断逻辑必须重新 `self.get_parameter('pwm_max').value`**。如果你在 `__init__` 里把值存进 `self.pwm_max` 就再也不读了，参数改了也不生效 —— 这就是 ④ 那步失败的最常见原因。

### 2.7 第七步 · ros2 bag 当交付物

**除了 B 站录屏，这次还要交一个能回放的 bag。**

为什么两个都要：录屏只能看，bag 能把你当时的**每一条指令、每一个反馈**原样重放给评审。以后整机出问题，第一个被要看的就是 bag。

**驱动节点必须额外订阅一个内部调试话题** `/servo/command`（就是你那个 `ServoCommand`），作用只有一个：让 bag 能回放。**它必须和 Action 走同一个底层发送函数** —— 两套逻辑的话，回放出来的动作和你录屏里的一定对不上。

**录制**（动作开跑前就开始录，跑完再停）：

- 只录 `/servo/command` 和 `/servo/state` 两个话题，**不许 `-a` 全录**（全录会把你板卡上所有节点的数据都塞进去，几百 MB）；
- 时长 **≤ 30 秒**；
- 交上去的 `bag/run1/` 体积 **≤ 10 MB**。

**回放验证**（这是验收点，不是可选项）：`ros2 bag info` 能看出消息条数；`ros2 bag play` 跑起来，**舵机应该自己把刚才那套动作再做一遍**，和你录屏里的动作一致。

> 如果回放时舵机不动，说明你只录了、没订阅 —— 那条 `/servo/command` 白接了，2.7 这 4 分没有。

## 五、任务 3：复制到整机 + 多舵机动作组　（25 分）

### 3.1 样机是唯一标准

动手前**先给样机拍照 / 拍视频**，尤其**接线特写**和**每个关节的舵机朝向**。事后想起来「好像是这么装的」时，你会庆幸拍了。

### 3.2 装配顺序（顺序错了要拆）

```
① 舵机全部已在 1500 标定（任务 1 已完成）
→ ② 舵机装进结构 → ③ 装舵臂 / 连杆（此时仍是 1500 位）
→ ④ 固定地瓜派板卡 → ⑤ 固定电池 → ⑥ 走线 + 扎带
```

> **②③ 的前提是①已经做完。** 带着错位零点装舵臂，等于把偏差固化进结构，整机姿态全歪且补不回来。

**走线决定寿命**：线贴在结构内侧走，用扎带固定，**别让它穿过任何会转动的关节**。一根线被夹断，整台机器瘫。

### 3.3 整机上电验证（一次只验证一个变量）

**不要**上电后就跑复杂动作。按这个顺序，每步通过再往下：

```
① 量总电压 → ② 上电，看有没有冒烟/异味 → ③ 逐个 ID 扫描，确认全部在线
→ ④ ROS2 逐个控制回中位 → ⑤ 单个舵机小幅正反转 → ⑥ 全部舵机同时回中位
```

**装完不要立刻上电**，先手动转每个关节，确认不卡、不刮线。

**任何一步听到「嗡嗡」声、看到发烫，立刻断电回查。**

### 3.4 多舵机动作组（本周的核心难点）

单个舵机能动之后，让 **2 个及以上舵机协同**做一套**流畅、可重复**的动作（比如两个关节一起抬、一起收，再做第二段）。

**难点在时序**：两个舵机不是同时到位的，先后顺序错了结构会互相打架。做之前先想清楚：

- 谁先动、谁后动，差多少毫秒；
- 每个舵机的 `duration_ms` 给多少（给太小会猛跳撞结构）；
- 重复跑三遍，动作是不是每次都一样。

**实现方式只用 Action**：一个动作组 = 一串 goal 顺序下发，**等上一个 result 回来再发下一个**。不许用固定 `sleep` 猜时间 —— 舵机走完的时间不等于 `duration_ms`，会累积误差。

> 用 `sleep(1.0)` 硬等的人，第三遍和第一遍的动作一定对不上。**用 result 当同步信号。**

#### 动作组必须是「数据」，不是「代码」

**这是任务 3 的硬要求：一套动作写在一个 yaml 里，播放器负责读它、展开成一串 goal、按顺序打出去。**

理由很直接：下周开始动作天天改（站立、走的预备姿、起身、挥手），每次改都动 python 就得重新编译、重新测。**动作是参数，不是逻辑。**

yaml 结构你自己设计，但必须同时表达得清这三件事：

| 必须能表达         | 说明                                                |
| ------------- | ------------------------------------------------- |
| **一步之内多舵机协同** | 同一个 step 里可以放好几个关节，各自带自己的目标值和用时，**同时下发**          |
| **步与步之间串行**   | 上一个 step 的 result 全回来了才允许进下一个，不许提前发               |
| **一步之内有先后**   | 某个关节必须先动，就给它单独开一个 step。**别靠调 `duration_ms` 硬凑先后** |

示意（**结构而已，字段名你自己定**）：

```text
一套动作 = 若干 step 组成的有序列表
每个 step = 若干条「哪个舵机 / 目标 PWM / 用多久」
```

> 📌 验收标准就一句：**换一套动作，只需新增一个 yaml，不用改一行 python。** 做到这样才给这 8 分。
>
> 播放器放 `cquick_servo` 包里，动作文件放 `config/actions/` 下，和 `servo_params.yaml` 同一层。

### 3.5 完成标准

- [ ] 整机装配完成，结构无松动、手动转关节不卡、**无刮线**；
- [ ] 上电前量过总电压，上电无异常；
- [ ] 全部舵机 ID 扫描在线，`servo_ids` 参数与实际一致；
- [ ] 用任务 2 的 Action 能**逐个**控制每个舵机，动作方向正确；
- [ ] **动作组流畅、可重复**，连跑三遍结果一致（误差肉眼看不出来）；
- [ ] **动作定义在 yaml 里**，播放器读 yaml 播放；现场随便换一份 yaml，不改代码就能跑；
- [ ] 动作组里**每个 goal 都收到了 result 才发下一个**（用日志证明，日志里要有 result 时间戳）;
- [ ] 能说明装配过程中遇到的一个具体问题以及怎么解决的。

**材料（截图带姓名 + 时间戳）**：整机照片（正面 + 侧面）/ **接线特写** / 电池电压读数 / 各舵机 ID 扫描结果 / 整机逐个动作录屏 / **动作组录屏（连跑三遍 + 换一套 yaml 再跑一遍）** / 动作组日志（能看到 result 时序）。

> **要交代码 + 交数据**：动作组播放器（读 yaml → 展开成 goal 序列 → 按 result 同步）放进 `cquick_servo` 包；动作定义的 yaml 放 `config/actions/`。**至少交两套动作**，交一套体现不出你是真数据驱动还是把一套动作硬编成了 yaml 的样子。

## 六、任务 4：安全下电　（10 分，必考）

### 4.1 固定流程

```text
先卸力  →  再断动力电（电池）  →  最后关板卡
```

| 步骤     | 做什么                               | 为什么是这个顺序              |
| ------ | --------------------------------- | --------------------- |
| ① 卸力   | 所有舵机发 `#xxxPULK!`（或上位机点「卸力 / 释放」） | 舵机断电前还在顶力矩，直接断电极易堵转发热 |
| ② 断动力电 | 拔电池                               | 先断动力，避免控制板在异常电压下乱发指令  |
| ③ 关板卡  | `sudo shutdown now`，别直接拔电         | 直接断电会损坏文件系统，下次开不了机    |

> 💡 **加分做法的提示**：`#xxxPULK!` 这一串也可以做成一个 `shutdown` 服务/参数触发的动作 —— 但**本周不要求**，先把手动流程做扎实。

### 4.2 四条红线

1. **禁止带电插拔舵机线。** 插拔瞬间的浪涌会烧舵机驱动或控制板通道，这是最常见的人为损坏。
2. **禁止反接电源。** 上电前必须量电压、看极性。
3. **电池鼓包立即停用**，交给队长，不要"再充一次看看"。充电必须有人看管，不短路、不过夜。
4. **禁止让舵机硬顶结构。** 持续「嗡嗡」就是堵转，立刻回中位，别加力硬刚。

### 4.3 完成标准

- [ ] 能**独立、完整、按顺序**演示一遍下电流程（评审现场看）；
- [ ] 能说出①②③顺序的**原因**，不只是背下来；
- [ ] 能说出带电插拔、反接、鼓包各自的后果。

**材料**：下电流程录屏一段（从发 `PULK` 到关机），带时间戳。**发 B 站，README 里贴链接**（和其他录屏一样，不放进仓库）。

> 任务 4 **不用交代码**，交录屏 + 当场演示就行。

## 十一、常见问题（FAQ）

### 接口编译（对应 2.1）

**Q1：`Cannot find message type` / `ros2 interface show` 说找不到包。**  
A：按顺序查四条：① `package.xml` 里是不是漏了 `<member_of_group>rosidl_interface_packages</member_of_group>`；② `CMakeLists.txt` 里 `rosidl_generate_interfaces` 之前有没有 `find_package(rosidl_default_generators REQUIRED)`；③ 改了 `.msg` 之后**没有重新 `colcon build`**（这是最多的）；④ 忘了 `source install/setup.bash`。

**Q2：`CMakeLists.txt` 明明在，`colcon build` 说找不到。**  
A：**Linux 区分大小写**。写成 `CMakelists.txt`（小写 l）在 Windows 上能过，在板卡上直接不认这个包。改名时注意 Windows/NTFS 下要两步：`git mv CMakeLists.txt tmp; git mv tmp CMakeLists.txt`，一步改大小写 git 可能不记录。

**Q3：python 包里能直接放 msg 吗？**  
A：能编，但会很难受。**接口单独一个 CMake 包**，这是本版明确要求的做法，别混。

### launch（对应 2.5）

**Q4：`ros2 launch` 报 `file not found` 或 yaml 加载不到。**  
A：九成是 `setup.py` 的 `data_files` 没把 `launch/`、`config/` 装进 `share/`。改完 `setup.py` **必须重新 `colcon build`**。查证：`ls install/cquick_servo/share/cquick_servo/launch`，没有就是没装进去。

**Q5：launch 起来了，但参数全是默认值，yaml 像是没生效。**  
A：yaml 顶层 key 必须和**节点名**一致（`Node(name='servo_driver')` ↔ yaml 里的 `servo_driver:`）。写错了**不报错**，只是静默不加载。用 `ros2 param get` 核对。

**Q6：`port:=/dev/ttyUSB1` 传了但没用。**  
A：`ParameterValue(LaunchConfiguration('port'), value_type=str)` 里的 `value_type` 不能省 —— 不写会被当数字解析，`/dev/ttyUSB1` 直接报错或忽略。

### 参数（对应 2.2、2.6）

**Q7：`ros2 param set` 返回 successful，但行为没变。**  
A：**本版最高频的坑**。原因是你在 `__init__` 里把值抄进了 `self.pwm_max`，之后再也没读过参数。改成每次判断时实时 `self.get_parameter('pwm_max').value`，或者在 `add_on_set_parameters_callback` 里同步更新 `self`。两条选一条，别混着用。

**Q8：`ros2 param set pwm_max 100000` 应该被拒，结果成功了。**  
A：你没注册 `add_on_set_parameters_callback`，或者注册了但不管 `pwm_max`。注意 Humble 里回调必须 `return SetParametersResult(successful=False, reason=...)` 才会真的拒。

**Q9：`ros2 param set` 报 `parameter is not declared`。**  
A：参数名拼错，或者节点根本没 `declare_parameter` 这个参数。`ros2 param list /servo_driver` 先看一眼有哪些。

**Q10：`grep` 自检的时候，我的协议字符串被算成硬编码了。**  
A：`#`、`!`、`PID`/`PRAD`/`PULR`/`PULK`、3 位补零这些是**协议常量**，不算。`ttyUSB`、`115200`、`900`/`2100` 这些是**配置**，必须参数化。

### Action（对应 2.3）

**Q11：`Ctrl+C` 取消 goal，节点没反应，舵机继续转。**  
A：`execute_callback` 在 executor 的单线程里跑，`time.sleep()` 把线程占死了，回调根本进不来。两件事都要做：① 用 `MultiThreadedExecutor`（`rclpy.init()` 之后 `executor = MultiThreadedExecutor(); executor.add_node(node); executor.spin()`）；② ActionServer 要挂 `ReentrantCallbackGroup`。

**Q12：feedback 一条都不来。**  
A：忘了 `goal_handle.publish_feedback(msg)`，或者循环里没有 sleep 直接跑完了（动作 1 秒，你 1 毫秒就返回 result）。feedback 至少 5 Hz。

**Q13：`ros2 action send_goal` 一直显示 goal accepted 但永远没 result。**  
A：`execute_callback` 里某处卡住了（串口没开、在等一个永远不来的数据）。看你自己的日志，别猜。

**Q14：`sleep` 用什么？**  
A：`time.sleep()` 在 `MultiThreadedExecutor` 里能用，但更稳的是用 `self.get_clock().sleep_for(...)` 或 `Rate`，并且每轮都检查 `goal_handle.is_cancel_requested`。

### bag（对应 2.7）

**Q15：bag 录出来一百多 MB。**  
A：你用了 `-a`。只录 `/servo/command /servo/state` 两个话题。再加 `--max-cache-size` 限内存。时长控制在 30 秒内。

**Q16：`ros2 bag play` 之后舵机不动。**  
A：驱动节点没订阅 `/servo/command`，或者话题名对不上（`ros2 topic list` 里没有就是没订上）。**这是硬性要求**，不订阅等于 2.7 没做。

### 串口与舵机（对应任务 1、2）

**Q17：`import serial` 报 `ModuleNotFoundError`。**  
A：装到**系统 Python**：`sudo apt install python3-serial`。如果之前给 ROS2 用过 conda，先 `conda deactivate`。

**Q18：打开串口报 `Permission denied: '/dev/ttyUSB0'`。**  
A：`sudo usermod -aG dialout $USER` 后**必须重新登录**（注销或重启）。`newgrp dialout` 只对当前终端临时生效。

**Q19：`ls /dev/ttyUSB*` 什么都没有。**

|                                                       |                                                   |
| ----------------------------------------------------- | ------------------------------------------------- |
| A：三查：① 线是不是只能充电不能传数据的「阉割线」；② 换主板后面的 USB 口；③ 跑 \`dmesg | tail -20`看认成了哪个名字（可能是`ttyACM0\`）。CH340 在部分系统要装驱动。 |

**Q20：串口里收到一堆乱码。**  
A：**99% 是波特率不对**。舵机是 **115200**，串口助手默认常是 9600。

**Q21：发了 `#001P1500T1000!`，舵机一动不动。**  
A：按概率查：① 忘发 `#001PULR!`（**最常见**）；② ID 不对（先 `#001PID!` 扫）；③ 结尾漏了 `!`；④ 电池低于 5V；⑤ `write` 后没 `flush`。

**Q22：舵机猛跳、有异响，或者一直「嗡嗡」响。**  
A：**立刻回中位。** 三件事：① 缩小 `pwm_min`~~`pwm_max`；② 查结构干涉；③ `duration_ms` 别给太小，500~~1000 让它平滑走。

**Q23：能直接用 500–2500 全范围吗？**  
A：**不能。** 那是电气范围。安全区间要实测，写进 `pwm_min`/`pwm_max`。

### 装配与动作组（对应任务 3）

**Q24：两个舵机一起动的时候互相打架。**  
A：**时序**问题。要么把它们放进同一个 step 让它俩同时走（同一个 step 内就是并行的），要么拆成两个 step、等前一个的 result 回来再发。不许用 `sleep` 猜。

**Q25：动作组每次跑出来都不一样。**  
A：**没等上一条指令走完就发了下一条**。舵机是「按时间平滑转到位」的，不是瞬间跳。用 result 当同步信号，或者发完读 `PRAD` 确认到位再继续。

**Q26：动作能不能直接写在 python 里？**  
A：**不行，这周这条是硬要求。** 写成一串 `goal` 硬编码在代码里的，扣 4 分。换动作必须只改 yaml —— 评审现场会给你一套没见过的新动作让你跑。

### 提交

**Q27：任务 2 能不能直接抄网上的舵机驱动代码？**  
A：**驱动那几行**（开串口、拼字符串、`write`）可以参考，我们自己也这么写。但**节点结构、Action 设计、参数设计、限位判断、调试记录必须是你自己的**，现场追问「这一行为什么这么写」，答不上来按抄处理。

**Q28：任务 1 没过，能不能先做任务 3 装配？**  
A：**不能。** 装配会把舵机零点固化进结构，零点还是错的话整机姿态就是歪的，**事后无法靠软件修正**。
