## 一、任务 1：自定义消息与发布订阅（40 分）

### 1.1 消息定义

`msg/BallPos.msg`：

```
int32 id
float32 x
float32 y
```

三个字段分别表示球的编号与平面坐标。包类型必须用 `ament_cmake`——`rosidl_generate_interfaces` 是 CMake 宏，`ament_python` 包的构建流程里没有生成消息代码这一步。

验证：

```bash
ros2 interface show ball_pkg/msg/BallPos
```

### 1.2 发布者设计

- 话题名 `/ball_pos`，消息类型 `BallPos`，队列深度 10
- 定时器 2 Hz（可调参数 `rate_hz`），每个周期连续发布 **3 条**消息，id 分别为 1 / 2 / 3
- 坐标写死为 `(2.0, 3.0)`、`(5.5, 8.0)`、`(9.0, 4.0)`，不随周期变化

### 1.3 频率可调（加分项）

频率通过 ROS 参数暴露，无需改代码：

```bash
ros2 run ball_pkg publisher.py --ros-args -p rate_hz:=5.0
ros2 param get /ball_publisher rate_hz    # Double value is: 5.0
```

用 `ros2 topic hz /ball_pos` 测量：

| 定时器频率 | 每周期消息数 | 实测消息频率 |
| ----- | ------ | ------ |
| 2 Hz  | 3      | 6 条/秒  |
| 5 Hz  | 3      | 15 条/秒 |

**注意**：`ros2 topic hz` 统计的是消息条数，不是定时器次数，所以是 2×3=6、5×3=15。若测出 30 左右，说明同时存在两个发布者（`ros2 topic info /ball_pos` 的 Publisher count 会显示 2）——这是我们实际踩过的坑。

### 1.4 订阅者设计

- 订阅 `/ball_pos`，回调里打印 `id / x / y`
- 订阅对象必须挂到 `self` 上（`self.sub = self.create_subscription(...)`）。写成局部变量会被 Python 垃圾回收，现象是「一条也收不到，但也不报错」

### 1.5 三种通信方式对比

|      | 话题 Topic      | 服务 Service                 | 动作 Action    |
| ---- | ------------- | -------------------------- | ------------ |
| 模型   | 发布 / 订阅       | 请求 / 响应                    | 目标 / 反馈 / 结果 |
| 通信关系 | 多对多           | 一对一                        | 一对一          |
| 方向   | 单向、持续数据流      | 同步、有返回值                    | 长任务、持续反馈     |
| 适用场景 | 持续广播状态，不关心谁在听 | 一次问答，要拿到结果                 | 执行时间长、可中途取消  |
| 本周实例 | `/ball_pos`   | `ros2 service call /clear` | 本周未使用        |

### 1.6 两个概念问题

**Q1：频率从 2 Hz 改到 5 Hz，变的是什么？**

数据内容没变（仍是那三组坐标、id 仍是 1/2/3），变的是发送节奏。节奏由**发布者**决定：`rate_hz` 是发布者的参数，控制它自己的定时器周期；订阅者只是被动接收，发多快就收多快，无法改变节奏。订阅者唯一的影响是队列深度——处理不过来时会丢旧消息，但那是丢数据，不是改节奏。

**Q2：发布者等订阅者回复吗？**

不等，这叫「发后即忘」。实测：订阅者没启动时，发布者照常发布，不报错也不停止。好处是发布者永远不被听众拖慢（视觉节点 30 Hz 发球位置，绝不能等下游回执）；风险是没人接收就等于白发，中途加入的订阅者收不到历史数据——比赛里表现为「慢半拍的决策节点拿到旧球位」。这与服务正好相反：服务必须有人应答才返回。

## 二、任务 2：闭环导航（35 分）

### 2.1 系统结构

```
publisher.py  --/ball_pos-->  nav_node.py  --/turtle1/cmd_vel-->  turtlesim
                                   ^                                  |
                                   +------/turtle1/pose---------------+
```

导航节点订阅两路数据（球坐标、乌龟位姿），计算后向 `cmd_vel` 发布 `Twist` 指令，形成闭环。

### 2.2 控制逻辑

每个周期（10 Hz）执行：

1. 目标点 = 当前球坐标；`dx, dy` = 目标 − 当前位置；`dist = hypot(dx, dy)`
2. 期望朝向 `target_theta = atan2(dy, dx)`
3. 角度误差归一化到 (-π, π]：  
   `err = atan2(sin(target_theta − theta), cos(target_theta − theta))`
4. 控制律：
   - `|err| > 0.15 rad`：只原地转，`angular.z = clamp(2.0 × err, ±1.5)`
   - 否则：边走边微调，`linear.x = min(0.6, 0.8 × dist)`
5. `dist < 0.15` 判定到达，切换到下一个目标；三个都到则停止

三个设计要点：

- **先对准再走**：偏差大于 8.6° 时只转不走，避免走出弧线
- **速度正比于距离**：越近越慢，靠减速而不是急停来过冲
- **角度归一化**：不归一化时，目标在身后会算成 350° 误差，乌龟舍近求远转一大圈

### 2.3 实测结果

| 目标  | 目标坐标         | 到达时实际坐标          | 位置误差  |
| --- | ------------ | ---------------- | ----- |
| 球 1 | (2.00, 3.00) | (2.12, 3.08)     | 0.144 |
| 球 2 | (5.50, 8.00) | (5.42, 7.88)     | 0.143 |
| 球 3 | (9.00, 4.00) | (8.90, 4.11)     | 0.148 |

全程用时约 15 秒，无人工干预。三次误差都在到达阈值 0.15 以内，说明「越近越慢 + 阈值判定」这组参数是可用的。

### 2.4 调试记录（遇到的问题）

1. **`ros2 run` 报 No executable found**：新终端未 source 工作空间，`ros2` 认得系统包但不认得自己的包。已把 `source ~/ros2_ws/install/setup.bash` 写入 `.bashrc`。
2. **脚本名带空格**：文件建成 `nav node.py`，`ros2 run` 按 `nav_node.py` 找不到。
3. **缺少执行权限**：新建脚本未 `chmod +x`，`ros2 run` 不把它当可执行文件。
4. **Windows 换行符**：从 Windows 粘贴代码带入 `\r`，shebang 变成 `python3\r`，启动即 `Exec format error`。
5. **`__name__` 行被输入法破坏**：引号被替换成中文弯引号/混入乱码，`main()` 不执行，脚本静默退出、不报错。这是最难查的一类问题——程序「正常结束」但什么都没干。

## 四、差速三公式

乌龟是两轮差速底盘，左右轮速 vL / vR，轮距 L：

- 线速度：`v = (vL + vR) / 2`
- 角速度：`ω = (vR − vL) / L`
- 转弯半径：`r = v / ω`（ω = 0 时走直线，ω 越小弯越大）

对应到 Twist：

| 想要   | 给什么                                |
| ---- | ---------------------------------- |
| 直行   | `linear.x = v`，`angular.z = 0`      |
| 原地转  | `linear.x = 0`，`angular.z ≠ 0`      |
| 边走边转 | 两者都非 0                             |

任务 2 用的是第一、二种的组合：方位差大时只给 `angular.z`（原地转），对准后两者同时给（边走边微调）。
