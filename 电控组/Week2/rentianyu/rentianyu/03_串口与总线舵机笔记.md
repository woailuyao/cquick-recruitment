## 一、串口四个参数

| 参数 | 是什么 | 常见值 | 我的理解 |
|---|---|---|---|
| 波特率 | 每秒传多少位，双方必须一致 | 115200、9600 | 相当于"说话速度"，两边语速必须一样，否则听成乱码 |
| 数据位 | 一个字符用几位 | 8 | 一个字节的数据部分，8 位正好凑一个 char |
| 停止位 | 一帧的结尾标志 | 1 | 告诉接收方"这个字符传完了"，同时给下一次起始位留出间隔 |
| 校验位 | 简单查错 | 无（N） | 用一个额外位做奇偶校验，简单场景常关掉，靠协议自己校验 |

**8-N-1 = 8 个数据位、无校验位、1 个停止位。**

实际一帧要传 10 位：1 个起始位 + 8 个数据位 + 0 个校验位 + 1 个停止位。所以 115200 波特率下每秒能传的有效字节是：

```
115200 ÷ 10 = 11520 字节/秒
```

这条换算很有用：它能算出"一帧指令（比如 13 个字符）传过去只要约 1.1 ms"，所以 115200 对舵机控制完全够用。

## 二、波特率不一致为什么会乱码（原理）

串口是**异步**通信：只有一根数据线，**没有时钟线**。既然没有时钟，接收方靠什么知道每一位该采多久？靠**起始位**。

一位一位看这个过程：

1. 线路空闲时是高电平。
2. 发送方要发数据，先把线拉低一个位宽 —— 这就是**起始位**。接收方看到这个下降沿，知道"数据来了"，并从这一刻开始计时。
3. 之后接收方按**自己的位宽**去采样每一位。位宽 = 1 / 波特率：
   - 115200 → 每位约 8.68 µs
   - 9600 → 每位约 104 µs
4. 理想情况：发送方和接收方位宽一致，采样点始终落在每一位的正中间，读出来就是对的。

波特率不一致时发生什么：

- 发送方按 115200 发，每位 8.68 µs；接收方按 9600 收，以为每位有 104 µs。
- 接收方在第一个起始位对齐后开始数，但它的"一位"长度是对方的 12 倍左右，**采样点会迅速漂移到后面几位上**。
- 采到的电平组合跟原始字节毫无关系 → 屏幕上就是一堆乱码（`烫烫烫`、`�` 这类）。
- 更严重时，接收方在它以为的"停止位"位置读到低电平，硬件直接报 **Framing Error（帧错误）**——因为停止位按协议必须是高电平。

**结论：波特率不是"越快越好"，而是"两边必须完全一致"。** 误差容忍度很小（一般要求 2% 以内），因为采样点的偏移会随位数累积，漂过半个位宽就必然读错。这也是为什么调试串口时"能收到但全是乱码"，第一反应就该去查两边波特率。

## 三、三个必须搞懂的点

**1. 单线半双工**
总线舵机把收发合并在一根信号线上：舵机发出去的数据，自己也会"听到"。所以同一条总线上**不能两个设备同时说话**，否则信号叠加，谁都读不出来。指令是"一问一答"的节奏：主机先发 `#001PRAD!`，舵机再回位置值。

**2. 共地（GND 必须连）**
"高电平"和"低电平"是相对 GND 而言的电压差。如果两块板只接了 TX/RX 没接 GND，两边没有共同的参考零点，接收方根本无法判断某根线到底是高还是低 —— 现象就是"线都接对了但一个字节都收不到"。所以接线第一件事永远是**先共地**。

**3. 电平不匹配**
5V 器件的输出高电平是 5V，直接接到 3.3V 器件的 RX 上，会通过它内部的保护二极管灌电流，轻则工作异常，重则烧掉 3.3V 那一侧。要么用逻辑电平转换模块，要么确认器件引脚本身是 5V 容忍的。舵机控制器与 USB 转 TTL 模块之间同样要注意这一点。

## 四、总线舵机指令逐字拆解

总线舵机和普通舵机最大的区别：**不靠单独的 PWM 信号线，所有舵机挂在同一条串口总线上，用 ID 区分**。指令是可读的 ASCII 字符串，`#` 开头、`!` 结尾。

### 4.1 `#001P1500T1000!` 七段拆解

| 段 | 内容 | 含义 |
|---|---|---|
| `#` | 帧起始符 | 告诉舵机"一条新指令开始了" |
| `001` | 舵机 ID，固定 3 位 | 1 号舵机（不足 3 位要补零） |
| `P` | 位置指令标志 | 后面跟的是目标 PWM 值 |
| `1500` | PWM 值，固定 4 位 | 范围 500–2500，**1500 = 中立位**（约 90°） |
| `T` | 时间指令标志 | 后面跟的是运动时间 |
| `1000` | 时间值，固定 4 位，单位 **ms** | 用 1000 ms（1 秒）平滑转到位，不是瞬间跳过去 |
| `!` | 帧结束符 | 告诉舵机"这条指令到此为止" |

整句读法：**让 1 号舵机在 1000 ms 内平滑转到 PWM=1500 的中立位置。**

为什么 `T` 重要：舵机是**按给定时间插值运动**的，`T` 太长动作慢、太短会猛冲甚至抖动过流。这也解释了为什么不能"瞬间给目标角"——机械结构承受不了突变。

### 4.2 自己写两条

**① 1 号舵机转到中立位，用 1.5 秒**

```
#001P1500T1500!
```

拆解：`#` + `001`（1 号）+ `P` + `1500`（中立 PWM）+ `T` + `1500`（**时间单位是 ms，1.5 s = 1500 ms**，注意不是写 1.5）+ `!`

**② 3 号舵机卸力**

```
#003PULK!
```

拆解：`#` + `003`（3 号）+ `PULK`（卸力指令）+ `!`

补充一句：卸力之后再想让它动，必须先发 `#003PULR!` 恢复扭力，否则发角度指令它**纹丝不动**——因为卸力状态下电机不输出力矩。

### 4.3 常用指令速查

| 功能 | 指令 | 说明 |
|---|---|---|
| 控制角度 | `#001P1500T1000!` | 1 号转到 PWM 1500，用时 1000 ms |
| 读 ID | `#001PID!` | 查询当前舵机 ID |
| 读位置 | `#001PRAD!` | 读回当前 PWM 位置 |
| 恢复扭力 | `#001PULR!` | 重新上力，**动之前必须先发** |
| 卸力 | `#001PULK!` | 安全下电必发，防止堵转发热烧舵机 |

## 五、回环测试

**状态：未做。计划下周拿到舵机后补做。**

原因：本周不发舵机，也没有自购 CH340 USB 转 TTL 模块，手上没有可用的串口硬件。

**如果做了，我会这样做 / 预期看到什么：**

- 接线：CH340 的 **TX 用杜邦线短接到 RX**，GND 不需要额外接（同一模块），形成自发自收。
- 用串口助手或 `minicom`/`screen` 打开端口，参数设 **115200-8-N-1**。
- 发送字符串 `AT`，预期**原样收到 `AT`**：字符不丢、不花、不重复。
- 发送 `#001P1500T1000!`，预期原样收到同一串字符——这就是"回环通了"的直接证据。
- **对照实验**：把一端改成 9600、另一端保持 115200，再发 `AT`，预期收到乱码或帧错误。这一步能把第二节的原理亲手验证一遍，比看十遍文档都牢。

回环通了说明三件事都对了：线接对了（TX/RX 交叉或短接）、GND 参考一致、两边波特率一致。

## 六、我还没搞懂的问题

**问题 1：为什么必须先 `PULR` 才能动？卸力之后位置信息还在吗？**

我的理解：`PULK` 是切断电机力矩，让它变成"自由状态"，但舵机内部的磁编码器/电位器应该还在工作，所以位置读数理论上还在。那为什么恢复扭力后它不会自己弹回原来的位置，而是保持当前（被外力掰到的）位置？

还没想明白的是：`PULR` 之后舵机的目标位置是"上一次指令给的值"，还是"当前实际位置"？如果是前者，卸力期间被外力掰动过，一上力会不会突然弹回去、甚至打坏机构？

**问题 2：同一条总线上多个舵机同时回数据会不会撞？**

读 ID 的时候，如果总线上挂了 6 个舵机，我发 `#001PID!`，是不是只有 1 号会回答？如果是广播查询（不带 ID），六个同时回答，单线半双工不就直接撞车了吗？协议里是靠时间片轮询，还是靠 ID 优先级？

**问题 3：`T` 时间设太短会发生什么？**

`T` 设成 10 ms 让它从 500 转到 2500，等于要求极高角速度。这时舵机会不会因为跟不上而抖动、或者电流过大触发保护？工程上有没有经验公式（比如 60° 最少给多少 ms）？
