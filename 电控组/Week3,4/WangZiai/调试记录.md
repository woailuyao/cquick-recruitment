# 调试记录

> 记的是"每天干了什么、卡在哪、怎么过的"。只写过程和证据，结论都在 README 里。

## 11-12 · 第一天：点灯、认 ID

- 接线：USB-TTL 的 TXD 接舵机信号（橙/白）、GND 接舵机棕/黑和电池负极、舵机红线单独接电池正。上电前万用表量了电池，**7.99 V**。
- 装 `python3-serial`，把自己加进 `dialout` 组，`ls -l /dev/ttyUSB*` 能看到设备。
- 第一件事就卡住：发 `#001PID!`、`#001PRAD!` 全都没有回显，但串口能打开、能写。
- 试过的错误方向：换波特率（9600 / 57600 / 115200 都试了）、怀疑线序反了把 TXD/RXD 对调、换 USB 口。
- 最后是**发广播**问出来的：`#255PID!` 回 `#003P!` —— 舵机的出厂 ID 其实是 **000**，我一直在给 001 发指令。
- 用 `#000PID001!` 改成 001（回 `#001P!#OK!`），再发 `#001PRAD!` 就回 `#001P1504!` 了。

**教训**：先发广播确认"总线上有没有人、是谁"，再谈驱动。

## 11-13 · 第二天：串口说没就没

- 同一套线，昨天还能用，今天 `ros2 launch ... port:=/dev/ttyUSB0` 一启动就报
  `could not open port /dev/ttyUSB0: [Errno 5] Input/output error`。
- `ls -l /dev/ttyUSB*` 发现只有 **ttyUSB1**，ttyUSB0 不存在了 —— 拔插过一次，编号漂了。
- 临时改 `port:=/dev/ttyUSB1` 能用，但这不能交给别人用。
- 写了 udev 规则 `99-cq-servo.rules`（`1a86:7523` → `SYMLINK+="cq_servo"`），`udevadm reload/trigger` 之后 `/dev/cq_servo` 稳定出现。
- 顺手发现：**这个固件对 `P...T...` 运动指令根本不回显**，只有 `PID`/`PRAD` 会回。之前以为"没回显=没收到"判断错了。
- 当天还遇到 `dmesg` 刷 `ch341-uart ttyUSB0: failed to read modem status: -110`，换了一根短一点的 USB 线才稳定。

## 11-14 · 第三天：把 ROS2 这条链接起来

- 建两个包：`cquick_servo_interfaces`（msg + action）和 `cquick_servo`（驱动 / 客户端 / 播放器）。
- 第一次编译就踩到"中文路径"：工作区放在 `~/桌面/ROS2` 时 `rosidl` 报 `list index out of range`，换到 `~/ros2_ws` 立刻正常。
- Action 跑通：`send_goal {id: 1, target_pwm: 1800, duration_ms: 1200}` → `SUCCEEDED`，`actual=1794, error=6`。
- 参数化：`ros2 param set /servo_driver pwm_max 1600` 之后同一个 goal 被拒，调回 2100 又能过 —— 证明限位确实是从参数读的，不是写死的。

## 11-15 · 第四天：录 bag、写证据

- `ros2 bag record -o bag/run1 /servo/command /servo/state`，跑一遍 `nod`，Ctrl+C。
- `ros2 bag info`：11.38 s、42 条、25.5 KB，两个话题各 21 条。
- 坑：`-o bag/run1` 时目录已存在会直接失败；还有一次没 source 工作空间，回放时提示 `package 'cquick_servo_interfaces' not found`，加上 source 就好了。

## 11-19 · 第五天：上板（地瓜派 RDK X5）

- 板子上装 ROS2 Humble，把两个包拷过去 `colcon build`。
- 又遇到一次坑：`--symlink-install` 在板子上对 `config/actions/*.yaml` **不生效**，install 里是真实副本。我改了 src 的 yaml 却发现动作没变，`md5sum` 对比两份文件才发现读的是旧的那份。
- 处理：`rm -rf build/<pkg> install/<pkg>` 重编；后来干脆把 install 里的配置换成指向 src 的软链，改完即生效。
- 网络也坑了一次：同一个 Wi-Fi 下 DHCP 换池，板子 IP 从 `10.109.133.99` 变成 `172.28.198.99`，ssh 直接超时。扫网段 + 认主机名才找回来，之后改成用 `rdkx5.local` 访问。

## 11-22 · 第六天：动作组跑不完整

- 现象：`squat_down` 跑到一半报 `step 1：舵机 3 失败 —— 读不到位置（PRAD 无应答）`，整组取消。
- 连跑 3 次能复现 1 次，说明不是必现。
- 逐个 ID 裸串口发 `PRAD` 各 10 次：除 1 号 3/10 外，其余都是 10/10 —— 硬件基本没问题，怀疑总线忙。
- 翻驱动日志看到 `⚠ 串口应答偏慢：8 段中有 8 段超时`。**每一步都在等一个不会来的应答**：`move()` 走的是"要应答"的 `_cmd()`，写完之后还要等满 50 ms 超时才返回；4 个舵机并行，一步就白耗 200 ms，把总线占满了，后面 PRAD 回读自然超时。
- 改成 `_cmd_fast()`（只写不读），只有 `read_pos()` / `ping()` 仍等应答。改完连跑 5 次 5/5 成功，单次动作从 3.4 s 降到 2.3 s。
- 还是偶发 `应答偏慢：8 段中有 1 段超时`，但不影响动作，先留着观察。
