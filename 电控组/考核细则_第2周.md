## 一、本周目标

第 1 周你让小乌龟动了，也知道了 `ros2 run` 是怎么回事。但那时候**每一条指令都是你手敲的**。真正的足球机器人打比赛时没有人按键：

```
视觉节点算出「场上有 3 个球，坐标分别是 …」 → 发布 BallPos
   ↓ 话题（Topic）
战术决策节点算出「先去哪一个」 → 发布 Twist 速度指令
   ↓ 话题（Topic）
运动控制节点把速度换算成左右轮转速 → 串口发给下位机
   ↓ 串口（UART）
单片机驱动电机（含总线舵机）→ 机器人真的动起来
```

本周的三项任务，正好对应这条链路上的三个环节：

| 任务   | 对应链路的哪一环 | 干什么                                    |
| ---- | -------- | -------------------------------------- |
| 任务 1 | 上层「传数据」  | 自己定义 `BallPos` 消息，把 **3 个球**的坐标发布出去并打印 |
| 任务 2 | 中层「发指令」  | 订阅这 3 个坐标，用 `Twist` 让乌龟**依次**走过去       |
| 任务 3 | 底层「通物理」  | 搞懂串口，先**看懂**总线舵机的串口指令（下周线下实操）          |

> ⚠️ **本细则只给流程和要求，不提供现成代码。** 电控组的日常就是「查文档 + 试错 + 问 AI」，能自己把流程走通才算学会。卡住是正常的，卡住之后查到了才叫学到。

### 任务 1：自定义消息 + 发布 3 个球的坐标　（40 分）

**要做什么**：新建一个 ROS2 包，自己定义球的位置消息 `BallPos`，写一个**发布者**把下面 3 个固定坐标循环发出去，再写一个**订阅者**收到后打印出来。最后用自己的话讲清「话题 / 服务 / 动作」三种通信方式。

#### 1.1 消息设计要求（字段固定，不要自创）

消息名 `BallPos`，三个字段：

| 字段   | 类型        | 含义             |
| ---- | --------- | -------------- |
| `id` | `int32`   | 球编号（1 / 2 / 3） |
| `x`  | `float32` | 球在场地坐标系下的 x（米） |
| `y`  | `float32` | 球在场地坐标系下的 y（米） |

> 为什么要 `id`：场上有 3 个球，得让接收端能分清「这是第几个球」。真实视觉系统也是这么干的——一条话题上跑很多目标，靠 id 区分。这个设计后面会一直用。

#### 1.2 三个球的坐标（**写死，不许改**）

| 球编号 | x       | y       | 位置说明     |
| --- | ------- | ------- | -------- |
| 1   | **2.0** | **3.0** | 左下（我方半场） |
| 2   | **5.5** | **8.0** | 中上（对方半场） |
| 3   | **9.0** | **4.0** | 右下（边路）   |

> **必须用这三个值，一个都不能改。** 评审会用同一组坐标复跑你的代码，你改了值，跑出来的结果和你截图对不上。
>
> **说明**：这三个坐标直接落在小乌龟的场地坐标系里（0~11），所以「球坐标」和「乌龟坐标」是同一个系——这是为了本周好上手做的简化。真实比赛里视觉给的是球场坐标，要经过坐标变换才能交给底盘

#### 1.3 流程（照着走，代码自己写）

**第 1 步 · 建包**  
用 `ament_cmake` 类型建包（**不能用 `ament_python`**——自定义消息必须走 CMake 编译流程）。建完之后自己补一个 `msg/` 目录和一个 `scripts/` 目录。

**第 2 步 · 写消息文件**  
在 `msg/` 下建 `BallPos.msg`，按 1.1 的三行字段写进去。注意类型写法是 `int32` / `float32`，行内 `#` 后面是注释。

**第 3 步 · 改 `package.xml`（最容易漏的一步）**  
除了自动生成的 `ament_cmake`，你至少还要让这些内容出现：消息生成工具、`rclpy`、消息运行时依赖，以及一条「声明本包属于接口包分组」的标签（`member_of_group`）。少任何一个，第 6 步编译都会报一堆 `rosidl` 相关的错。

> 👉 **具体是哪些标签、写在哪里，自己查**

**第 4 步 · 改 `CMakeLists.txt`**  
你需要在这里做两件事：① 调用消息生成宏，把 `msg/BallPos.msg` 编成消息类型；② 把 `scripts/` 下的 Python 脚本安装成**可执行程序**，放进包的 `lib/<包名>` 目录（不装的话 `ros2 run` 会报 No executable found）。

**第 5 步 · 写发布者和订阅者**

- **发布者**：创建发布者 → 定时器按固定频率（建议 2 Hz）触发 → **每个周期把 3 个球依次发一遍**（id 1、2、3，坐标用 1.2 的表）→ 发的同时打印自己发了什么；
- **订阅者**：创建订阅者（**话题名必须和发布者一字不差**，建议就叫 `ball_pos`）→ 回调里把 `id / x / y` 打印出来；
- 两个脚本都要 `chmod +x`，否则既装不上也跑不起来。

**第 6 步 · 编译、验证、跑起来**

```bash
cd ~/ros2_ws
colcon build --packages-select <你的包名>
source install/setup.bash

ros2 interface show <你的包名>/msg/BallPos     # 应看到 id / x / y
ros2 run <你的包名> <发布者脚本>
ros2 run <你的包名> <订阅者脚本>               # 另开终端，记得先 source
ros2 topic info /ball_pos                      # Publisher 1 / Subscription 1
```

#### 1.4 三种通信方式对比（写进 README）

| 通信方式           | 模型        | 特点             | 足球机器人典型场景                |
| -------------- | --------- | -------------- | ------------------------ |
| **话题 Topic**   | 发布/订阅，多对多 | 单向、持续流、不管对方在不在 | 视觉持续广播球位置；战术持续广播速度指令     |
| **服务 Service** | 请求/响应，一对一 | 同步、有返回值、调一次答一次 | 「现在比分多少」「切到防守模式」         |
| **动作 Action**  | 目标/反馈/结果  | 长任务、报进度、可取消    | 「走到点 (1,1)」→ 过程报进度，可中途取消 |

**任务 1 用的是话题**（一直发，不管有没有人听）。**任务 2 开头你要执行的那条清屏命令 `ros2 service call /clear std_srvs/srv/Empty`，就是一次服务调用**——注意它必须有回应、且只调一次就结束，这就是服务和话题最直观的差别。

**完成标准**：

- [ ] `ros2 interface show <包名>/msg/BallPos` 能看到 `id`、`x`、`y` 三个字段；
- [ ] 发布端每个周期连发 3 条（id 1/2/3），订阅端**持续**收到并打印；
- [ ] 自己改过一处（如发布频率 2 Hz → 5 Hz），能说出订阅端的变化；
- [ ] 能讲清：节点 / 话题 / 消息 / 发布者 / 订阅者五个词分别是什么，两个节点靠什么「对上号」。

**截图要求（缺一不可，必须带姓名 + 时间戳）**：

1. `ros2 interface show <包名>/msg/BallPos` 的输出（证明消息定义成功）；
2. `colcon build` 无报错 + 两终端**同时运行**、订阅端在打印的截图（分屏）；
3. `ros2 topic info /ball_pos` 的输出（Publisher 1 / Subscription 1）；
4. 改频率后订阅端输出变化的截图。

### 任务 2：订阅 3 个球坐标，依次走过去　（35 分）

**要做什么**：写一个节点，**订阅任务 1 的 `ball_pos`**，收齐 3 个球之后，用 `Twist` 让乌龟按 **1 → 2 → 3 的顺序**依次走到这三个坐标，每到一个就在日志里报一次。

> 这就是足球机器人最基础的战术行为：**「视觉告诉我球在哪 → 我过去」**。你写的这段逻辑，就是比赛里「追球」的放大版。

#### 2.1 先搞清 Twist 和转弯原理

`geometry_msgs/msg/Twist` 本周只用两个字段：`linear.x`（线速度，m/s）和 `angular.z`（角速度，rad/s，正值 = 左转）。

乌龟是**两轮差速底盘**，设左右轮速 `vL`、`vR`，轮距 `L`：

- 线速度：`v = (vL + vR) / 2`
- 角速度：`ω = (vR − vL) / L`
- 转弯半径：`r = v / ω`（ω 越小弯越大，ω = 0 走直线）

| 想要       | 该给什么                           |
| -------- | ------------------------------ |
| 直行       | `linear.x = v`，`angular.z = 0` |
| 原地转      | `linear.x = 0`，`angular.z ≠ 0` |
| 边走边转（画弧） | 两者都非 0                         |

#### 2.2 两条实现路线（任选一条，做到了就算过）

**路线 A（推荐）· 闭环跟随**  
两个动作配合：**订阅 `/turtle1/pose` 拿到乌龟当前 (x, y, θ)**，再根据「目标点 − 当前点」实时算该往哪走。核心思路就三句：

1. 算出到目标点的**距离**和**方位角**；
2. 方位角相差大 → 原地转（`linear.x = 0`），先对准再走；
3. 方位角对上了 → 边走边微调，**越接近目标速度越小**（否则一定冲过头）；距离小于阈值就认为到了，切下一个点。

这套「用反馈修正自己」的做法叫**闭环**，是运动控制最核心的思想。

**路线 B（兜底）· 开环按时间估算**  
不算方位差，直接按「转多少角度 = ω × t」「走多远 = v × t」估算每段给多久。缺点是：`Twist` 是**速度不是位移**，误差会累积，越到后面越偏。**能依次到达三个点（误差在容许范围内）同样给分**

#### 2.3 通关判定（评审按这个量）

| 项    | 要求                               |
| ---- | -------------------------------- |
| 顺序   | 必须 1 → 2 → 3，不能跳、不能倒             |
| 到点精度 | 每个点最终位置与目标点的距离 **≤ 0.5**（乌龟坐标单位） |
| 证据   | 日志里能看到「到达球 1 / 2 / 3」并打出实际坐标     |
| 全程   | 无人工按键，一次跑完                       |

**几个实用提示**（不涉及代码，自己实现）：

- 开始前先 `ros2 service call /clear std_srvs/srv/Empty` 清屏，轨迹才看得清；
- 乌龟默认**落笔**，走过去会留下轨迹，这就是你最好的证据图；
- 乌龟出生点在 **(5.54, 5.54)**，三个目标点都在画布内且离墙很远，不用担心撞墙；
- **收齐 3 个球再动**：用字典按 `id` 存坐标，长度到 3 才开始；没收齐就继续等（发布端 2 Hz，最多等 1 秒）；
- 日志一定要打「到达第 N 个球，实际坐标 (x, y)，误差 d」

**完成标准**：

- [ ] 乌龟按 1→2→3 依次走到三个固定坐标，全程无人工按键，一次跑完；
- [ ] 每个点误差 ≤ 0.5，日志里有实际坐标和误差；
- [ ] 能讲清代码里 `linear.x` / `angular.z` 各在什么时候给、为什么「先对准再走」；
- [ ] 能说出 `v = (vL+vR)/2`、`ω = (vR−vL)/L`、`r = v/ω` 三个式子的含义。

**截图要求（缺一不可，带姓名 + 时间戳）**：

1. 乌龟走完三个点、**轨迹清楚可见**的窗口截图；
2. 运行日志截图（能看到「到达球 1/2/3」+ 误差）；
3. `ros2 node list` 截图（能看到你的导航节点）；
4. 三个点的最终误差汇总（日志里打出来的那几行）。

### 任务 3：串口基础 + 总线舵机串口模式（只交学习笔记）　（25 分）

> **本周不发舵机**——舵机下周线下拼装时才发。这一项**不动手控舵机**，目标只有三个字：**搞懂、看懂**。

#### 3.1 先说清楚：回环测试不影响本周成绩

**本周考核只看笔记，不看回环测试有没有做。** 没做回环测试**一分不扣**，下周拿到舵机后统一补做。

想现在就动手的，两条路：

- **自己买**一个 **CH340**（USB 转 TTL 串口模块，几块钱），把 TX 和 RX 用杜邦线短接就能做回环；
- **来实验室拿舵机**（配 24 路舵机控制器，本身就有串口），跟下周发的是同一套设备，提前摸一遍也行。

做了的话，笔记里如实写现象，**加 3 分**；没做就写「未做，下周补做」+ 你的预期，不扣分。

#### 3.2 串口四个参数（必须背下来）

| 参数      | 是什么               | 常见值         |
| ------- | ----------------- | ----------- |
| **波特率** | 每秒传多少位，双方**必须一致** | 115200、9600 |
| **数据位** | 一个字符用几位           | 8           |
| **停止位** | 一帧的结尾标志           | 1           |
| **校验位** | 简单查错              | 无（N）        |

默认组合写作 **8-N-1**。**波特率不一致 = 收到一堆乱码**，这不是设备坏了，是采样节拍对不上。

#### 3.3 三个必须搞懂的点（笔记评分重点）

1. **单线半双工**：收发共用一根线，自己发出去的数据自己也会「听到」。所以同一条总线上不能两个设备同时说话。
2. **共地（GND 必须连）**：两个设备只有电平参考点相同，才能判断「高」还是「低」。只接 TX/RX 不接地，收不到数据是必然的。
3. **电平不匹配**：5V 和 3.3V 设备不能直连，会烧 3.3V 那一侧。要么加电平转换，要么确认器件本身兼容。

#### 3.4 看懂：众灵总线舵机的串口指令格式

总线舵机不靠单独的 PWM 信号线，而是**所有舵机挂在同一条串口总线上，用 ID 区分**。指令是 ASCII 字符串，`#` 开头 `!` 结尾。

| 功能   | 指令                | 说明                                  |
| ---- | ----------------- | ----------------------------------- |
| 控制角度 | `#001P1500T1000!` | 1 号舵机转到 PWM **1500**，用时 **1000 ms** |
| 读 ID | `#001PID!`        | 查询当前舵机 ID                           |
| 读位置  | `#001PRAD!`       | 读回当前 PWM 位置                         |
| 恢复扭力 | `#001PULR!`       | 重新上力（**要它动之前必须先发这个**）               |
| 卸力   | `#001PULK!`       | 断电前卸力，防止堵转发热烧舵机（**安全下电必发**）         |

**字段规则（写笔记要逐字拆）**：

- ID 固定 **3 位**，1 号写 `001`；
- PWM 固定 **4 位**，范围 **500–2500**，**1500 = 中立位**；
- 时间固定 **4 位**，单位 **ms**（舵机用这段时间平滑转到位，不是瞬间跳）；
- 通信参数：**波特率 115200**，供电 **5–8.4V**。

## 七、常见问题（FAQ）

**Q1：`from <包名>.msg import BallPos` 报 ModuleNotFoundError。**


A：八成没 source。`cd ~/ros2_ws && colcon build --packages-select <包名> && source install/setup.bash`，并且**在同一个终端里**启动节点。

**Q2：`ros2 run` 说 No executable found。**  
A：`CMakeLists.txt` 里没把脚本 `install(PROGRAMS ...)`，或者脚本没有可执行权限（`chmod +x scripts/*.py`）。改完必须重新 `colcon build`。

**Q3：编译时报一堆 `rosidl` / `member_of_group` 相关错误。**  
A：这是自定义消息最经典的坑，99% 是 `package.xml` 里少声明「本包属于接口包分组」。搜关键词 `ros2 自定义 msg member_of_group` 就能找到，照着补一行即可。

**Q4：订阅者一直在等，一条都收不到。**  
A：查三处：① 话题名是否完全一致；② 发布端真的在跑吗（看它自己的日志）；③ `ros2 topic info /ball_pos` 看 Publisher / Subscription 是不是各 1。

**Q5：乌龟走到点附近打转 / 冲过头。**  
A：典型的速度控制没收敛。**越近越慢**（速度跟距离挂钩）、**降低最大速度**、**放宽到点阈值**。先做到「能到」，再谈快。

**Q6：任务 2 要不要重写一遍任务 1 的发布者？**  
A：不用。任务 1 的发布者原样跑着，任务 2 的节点在**另一个终端**订阅同一个话题——这就是话题「一对多」的意义：一个视觉节点发数据，好几个决策节点能同时听。

**Q7：能把坐标改成自己想要的值吗？**  
A：不能。改了任务 1 扣 10 分、任务 2 直接判不通过。坐标是**统一基准**，跟比赛里「场地尺寸必须一致」是一个道理。

**Q8：没有 CH340 也没去实验室，任务 3 会废吗？**  
A：不会。任务 3 的分全在笔记上，回环测试是加分项、不是必做项。**下周拿到舵机一定补做**。

## 九、下周预告

**第 3 周：线下拼装 + 单舵机可控。**

舵机发下来后，第一件事不是「让它转」，而是按这个链条走一遍：

```
读 ID（#001PID!） → 恢复扭力（#001PULR!） → 写角度（#001P1500T1000!）
→ 读位置（#001PRAD!） → 卸力（#001PULK!）
```

**顺序不能乱**：不读 ID 就不知道总线上有谁；不先 PULR 就写角度，舵机会纹丝不动；不下电 PULK，舵机会一直顶着力发热。**回环测试也在这一周补做。**
