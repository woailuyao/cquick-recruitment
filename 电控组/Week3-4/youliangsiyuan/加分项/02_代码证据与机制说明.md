## 1. PRAD 闭环校验（细则 +3）

### 参数

```yaml
prad_tolerance: 30        # 允许误差（PWM）
prad_retries: 1           # 超差时自动重发次数
```

参数声明在 `servo_driver.py` 第 166~167 行，并在参数校验回调里限制为非负（第 271~279 行）。

### 实现流程（`servo_driver.py` 第 653~699 行）

```python
# ---- 5) PRAD 闭环校验（加分项 +3）----
tolerance = int(self.get_parameter('prad_tolerance').value)
retries = int(self.get_parameter('prad_retries').value)
final_pwm = self._read_prad(servo_id)

attempt = 0
while (final_pwm is not None
       and abs(final_pwm - applied) > tolerance
       and attempt < retries):
    attempt += 1
    self.get_logger().warn(
        f'[PRAD] 未到位：目标 {applied}，实测 {final_pwm}，'
        f'差 {abs(final_pwm - applied)} > {tolerance} -> 第 {attempt} 次重发')
    self._watchdog_arm((duration_ms + 300) * 1_000_000)
    self._dispatch(servo_id, target, duration_ms)      # 重发一次
    self.get_clock().sleep_for(Duration(seconds=duration_ms / 1000.0))
    final_pwm = self._read_prad(servo_id)              # 重发后再读

result.retry_count = attempt
```

到位与未到位的结论分别写进 Result：

- 到位：`到位：目标 X，PRAD 读回 Y，误差 Z <= 30`（第 685~692 行）
- 未到位：`没到位：目标 X，PRAD 读回 Y，差 Z > 30（已重发 N 次）` 并 `abort()`（第 694~698 行）

`retry_count` 字段就是给评审看“这次到底重发了几次”，正常为 0。

### 实测证据与机制边界

已在真机完成“未到位 → 重发 → 到位”验证，证据见 `03_Prad闭环_未到位重发到位.png`。测试使用 `id=2, pwm=1300, duration_ms=300`，并临时设置 `prad_tolerance=25`、`prad_retries=1`：

```text
第一次：目标 1181（已叠加 ID 2 的 offset），实测 1211，误差 30 > 25
重发后：PRAD 读回 1202，误差 21 <= 25，success=true，retry_count=1
```

这是通过缩短动作时长，让第一次读回发生在行进中而人为构造的真实触发。常规停稳动作中，重发同一目标不保证位置继续改善；容差过小也可能重发后仍失败，因此不能把该机制描述成“只要重发就一定到位”。测试结束后参数已恢复为 `prad_tolerance=30`、`prad_retries=1`。

## 2. 安全看门狗（细则 +3）

### 参数

```yaml
watchdog_timeout_s: 1.0   # 动作推进停滞超过 1 s 就全部卸力
```

### 机制

| 环节 | 代码位置 | 行为 |
|---|---|---|
| 布防 | `_watchdog_arm()` 第 720~731 行 | 每个 goal 每推进一步就重算截止时间 `now + timeout` |
| 撤防 | `_watchdog_disarm()` 第 732~734 行 | 正常到位后清除截止时间 |
| 巡检 | `_tick_safety()` 第 735~766 行，10 Hz 定时器（第 133 行 `create_timer(0.1, ...)`） | 超过截止时间 → 置 `_watchdog_tripped=True` → **对全部舵机发 `PULK`** → 打 ERROR |
| 锁死 | 第 591~592、630~631 行 | 触发后所有新 goal 直接 `abort()`，message 为“看门狗已触发，全部舵机已卸力；确认安全后…” |
| 恢复 | 第 744~753 行 | 只有外部把 `torque_enable` 设回 `true` 才清除 `_watchdog_tripped` 并重新上力；**不会自己乱动** |

触发时的 ERROR 日志（第 761~765 行）：

```text
看门狗触发：动作推进超过 1.0s 没有进展，已全部 PULK 卸力
```

### 实测证据

已临时将 `watchdog_timeout_s` 设为 `0.05`，配合 `duration_ms=50` 的短动作制造推进停滞，并在真机验证了完整过程：

1. 看门狗触发并输出 ERROR；
2. 对 ID 1～10 全部发送 `PULK` 卸力；
3. 后续 goal 因看门狗锁死而被拒；
4. 外部确认安全、设置 `torque_enable=true` 后才恢复上力，后续 goal 可正常执行。

证据见 `04_看门狗_触发卸力与外部恢复.png`。测试结束后已恢复 `watchdog_timeout_s=1.0`、`torque_enable=true`。

## 3. 串口掉线自动重连（细则 +3）

### 参数

```yaml
reconnect_interval_s: 1.0   # 重连定时器周期
```

### 机制

| 环节 | 代码位置 | 行为 |
|---|---|---|
| 定时器 | 第 134~135 行 | 每 `reconnect_interval_s` 跑一次 `_tick_serial` |
| 巡检 | `_tick_serial()` 第 351~359 行 | 端口/波特率参数变了 → 重开；`_serial_ok` 为假 → 重试打开 |
| 写失败处理 | `_write_locked()` 第 371~373 行 | 捕获 `SerialException/OSError`，**不抛出、不让节点崩溃**，置 `_serial_ok=False` 并打 ERROR“串口写入失败（USB 可能掉了）” |
| 打开失败去重 | 第 330~340 行 | 只有失败原因变化才打 WARN，避免每秒刷屏；WARN 会提示“之后会每 1.0s 自动重试，不再重复刷屏” |

也就是说：拔掉 USB 后节点继续活着，每 1 秒尝试打开一次；插回去后 `_open_serial()` 成功即恢复可用。

### 实测证据

已在运行 `sync_check.yaml` 期间拔掉 USB-TTL，等待约 3～5 秒后插回，真机验证了“写入失败 → 节点保持运行 → 每秒重试 → 插回自动恢复”：

- 拔线后出现串口写入失败，随后按 `reconnect_interval_s=1.0` 周期尝试重新打开端口；
- 拔线期间 `ros2 node list` 仍能看到 `/servo_driver`，进程 PID 未变，说明节点没有崩溃；
- 插回后日志重新出现“串口已打开”，后续 goal 可正常执行；
- 播放器因部分 goal 未到位而退出，这是“任一 goal 失败即停止后续动作”的设计行为，不代表重连失败。

证据见 `05_串口重连_拔插恢复.png`。拔线期间动作推进停滞还真实触发了看门狗，因此恢复后继续控制前需要确认安全并设置 `torque_enable=true`。

## 4. 与看门狗相关的一个诚实说明

细则原文是“节点持续发 `/servo/state` 心跳；超过 1 秒没心跳就自动 PULK”。

我的实现是**以“动作推进是否停滞”作为看门狗判据**：每推进一步重新布防，超过 `watchdog_timeout_s` 没有任何推进就 PULK 并锁死。`/servo/state` 的 1 Hz 心跳是独立发布的（第 132 行 `create_timer(1.0, self._publish_state)`，发布实现见第 474~482 行），但看门狗并不直接监听这个话题。

这个差异必须在答辩时讲清楚，不能把它说成“严格按心跳实现”。它覆盖的实际风险是一样的：上位机卡死、播放器挂在半路、goal 推进停滞时，舵机不会一直顶着满力矩烧结构。
