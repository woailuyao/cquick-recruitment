## 二、重点问题详述

### 2.1 PRAD 偶发无回显（#1）

**现象**
同一个舵机、同一波特率，`#001PID!` 每次都有回显，但 `#001PRAD!` 大约每 10 次有 1～2 次收不到。

**怀疑**
1. 半双工总线：舵机正在按 `T` 平滑走位时，板子内部在跑定时器，此时收到查询会丢掉；
2. 驱动里 `reset_input_buffer()` 把**迟到的回复**清掉了；
3. 动作后等待时间不够（`duration_ms=1000` 只等了 1.2 s）。

**验证**
- 写 `prad_check.py` 连发 10 次 PRAD，统计成功次数；
- 把动作后的等待从 1.2 s 提到 1.4 s，成功率上升但仍有偶发；
- 打印原始字节，确认是"没有回复"而不是"回复被截断"。

**结论与修改**
属总线时序问题，不是硬件故障。驱动中把 PRAD 读取改为**带重试**：

```python
def _transact(self, cmd, wait=0.8, retries=3):
    for _ in range(retries):
        # 发命令 + 按 '!' 收帧
        if buf.strip():
            return buf.strip()
        time.sleep(0.2)
    return b''
```

同时 `PULR` 之后加 300 ms 间隔（见 2.2）。

### 2.2 PULR 后立即发位置指令被丢弃（#5，最有价值的一条）

**现象**
ROS 节点发出的所有 goal 都"执行"了，但 PRAD 读回一直是 1506（原位），客户端 feedback 却显示 progress 到 1.0。
手动用串口助手发同样的指令，舵机能正常转到 1800。

**怀疑**
节点里是这样写的：

```python
self._send(self._cmd(sid, C_TORQUE_ON))   # PULR
time.sleep(0.02)                          # 只等 20 ms
self._send(self._cmd(sid, C_MOVE, target, dur))
```

**怀疑点**：`PULR`（恢复扭力）之后板子需要时间生效，20 ms 太短，位置指令被丢弃。

**验证（关键）**
停掉节点（释放串口），用一段独立脚本手动发：

```python
tx("#001PULR!", 1.5)      # 恢复扭力，等 1.5 秒
rad()                     # 读回 1506
tx("#001P1800T2000!", 2.4)
rad()                     # 读回 1790  ← 舵机确实转了
```

**结论**
舵机与接线都是好的，问题在**命令间隔**。修改驱动：`PULR` 后统一等 **300 ms**（4 处：正常执行、PRAD 重发前的重试、调试话题、启动回中位）。

**这条的教训**：`feedback` 里的 `current_pwm` 是"起点到目标"的插值，**不是实测值**。判断是否真的到位，只能看 `PRAD` 读回值和 `result.final_pwm`。后来在 README 的接口契约里也写明了这一点。

### 2.3 duration_ms = 800 时位置指令不执行（#6）

**现象**
把演示动作的 `duration_ms` 从 1000 改成 800 之后，所有 goal 全部报"未到位"，PRAD 停在 1493。

**验证**
把所有历史数据排在一起对比：

| duration | 结果 |
|---|---|
| 800  | ❌ 卡 1506 / 1493（4 次全失败） |
| 1000 | ✅ 1690 / 1218 / 1489 |
| 1200 | ✅ 1685 / 1221 / 1485 |
| 1500 | ✅ 1688 |

**结论**
本机 `T < 1000 ms` 时位置指令实际不执行（可能是板子对最小 `T` 有限制）。
处理：演示与默认值统一用 **1200 ms**；`config/servo_params.yaml` 里 `default_duration_ms: 1200`，README 参数表中注明原因。

### 2.4 Ctrl+C 取消 goal 无效（#4）

**现象**
`ros2 run cquick_servo move_client --duration 5000` 执行中按 `Ctrl+C`，程序直接退出等待，但服务端 goal 跑满 5 s 并返回 `success=True`。

**怀疑**
`except KeyboardInterrupt` 永远不触发 → rclpy 把 SIGINT 变成了 `context.shutdown()`，而不是抛 `KeyboardInterrupt`。

**验证**
- 去掉 `except` 后现象不变，说明确实没抛异常；
- 在 `rclpy.init()` 之后加一行 `signal.signal(signal.SIGINT, signal.default_int_handler)`，`Ctrl+C` 立刻能进 `except` 分支。

**结论与修改**
客户端增加：

```python
rclpy.init()
signal.signal(signal.SIGINT, signal.default_int_handler)
```

并增加 `--cancel-after 1.5` 参数，用**程序化取消**做确定性演示（不依赖手速）：

```bash
ros2 run cquick_servo move_client --id 1 --pwm 1900 --duration 8000 --cancel-after 1.5
```

结果：`success=False final_pwm=0 message=canceled`，服务端日志 `收到取消请求，接受` + `[cancel] id=1 停发、卸力、回中位`。

**另一个隐患（已修）**：取消分支里 `PULK`、`PULR`、`P1500T600` 三条背靠背发送，中间无间隔，可能导致 `PULR` 被吞、舵机停在卸力状态。改为每条之间 `time.sleep(0.1)`。

### 2.5 bag 里 /servo/command 为 0 条（#7）

**现象**
按要求只录 `/servo/command` 和 `/servo/state`，但 `ros2 bag info` 显示 `/servo/command` 消息数为 0，`ros2 bag play` 时舵机不动。

**原因**
驱动节点只**订阅**了 `/servo/command`，从来没有任何节点**发布**它 —— 录出来自然是空的。

**修改**
在 `execute_callback` 里把收到的 goal 镜像发布一次，并加一个时间窗抑制自身回环（否则节点会收到自己发的消息，导致一条 goal 执行两次）：

```python
self._cmd_pub.publish(self._make_cmd(sid, target, dur))
self._ignore_topic_until = time.monotonic() + dur / 1000.0 + 1.0
```

订阅回调里：

```python
if time.monotonic() < self._ignore_topic_until:
    self.get_logger().debug('/servo/command 回环忽略（本节点 Action 刚发过）')
    return
```

**验证**
- 录制后 `/servo/command` 有 3～4 条消息；
- `ros2 bag play` 时舵机重演 1700 → 1200 → 1500，与录屏一致。

### 2.6 bag 时长超标（#8）

**现象**
第一次录完 `Duration: 143.9 s`，超过 ≤30 s 的要求（体积只有 33.5 KiB，说明不是数据量问题）。

**原因**
开始录制后，中间隔了 2 分半才去发 goal，1 Hz 的 `/servo/state` 心跳一直在写。

**处理**
开始录制后 15 s 内发完三条 goal 并 `Ctrl+C`。重录后 `Duration` 落在 12～20 s。

### 2.7 虚拟机 USB 直通掉线（#11）

**现象**
```
termios.error: (5, 'Input/output error')
serial.serialutil.SerialException: Could not configure port: (5, 'Input/output error')
```
串口打不开，但 `/dev/ttyUSB0` 这个文件还在。

**怀疑**
USB 设备已经从虚拟机"松手"，但 udev 的节点残留，形成"僵尸设备"。

**验证**

```bash
lsusb | grep -i ch34        # 无输出
ls -l /dev/ttyUSB*          # No such file or directory
```

设备确实不在了。在 VMware 菜单 `虚拟机 → 可移动设备` 里也没有对应条目。

**处理**
重新插拔并在菜单中勾选 `QinHeng USB Serial`（出现 ✓ 表示归虚拟机），设备恢复。

**经验**
排查顺序固定为：**`lsusb` 看设备在不在 → `ls /dev/ttyUSB*` 看节点 → 再跑脚本**。
遇到 `Input/output error` 不要反复重试脚本，先确认设备是否还活着。

### 2.8 电池接入瞬间打火（#9）

**现象**
电池插入瞬间有小火花，之后一切正常。

**判断依据**

| 观察项 | 结果 |
|---|---|
| 火花是否持续 | 仅瞬间 |
| 有无焦味 | 无 |
| 控制板/线材是否发烫 | 不烫 |
| 电池电压 | 7.93 V（正常） |

**结论**
控制板上大容量电解电容充电造成的浪涌电流，属正常现象。频繁打火会使插头镀层氧化，导致接触电阻变大，长期隐患。
建议：换 XT30/XT60 防打火插头，或加船型开关（开关断开时接线），或串 10 Ω/5 W 电阻预充。

## 四、这轮调试得到的经验

1. **先分化故障域，再动手**。`PID` 有回显说明链路通，`PRAD` 无回显只说明读失败，两者含义完全不同，不能混为一谈。
2. **feedback 不等于实测**。插值算出来的 `current_pwm` 会骗人，判断到位必须看 `PRAD` 与 `result.final_pwm`。
3. **绕开上位机做一次手动验证，比改十行代码有用**。"手动能转、节点不能转"这一条直接把问题锁死在命令间隔上。
4. **数据对比胜过硬猜**。`duration` 与成功率的对应关系是靠 8 次记录排出来的，不是试出来的。
5. **虚拟机里的串口问题，先看 `lsusb`**。`/dev/ttyUSB0` 存在不代表设备存在。
6. **验收指标要提前量化**。bag 的时长、消息条数、体积都是有硬指标的，录之前就该定好节奏。
