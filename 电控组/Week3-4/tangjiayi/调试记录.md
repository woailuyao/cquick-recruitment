## 三、这周必须搞懂的问题（答辩会问）

| 问题 | 我的回答 |
| --- | --- |
| 为什么必须先 `PULR`？ | `PULK` / `PULR` 控制的是**输出轴锁不锁**。卸力态下电机会断电，位置指令只被记下、不产生扭矩，表现就是"发 1650 读回还是 1503、纹丝不动"。11-19 那次我发 1450 和 1650 读回都是 1502，就是卸力/保护态；先 `PULR`（或断电重上电）恢复力，再发 `P###T###` 才动。所以顺序固定：**先给力，再给位置** |
| 为什么指令要 `!` 结尾？ | `!` 是帧结束符。舵机靠它判断"这一条收完了"，没收完就整条丢弃、一个字节都不回 —— 这是最容易误判成"舵机坏了"的地方（少个 `!` 时回包是空的）。上位机这一侧同理，`serial_link` 也是按 `#` 开头、`!` 结尾切帧，两边的帧边界必须一致 |
| 波特率错了会看到什么？ | 串口**能打开**，但查询指令全无回包，或者读到 `b''` / 带 `\x00` 的乱码 —— 字节被采样错位，`#` 和 `!` 对不上，切不出帧。和硬件故障的区别：设备层故障报 `Errno 5`（打不开），波特率错是"打得开、没回包" |
| `execute_callback` 为什么不能阻塞？ | 它在 executor 线程里跑，一阻塞就把同一节点的其它回调全堵死：cancel 请求进不来（取消失效）、`/servo/heartbeat` 收不到（看门狗误跳闸）、参数服务也没响应。我们吃过这个亏（11-08 那条：Ctrl+C 后舵机仍走完全程）。现在 `execute_callback` 只做"接 goal → 丢给工作线程 → 立刻 return"，执行器用 `MultiThreadedExecutor` + `ReentrantCallbackGroup` |
| 为什么装结构前必须标定 1500？ | 装摆臂那一刻的姿态就是**机械零点**。四只实测中位是 1503 / 1496 / 1483 / 1480，本身就差 20 步；带着这个偏差装上去，偏差会被固化进结构，而且左右腿还不一样，成对动作就走歪、一转身就顶限位堵转发热。先标定 1500 再装，才能保证"动作组里写 1500 = 机械真的回中" |
| 动作组为什么不能用 `sleep` 同步？ | `sleep` 只知道"过了多久"，不知道"到没到位"。实际到位时间随负载、温度变化（同一个 600ms 的目标，实测会差 148 步没走到、需要重发），`sleep` 会在没到位时就发下一条，指令互相覆盖；而且它阻塞线程，取消插不进来。`sequence_player` 是逐条 `send_goal_async` 并**等 result**，`SUCCEEDED` 才发下一条，失败立即中止整组 |
| 你的 `pwm_min/pwm_max` 是怎么定出来的？ | 扫出来的，不是拍的，也不是电气范围 500~2500。**上限**：发 2100 读回 2089（`SUCCEEDED`），说明行程到 2089，取 `pwm_max: 2100`。**下限**：1400/1300/1200/1100/1000 全部成功（读回 1412/1313/1212/1113/1008），950 和 900 都卡在 **1007** 且 `ABORTED`（差 +57/+107 > 容差 30），判定 1007 到底；取 `pwm_min: 1050`，留 40 多步余量。原值 900 比硬件还宽，区间里有 100 多步是"发了也白发、等 2 秒再 ABORTED" |
