# 动作组：自己动手的操作方法

从「结构装完、串口可用」开始。全部命令在虚拟机里执行。

---

## 0. 先判断串口活着没有

每条动作之前先做这一条，比事后查半小时快：

```bash
ls -l /dev/ttyUSB*
```

- 时间戳是**刚才** → 串口刚被重新枚举过，大概率是死的
- 确认死没死：

```bash
python3 -c "import serial; s=serial.Serial('/dev/ttyUSB0',115200); print('可用'); s.close()"
```

- 打印 `可用` → 正常，往下走
- 报 `Errno 5 Input/output error` 或 `Errno 32 Broken pipe` → **串口死了**

### 串口死了怎么救（三种，按顺序试）

| 方法 | 操作 | 生效时间 |
|---|---|---|
| 1. 物理拔插 | 把 USB 转 TTL 从电脑上拔下来，等 2 秒，插回去（**换个 USB 口更好**） | 立刻 |
| 2. VirtualBox 菜单 | 窗口菜单「设备 → USB」→ 把 `QinHeng CH340` 取消勾选，等 2 秒再勾上 | 立刻 |
| 3. 命令行 | 见下方两条命令 | 不一定成功 |

命令行方式（宿主机 Windows 的 Git Bash 里执行）：

```bash
VBox="/c/Program Files/Oracle/VirtualBox/VBoxManage.exe"
"$VBox" controlvm "Ubuntu22.04" usbdetach e6764271-437b-4d6b-ad4c-306d71d6be15
sleep 4
"$VBox" controlvm "Ubuntu22.04" usbattach e6764271-437b-4d6b-ad4c-306d71d6be15
```

> 这两个命令报 `DetachUSBDevice ... error` 时，说明 USB 代理已经彻底卡住，
> 命令救不回来，**只能用方法 1 或 2**。

### 根治（建议做，但要关机）

CH340 是 USB 1.1 设备，虚拟机的 USB 控制器是 xHCI(3.0)，这种组合在高频串口通信时会掉线。
关掉虚拟机后，在宿主机执行：

```bash
VBox="/c/Program Files/Oracle/VirtualBox/VBoxManage.exe"
"$VBox" modifyvm "Ubuntu22.04" --usb-xhci off --usb-ehci on
```

再开机。之后 CH340 走 USB 2.0 控制器，掉线基本消失。

## 1. 把 10 个舵机回正

**做任何动作之前都要先回正**，保证每次起点一致。

```bash
# 串口是独占的，必须先停掉节点
pkill -f "[s]ervo_driver"

# 逐个回 1500，并读回实际位置
python3 ~/t1.py center
```

正常输出（每只一行）：

```
舵机 01 -> PRAD=1513  偏差 13 ✓
舵机 02 -> PRAD=1507  偏差  7 ✓
...
>>> 全部到位（±50），可以装舵臂，装的时候保持这个姿态别上电
```

**判据：10 行全部 `✓`，最后一句是「全部到位」。** 有 `✗` 就先查串口，再查那只舵机。

`~/t1.py` 是 `~/rec_ws/src/cquick_servo/tools/t1_servo.py` 的软链接，会自动找 `/dev/ttyUSB*`，不用管编号。

其他两个常用命令：

```bash
python3 ~/t1.py scan     # 扫在线 ID（结构装好后线动过就重扫一次）
python3 ~/t1.py pulk     # 全部卸力（收工前必做，免得长期堵转烧舵机）
```

## 2. 动作怎么写成 yaml

**动作是数据，不是代码**。换动作只改 yaml，不碰 Python。

文件放：`~/rec_ws/src/cquick_servo/config/actions/你的动作名.yaml`

```yaml
name: my_action              # 动作名，随便取
description: 我自己的动作     # 说明，可以不写

defaults:
  duration_ms: 1000          # 本文件默认动作时长，单个 joint 可以覆盖

steps:
  - name: 全部回中位          # 第 1 步
    joints:
      - {id: 1, pwm: 1500}
      - {id: 2, pwm: 1500}
      - {id: 3, pwm: 1500}

  - name: 三号抬一下          # 第 2 步
    joints: [{id: 3, pwm: 1650, duration_ms: 800}]

  - name: 一二号同时外摆       # 第 3 步
    joints:
      - {id: 1, pwm: 1620}
      - {id: 2, pwm: 1380}
```

### 四条规则

| 规则 | 说明 |
|---|---|
| `steps` 从上到下**顺序执行** | 第 2 步一定在第 1 步全部 result 回来之后才开始 |
| 同一个 step 里的 `joints` **同时下发** | 想同步动就写在一起，想先后动就拆成两个 step |
| `pwm` 必须在 **900–2100** | 超了直接报错，不会下发 |
| `id` 必须在 `servo_ids` 里 | 当前是 `[0..10]`，整机实扫是 001–010 |

### 三个现成文件可以参考

```bash
cat ~/rec_ws/src/cquick_servo/config/actions/check_all.yaml   # 31 步，逐关节自检
cat ~/rec_ws/src/cquick_servo/config/actions/stand_up.yaml    # 4 步，30 个 goal
cat ~/rec_ws/src/cquick_servo/config/actions/wave.yaml        # 9 步，18 个 goal
```

**新建 yaml 不用重新 `colcon build`**，播放器会自动去源码目录找。

## 3. 跑动作

```bash
cd ~/rec_ws
source /opt/ros/humble/setup.bash
source install/setup.bash

# ① 先看有哪些动作
ros2 run cquick_servo sequence_player --list

# ② 干跑：只把 yaml 展开成 goal 打印出来，一个字节都不发给舵机
ros2 run cquick_servo sequence_player --action my_action --dry-run

# ③ 真跑
ros2 run cquick_servo sequence_player --action my_action

# ④ 连跑三遍，自动比对每遍的 final_pwm
ros2 run cquick_servo sequence_player --action my_action --repeat 3

# ⑤ 一条命令起全套（节点 + 动作组）
ros2 launch cquick_servo servo.launch.py action:=my_action repeat:=1
```

**顺序别跳**：`--list` → `--dry-run` → 真跑。干跑能提前发现 id 写错、pwm 超域、字段名拼错。

## 4. 日志怎么读

### 正常的样子

```
[step 1/4] 全部回中位：同时下发 10 个 goal  id=1→1500(1200ms) id=2→1500 ...
[step 1/4] 全部 result 已回（2.47s），允许进入下一步
[step 2/4] 第一组撑起：同时下发 5 个 goal  ...
```

`全部 result 已回（2.47s）` 里的秒数 ≈ 该步最长的那个 goal 的时长。**如果它比 duration 大很多，说明串口在读 PRAD 上卡了。**

### 四种异常

| 日志 | 含义 | 怎么办 |
|---|---|---|
| `未确认到位: target=1680 PRAD 多次无回显` | 串口断了 / 多舵机并发时总线忙 | 先查串口（第 0 节），通了重跑 |
| `Ignoring unexpected goal/result response. There may be more than one action server` | **有两个 servo_driver 在跑** | `pkill -f "[r]os2 launch"; pkill -f "[s]ervo_driver"` 再起一个 |
| `串口打开失败(...)，进入仿真模式` | 串口没开成，**舵机不会动** | 一定先看到「串口已打开」再继续 |
| `串口名漂移：/dev/ttyUSB0 无应答，自动改用 /dev/ttyUSB1` | 枚举号变了，自动找回来了 | 正常，可以继续 |

### 必须确认的两行

启动时：

```
[servo_driver-1] [INFO] 串口已打开: /dev/ttyUSB0 @ 115200（已加独占锁）
```

**没有这一行就停下来。**「仿真模式」下一切日志都正常，但舵机一动不动。

动作时：

```
[servo_driver-1] [INFO] 动作结束: ok, PRAD=1577
```

`PRAD=` 后面必须是**实测值**，不会刚好等于目标值。如果 `final_pwm` 每次都和目标一模一样，说明读到的是假数据。

## 附：这次踩到的两个真 bug（已经修了，答辩可以讲）

**① 读不到位置时拿目标值冒充实测**

原来 PRAD 读不到就 `actual_pwm = target_pwm`，于是 `success` 永远 true、
`final_pwm` 永远等于目标值。等于驱动替舵机签字，日志完全失去证据价值。
现在真机读不到就 `success=False` + `message` 说明原因，只有仿真模式才按目标值记。

**② 并发时读错别的舵机的位置**

原来解析 PRAD 只用 `\d+` 抓数字，不校验回显里的 ID。5~10 个 goal 同时收尾时，
总线上别人的回显会被当自己的位置读走。现在按 `#007P1498!` 校验 ID，
并且读之前 `reset_input_buffer()` 清掉残留。
