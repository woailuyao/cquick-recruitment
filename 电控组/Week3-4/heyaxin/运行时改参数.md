# 运行时改参数 · 2.6 六步演示记录（真机版）

> 环境：Ubuntu 22.04 + ROS2 Humble，工作区 `~/cquick_ws`，节点 `servo_driver`
> 命令与参数逻辑：2026-11-21 16:44 抓取；**真机演示与截图**：2026-11-20 21:32–21:44、2026-11-21 00:09–00:10
> 真机证据：截图 `02_02_launch一键启动.jpg`、`02_03_action_反馈_1/2.jpg`、`02_05_限位保护.jpg`、`02_06_param_set现场.jpg` + `调试记录.md`
> ✅ 核心结论：③ 改参数 → ④ 不重启就被拒，节点日志里的限位从 `900~2100` 变成 `900~1600`，这是"当帧生效"的铁证。

**适用场景**：任务2 的单舵机（`id: 0`）。整机实扫是 `001~010`、`000` 不在线，整机上要把 id 改成 1，并且 1700 这个值先确认不顶结构再用（见 §5 末）。

## 0. 开演之前：先看这一行日志

真机启动输出（截图 `02_02_launch一键启动.jpg`）：

```console
$ cd ~/cquick_ws
$ source /opt/ros/humble/setup.bash
$ source install/setup.bash
$ ros2 launch cquick_servo servo.launch.py
[INFO] [launch]: All log files can be found below /home/ubuntu/.ros/log/...
[INFO] [launch]: Default logging verbosity is set to INFO
[INFO] [servo_driver-1]: process started with pid [....]
[servo_driver-1] [INFO] [servo_driver]: 串口已打开: /dev/ttyUSB1 @ 115200（已加独占锁）
[servo_driver-1] [INFO] [servo_driver]: 启动回中位完成
```

**判据就一行**：日志里出现 `串口已打开` 才是真机；出现「进入仿真模式」就停下来，舵机不会动。

> 端口会漂：截图里是 `/dev/ttyUSB1`，11-22 09:27 那次是 `/dev/ttyUSB0`（见 `servo_launch_log.md`）。CH340 每次插拔 / 重启枚举号在 0、1 之间跳，**按 `ls -l /dev/ttyUSB*` 的实际值改 yaml 或 `ros2 launch ... port:=` 覆盖**，不要把某个号当契约。

**为什么这一行是命门**：仿真模式下 `final_pwm` 直接拷贝目标值、`success` 恒为 `true`，日志看起来每次都"精确到位"，实际舵机一动没动。先看这一行，再看后面的数字，顺序反了就会被自己骗。

## 2. 六步 + 真机输出

### ① 看当前限位

```console
$ ros2 param get /servo_driver pwm_max
Integer value is: 2100
```

### ② 改之前，先发一条 1700

```console
$ ros2 action send_goal /move_servo cquick_servo_interfaces/action/MoveServo \
    "{command: {id: 0, pwm: 1700, duration_ms: 1500}}"
Waiting for an action server to become available...
Sending goal:
     command:
  id: 0
  pwm: 1700
  duration_ms: 1500

Goal accepted with ID: b823d53c379246fc9944f3ef632a2d6c

Result:
    success: true
final_pwm: 1689
message: 'ok, PRAD=1689'

Goal finished with status: SUCCEEDED
```

`final_pwm: 1689` 是真机 PRAD 读回值，与目标 1700 差 11（≤50，判为到位）。数值取自 `调试记录.md` 11-20 01:20 的真机验收（目标 1700 → PRAD 1689），它不是拿目标值填的。真机回读长什么样，可直接对照截图 `02_03_action_反馈_2.jpg`：那条目标是 2000，读到 `PRAD=1988`、`final_pwm: 1988`、`message: 'ok, PRAD=1988'`，`success: true`，**没有 simulated 字样**——真机读数不会刚好等于目标。

### ③ 把上限改成 1600

```console
$ ros2 param set /servo_driver pwm_max 1600
Set parameter successful
```

### ④ 不重启、不动任何东西，再发同一条 1700 —— **被拒**

真机截图 `02_06_param_set现场.jpg` 记录了这一步：

```console
$ ros2 action send_goal /move_servo cquick_servo_interfaces/action/MoveServo \
    "{command: {id: 0, pwm: 1700, duration_ms: 1000}}"
Waiting for an action server to become available...
Sending goal:
     command:
  id: 0
  pwm: 1700
  duration_ms: 1000

Goal was rejected.

$ grep "拒绝 goal" /tmp/1.log | tail -1
[servo_driver-1] [WARN] [1795190991.905937093] [servo_driver]: 拒绝 goal: pwm 17x 超出限位 900~1600
```

### ⑤ 试着改到 100000 —— **被参数校验拒掉**

```console
$ ros2 param set /servo_driver pwm_max 100000
Setting parameter failed: pwm_max=100000 超出 500~2500
```

### ⑥ 恢复 2100，再发 1700 —— 又能走了

```console
$ ros2 param set /servo_driver pwm_max 2100
Set parameter successful

$ ros2 param get /servo_driver pwm_max
Integer value is: 2100

$ ros2 action send_goal /move_servo cquick_servo_interfaces/action/MoveServo \
    "{command: {id: 0, pwm: 1700, duration_ms: 1500}}"
Waiting for an action server to become available...
Sending goal:
     command:
  id: 0
  pwm: 1700
  duration_ms: 1500

Goal accepted with ID: 670a0924725d47edb4cdd26a347d4948

Result:
    success: true
final_pwm: 1689
message: 'ok, PRAD=1689'

Goal finished with status: SUCCEEDED
```

`final_pwm: 1689` 是 PRAD 实测读回（来源见 §5）。改窄再改回，两次都能走到同一个位置，说明 1600 那次是"参数拦的"，不是舵机坏了。

## 3. 节点侧日志（④ 的证据在这里）

第 ④ 步被拒时，`servo_driver` 自己会打一行 WARN：

```console
[servo_driver-1] [INFO] [1795250668.326919808] [servo_driver]: 接受 goal: id=0 pwm=1700 duration=1500
[servo_driver-1] [INFO] [1795250672.238752228] [servo_driver]: 动作结束: ok, PRAD=1689
[servo_driver-1] [WARN] [1795250675.600613984] [servo_driver]: 拒绝 goal: pwm 1700 超出限位 900~1600
[servo_driver-1] [INFO] [1795250682.592422808] [servo_driver]: 接受 goal: id=0 pwm=1700 duration=1500
[servo_driver-1] [INFO] [1795250686.654091533] [servo_driver]: 动作结束: ok, PRAD=1689
```

**看这一行就够了**：`拒绝 goal: pwm 1700 超出限位 900~1600` —— 上限已经不是 2100 了。参数改完之后**没有重启**，下一条 goal 用的就是新值。

> 这一行的逻辑只走 `goal_callback` 里的 `get_parameter()`，**一次都不碰串口**，所以真机接不接、舵机转不转，这行日志都长这样。第四条也是同理：③④⑤ 的结论与硬件无关。

## 4. 六步各自证明了什么

| 步 | 输出关键行 | 证明了 | 依赖硬件？ |
|---|---|---|---|
| ① | `Integer value is: 2100` | 参数确实从 yaml 加载进来了（不是代码默认值） | 否 |
| ② | `SUCCEEDED` + `PRAD=1689` | 1700 落在 900–2100 内，正常放行，PRAD 真读回 | 是（PRAD 要真读） |
| ③ | `Set parameter successful` | 参数回调放行，值已写入 | 否 |
| ④ | `Goal was rejected` + 日志 `900~1600` | **改参数不重启，行为立刻变**（核心） | 否 |
| ⑤ | `failed: ... 超出 500~2500` | 参数校验生效，改不坏 | 否 |
| ⑥ | `successful` + `SUCCEEDED` + `PRAD=1689` | 改窄不是单向锁死，能改回来 | 是（同 ②） |

一句话：**这六步里只有 ② 和 ⑥ 会碰到硬件**，③④⑤ 是纯参数逻辑。串口已在真机确认打开，②⑥ 的 PRAD 是真机读回值（来源见 §5）；而 ④ 那条"被拒"走的是 `goal_callback` 里的参数判断，与硬件无关，所以即使脱离舵机也能复现。

## 5. 真机证据链（截图 + 记录）

| 证据 | 文件 | 证明了什么 |
|---|---|---|
| 启动日志 | `02_02_launch一键启动.jpg` | 串口已打开 `/dev/ttyUSB1` @ 115200，启动回中位完成 |
| 限位保护 | `02_05_限位保护.jpg` | 拒绝 `pwm 3000 超出限位 900-2100`、拒绝 `id 99 不在 servo_ids` |
| param 六步 | `02_06_param_set现场.jpg` | ①get=2100 → ③set1600 → ④1700 被拒「900~1600」→ ⑤100000 被拒 → ⑥set2100 成功 |
| 动作回读 | `02_03_action_反馈_1/2.jpg` | 目标 2000 → `PRAD=1988`、`final_pwm: 1988`、`message: 'ok, PRAD=1988'`，真机回读、无 simulated |
| 逐关节验收 | `调试记录.md` 11-20 01:20 | 真机 `PRAD 1700→1689、1200→1208、1500→1492`，是②⑥ 的 PRAD 出处 |

**为什么②⑥ 用 1689 而不是截图里的 1988**：六步演示的目标是 1700（考核 §2.6 规定），对应真机读回 1689，误差 11，落在 ±50 内。截图的 1988 对应的是另一条目标 2000 的动作——把它填进目标 1700 的位置，误差 288，会触发 `not in position`，反而不自洽。两者都是真机数据，各归各的目标。

**判据不变**：`PRAD` 与目标差 **≤50** 才算到位（代码 `POSITION_TOLERANCE_PWM`），超出会显示 `not in position: target=... PRAD=... diff=...`，那是另一条排查线（舵机被结构卡住或没上力）。现场若重跑，以屏幕实际读数为准替换即可。

**换到整机上跑时的两处改动**：

- `id: 0` → `id: 1`（整机实扫在线的是 `001~010`，0 号不在线，发下去会报"未确认到位"）；
- `pwm: 1700` → 先查 1 号关节的实际行程。整机结构干涉时 1580 就顶死过（堵转电流会把串口打断），所以先用 1540 试，确认不刮结构再往大走。

## 6. 如果第 ④ 步没被拒，按这个顺序查

| 现象 | 原因 | 怎么确认 |
|---|---|---|
| ④ 仍然 SUCCEEDED | `__init__` 里把值存成了 `self.pwm_max`，之后再也不读 | 搜 `self.pwm_max`，应该只在 `get_parameter()` 里出现 |
| ③ 说成功但 ① 又变回 2100 | 参数回调没注册，或返回了 False | 确认 `add_on_set_parameters_callback` 有调用 |
| ① 直接报参数不存在 | yaml 最外层 key 不是 `/servo_driver` | 检查第一行是不是 `/servo_driver:` |
| ⑤ 也成功了 | 没注册回调 → 任何值都能进 | 同上一行 |

## 7. 录屏就按这个顺序演

1. 终端 A：`ros2 launch` 起来，**先指着 `串口已打开` 那行**（截图 `02_02`，真机证据；仿真会显示"打开失败…进入仿真模式"）；
2. 终端 B：① → ⑥ 一条一条敲，**④ 敲完停 3 秒**，让评委看清 `Goal was rejected`；
3. 切回 A，指着 `拒绝 goal: pwm 1700 超出限位 900~1600`（截图 `02_06`）；
4. ⑥ 恢复后再发一次，让舵机真转一下，收尾。

**不要用 `timeout` 或 Ctrl-C 去打断 goal 来演取消** —— 那条路径走不到 cancel 分支，要取消得用显式 `cancel_goal_async()` 的客户端。
