# 9. 动作 yaml 长什么样

动作全部写在 `config/actions/*.yaml` 里。换一套动作就是换一个 yaml，python 一行都不用动。

实际文件 `config/actions/stand_up.yaml`（全机动作，10 台舵机都参与）：

```yaml
# 全机动作：10 台全部参与，每步 ≤4 台，幅度 ±30（保持力矩小，供电压力低）
name: stand_up
description: 全机动作（4+3+3 分组，10 台全参与，小幅）
defaults:
  duration_ms: 1400
steps:
  - name: "第 1 步：根部 1~4 同时动"
    joints: [{id: 1, pwm: 1530}, {id: 2, pwm: 1470}, {id: 3, pwm: 1470}, {id: 4, pwm: 1530}]
  - name: "第 2 步：中段 5~7 同时动"
    joints: [{id: 5, pwm: 1530}, {id: 6, pwm: 1470}, {id: 7, pwm: 1470}]
  - name: "第 3 步：末端 8~10 同时动"
    joints: [{id: 8, pwm: 1530}, {id: 9, pwm: 1470}, {id: 10, pwm: 1530}]
  - name: "第 4 步：1~4 回中位"
    joints: [{id: 1, pwm: 1500}, {id: 2, pwm: 1500}, {id: 3, pwm: 1500}, {id: 4, pwm: 1500}]
  - name: "第 5 步：5~7 回中位"
    joints: [{id: 5, pwm: 1500}, {id: 6, pwm: 1500}, {id: 7, pwm: 1500}]
  - name: "第 6 步：8~10 回中位"
    joints: [{id: 8, pwm: 1500}, {id: 9, pwm: 1500}, {id: 10, pwm: 1500}]
```

结构就三样：`name`、`description`、`steps`。`steps` 是一个列表，每个元素是一步；一步里的 `joints` 是这一步要动的关节，同一个 `joints` 列表里的全部同时下发。`defaults` 里的 `duration_ms` 是这一步没单独写时长时用的默认值。

---

## step 怎么切

切分依据有两条，顺序不能反。

先看结构：会互相打架的关节绝不能放同一步。比如两个关节一起抬会撞在一块，那必须拆成两步，一个先抬到位另一个再动。

再看电流：实机验证过，同一步里同时动的台数越多，舵机保持力矩越大，电源越容易塌。所以每步限制在 4 台以内，10 台拆成 4 + 3 + 3。

回中位也分了三步，没有一步到位。这不是为了好看，是因为一步 10 台实测跑到第 8 秒就把 USB 设备打掉线了，后面所有 result 都收不到。

---

## 谁先动

按结构承重的顺序排：

```
根部 1~4 先撑起来（承重关节先到位）
中段 5~7 跟上
末端 8~10 最后收
```

同一个 step 里的多个关节是同时下发的，视觉上是一起动。先后关系靠拆 step 表达，不靠给某一个关节调小 duration_ms 去凑。后者看着也能用，但结构一有负载，先到的那个会被后面顶住，实际时序就不受控了。

---

## duration_ms 给多少

`1400`。这个数是试出来的：

| duration_ms | 结果 |
|---|---|
| 800 | 带结构负载走不到位。目标 1500，实际停在 1552，diff=52，被判定失败 |
| 1400 | 稳定到位，diff 都在 10 以内 |
| 再大 | 能到，但动作明显拖沓，看着像慢放 |

道理很简单：带负载的舵机比空载慢。空载给 800 够，装进结构就不够了。

---

## 怎么用 result 同步

播放器没有用 sleep 猜时间，而是拿 result 当同步信号。

同一个 step 里，所有 goal 一次性 `send_goal_async` 发出去，不等待；然后逐个取 result，等这一步的**全部** result 都回来了，才进下一个 step。

真实日志，毫秒时间戳能直接看出顺序：

```
[step 1/6] 第 1 步：根部 1~4 同时动：同时下发 4 个 goal  id=1→1530(1400ms) id=2→1470(1400ms) id=3→1470(1400ms) id=4→1530(1400ms)
  ↳ result id=1 success=True final_pwm=1522 用时=2.31s [22:07:35.888] — ok, PRAD=1522
  ↳ result id=2 success=True final_pwm=1486 用时=2.65s [22:07:36.234] — ok, PRAD=1486
  ↳ result id=3 success=True final_pwm=1473 用时=2.97s [22:07:36.551] — ok, PRAD=1473
  ↳ result id=4 success=True final_pwm=1510 用时=3.37s [22:07:36.954] — ok, PRAD=1510
[step 1/6] 全部 result 已回（3.37s），允许进入下一步
[step 2/6] 第 2 步：中段 5~7 同时动：同时下发 3 个 goal  ...
```

四个 result 的时间分别是 35.888、36.234、36.551、36.954，最后一个回来之后才打出"允许进入下一步"，下一行才开始第 2 步。

如果用 sleep 硬等，问题是舵机实际走完的时间不等于 `duration_ms`。它有负载、有电压波动、指令还要排队，每步差一点，累积下来第三遍和第一遍就对不上了。

## 连跑三遍的实测数据

同一套动作跑三遍，四台关节的 final_pwm：

| | id1 | id2 | id3 | id4 |
|---|---|---|---|---|
| 第 1 遍 | 1522 | 1486 | 1473 | 1510 |
| 第 2 遍 | 1519 | 1485 | 1474 | 1509 |
| 第 3 遍 | 1519 | 1480 | 1474 | 1509 |

最大偏差 6 个 PWM 单位。

播放器里带了一致性检查，做法是把每遍的 final_pwm 拉平成一个列表逐条比。阈值给的是 15，不是精确相等——PRAD 本身有几个单位的抖动（同一位置连读两次都可能差 1~2），用精确相等会天天报"不一致"，那个报错就没意义了。

```
一致性检查：第 2 遍与第 1 遍一致（20 条，偏差均 ≤ 15 个 PWM 单位）
```

## 换动作

另外几套：`wave.yaml`（挥手）、`home.yaml`（全体回中位）、`check_a/b/c.yaml`（分段自检，逐个关节动，用来确认哪个 ID 对应哪个关节）。

换动作就是：

```bash
ros2 run cquick_servo sequence_player --action wave
```

不用重新编译，不用改代码，不用重启驱动。
