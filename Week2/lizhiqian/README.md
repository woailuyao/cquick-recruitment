## 任务 1：命令行体验发布/订阅
<说明：谁在发布、谁在订阅，消息怎么流动的>

- **节点与话题**：自定义了消息 `BallPos`（含 `id`、`x`、`y`）。发布者节点 `pub_ball` 将数据发到 `ball_pos` 话题，订阅者节点 `sub_ball` 从该话题接收并打印。两个节点靠相同的**话题名**和**消息类型**成功通信。
- **消息流动过程**：在终端执行 `colcon build` 编译通过后，我同时运行了发布者和订阅者。通过命令 `ros2 run ball_pkg pub_ball.py` 启动发布，通过 `ros2 run ball_pkg sub_ball.py` 启动订阅。可以看到 `[ball_pub]` 持续发送 1、2、3 号球的坐标， `[ball_sub]` 持续接收打印出相同的坐标。
- **命令行验证**：使用 `ros2 interface show ball_pkg/msg/BallPos` 查看消息结构，用 `ros2 topic info /ball_pos` 查看到 Publisher 和 Subscription 均为 1。

节点（Node）：ROS2 里独立运行的程序，比如我写的 ball_pub 和 ball_sub 就是两个节点。
话题（Topic）：节点之间传输数据的“通道”，它是一个名字，比如 ball_pos。
消息（Message）：在通道里传输的“数据包格式”，比如我定义的 BallPos。
发布者（Publisher）：负责往通道里扔数据包的节点（发件人）。
订阅者（Subscriber）：负责从通道里拿数据包的节点（收件人）。
两个节点对上话的依靠是完全一致的话题名和消息类型。比如，我发布的 `ball_pos` 话题用的是 BallPos 格式的消息，订阅者也用这个来接收数据。

## 任务 2：发布者 + 订阅者节点
<说明：跑通了什么，改了什么参数、观察到什么变化>
- **跑通了什么**：编写并跑通了 `nav_ball.py` 导航节点。它同时订阅 `ball_pos` 获取目标，订阅 `/turtle1/pose` 获取乌龟实时位置，通过闭环算法控制乌龟按 1→2→3 的顺序依次走到指定坐标，误差均小于 0.5。
- **参数修改观察**：在 `pub_ball.py` 节点中，我编写了参数回调。在终端使用 `ros2 param set /ball_pub timer_period 0.1` 修改发布周期后，无需重启节点，立刻观察到订阅端打印数据的速度明显变快。
线速度（linear.x）：控制乌龟往前/往后移动的快慢。
角速度（angular.z）：控制乌龟原地转圈/转弯的快慢。
代码里通过左右轮速算出来的：轮子一起往前，就有线速度；左轮慢、右轮快，就有了角速度，乌龟就会拐弯。
为什么代码里要「先对准再走」？
如果边大步往前走、边猛打方向盘，乌龟会走出一条巨大的弧线，很容易偏出轨道或者冲过头。所以我的代码里做了一个判断：
计算当前乌龟朝向与目标的夹角 angle_err。
当角度误差很大（大于 0.12 弧度）时，先不走，原地转（linear.x = 0，只给 angular.z），把车头对准目标点。
当对准之后，再往前开（给 linear.x），并且边走边微调角度。
代码里怎么防止冲过头？
如果在目标点前一直给固定的线速度，肯定冲过 0.5 的误差圈。所以我在代码里让线速度和距离成正比（linear.x = 1.2 * dist）。离目标越近，速度越慢，到了 0.5 之内直接停车，完美停在圈里。
## 任务 3：自定义消息 + 三种通信方式
<说明：自定义消息怎么定义的；用你自己的话讲清话题/服务/动作的区别和场景>
- **自定义消息**：在包的 `msg/` 目录下新建 `BallPos.msg` 写入三个固定字段。在 `CMakeLists.txt` 中调用 `rosidl_generate_interfaces` 编译消息，并声明了脚本的安装路径。
- **三种通信方式的区别与场景**：
  - **话题 (Topic)**：多对多，单向流，只管发不管有没有人听。比如视觉持续广播球的位置。
  - **服务 (Service)**：一对一，有请求必须有响应，调用一次就结束。比如任务 2 开始前我执行 `ros2 service call /clear std_srvs/srv/Empty` 清屏。
  - **动作 (Action)**：针对长任务，有目标、有进度反馈、还能中途取消。比如“导航到坐标 (X,Y)”并随时查看进度。
