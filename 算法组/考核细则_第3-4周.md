# CQuick 战队算法组 · 招新考核细则（第 3–4 周 单目场地定位路线）

> **考核周期**：两周专项考核  
> **面向**：已完成前两周 OpenCV、HSV 图像处理与 ROS2 基础的视觉组成员  
> **考核方式**：实验室实拍数据采集 → 足球检测模型训练 → 场地标志检测 → 单目地面几何计算 → `field.yaml` 场地匹配 → 实时位姿输出 → B 站录屏 + C0 场地现场测试  
> **考核仓库**：`https://github.com/woailuyao/cquick-recruitment`  
> **考核证据形式**：以连续录屏视频为准，不以静态截图 / 图片作为演示验收材料。考核结束后必须将录屏上传 B 站，并把可访问链接提交到个人 GitHub 考核目录；GitHub 不上传录屏原文件。
>
> **本次考核最终只有两个视觉任务：**
> 1. **足球检测**：使用本人采集的实验室数据训练目标检测模型，在单目相机实时画面中识别足球并绘制检测框。
> 2. **基于场地标志匹配的单目自定位**：不检测球门，不训练 `goal_frame` / `goalpost` 类别。使用 YOLO 识别足球场上的 L/T/X 型标志及点球点，结合单目相机内参、相机安装外参和已知地面平面，计算这些标志在相机/载体坐标系中的地面位置，再与组织方统一提供的 `field.yaml` 场地坐标匹配，估计相机载体（或机器人）在场地地图中的二维位置和朝向。
>
> **预期最终输出：** 以相机光心为显示对象，输出 `x_camera_map`、`y_camera_map`（米）和 `yaw_camera_map`（度），并同时输出定位有效状态、匹配特征数量和匹配残差。若相机刚性安装在机器人上，先估计机器人底座位姿，再通过已标定的相机安装外参换算相机光心在地图中的位姿；若相机安装在独立移动测试架上，也可以直接以相机光心作为载体参考原点。
>
> **单目能力边界：** 单目相机不直接提供任意物体的深度，但在相机内外参已知、地面可近似为平面、场地标志的地图坐标已知且实际场地与地图一致时，可以利用地面几何约束估计二维米制位置和航向。本次不要求恢复完整三维环境，不要求球门检测或球门距离测量。

## C0 标准考核场地与坐标系（由组长统一指定）

本次任务二是场地自定位，测试时相机 / 机器人必须在场地内不同位置和朝向进行测试。因此，**C0 指统一的测试场地、地图原点和测试流程，不是把相机永久固定在同一个空间位置**。相机可以固定安装在机器人或移动测试架上，但相机与载体之间不得松动；测试时由评审安排至少 3 个不同的地面位置 / 朝向。

### C0 场地与地图参数（由组长确认后统一发放）

| 参数 | 统一值 / 说明 |
| --- | --- |
| 场地编号 | `C0` |
| 地图坐标系 | 采用 `field.yaml` 对应的场地坐标定义；原点、X/Y 轴方向和单位由组长在 `field_geometry.yaml` 中明确 |
| 地面平面 | 定义为地图坐标系 `Z = 0` |
| 场地特征地图 | 统一发放 `config/field.yaml`，记录 L/T/X / 点球点等特征点的已知坐标 |
| 场地几何配置 | 统一发放 `config/field_geometry.yaml`，说明场地尺寸、坐标轴、原点和地图版本 |
| 相机测试方式 | 相机固定于移动载体，测试时在不少于 3 个指定位置 / 朝向进行定位 |
| 标准图像分辨率 | `1280 × 720`（720P） |
| 标称帧率 | `30 fps` |
| 相机及镜头 | 单目 RGB 摄像头；使用固定焦距、固定对焦镜头，不限定品牌和型号 |

**坐标系必须统一：** `field.yaml` 中所有坐标使用米；地图原点、X/Y 轴正方向、角度正方向和角度单位由组长统一定义。学生不得自行平移、旋转或缩放官方地图来迎合自己的算法。若实际考核场地与官方 `field.yaml` 的几何布局不一致，组长必须先测量并发布与实际场地一致的修订版地图；不得直接把不匹配的官方地图用于实际定位验收。

**相机安装要求：** 相机固定焦距、固定对焦位置；关闭自动对焦和自动变焦功能（设备支持时）。相机与机器人底座 / 移动测试架之间必须保持刚性连接。相机若在测试过程中相对载体发生移动，必须重新标定相机外参。

**测试参考位姿：** 组长至少设置 3 个不同的测试点，并记录载体参考位置和朝向（可使用地面标记、卷尺测量和角度量具建立参考）。这些参考数据只用于定位误差验收，不作为学生算法的实时输入。

## 一、本次考核目标

前两周已经完成 OpenCV 基础图像处理、HSV 颜色分割、目标像素中心提取和 ROS2 话题通信。本次两周专项考核聚焦足球机器人视觉系统中的两个能力：**足球目标检测**与**基于场地已知标志的单目二维自定位**。

任务二参考 Booster K1 公开 RoboCup Demo 的整体处理思路：视觉模块先检测 L/T/X 等场地标志，并结合相机几何参数估计标志相对于机器人 / 相机载体的位置；定位模块再把这些观测特征与场地中的已知特征位置进行匹配，求解载体在场地坐标系中的二维位姿。考核要求完成这一核心链路的单目简化实现，不要求复制 K1 的全部行为树、比赛策略、运动控制或 GameController。

## 二、统一硬件与软件要求

### 2.1 相机要求（不限定品牌和型号）

本次使用单目 RGB 摄像头作为统一视觉输入。**不指定摄像头品牌、具体型号或供应商**，但所有成员必须在数据采集、相机标定、模型测试和最终现场考核中使用同一台摄像头，避免更换设备后直接沿用不匹配的标定参数。

| 项目 | 统一要求 |
| --- | --- |
| 摄像头类型 | 单目 RGB 摄像头，不限定品牌和型号 |
| 镜头 | 固定焦距、固定对焦；考核期间不得改变焦距或对焦位置 |
| 图像分辨率 | 统一使用 `1280 × 720`；如现场设备不支持，由组长统一发布替代分辨率 |
| 帧率 | 目标 `30 fps`，记录实际采集帧率 |
| 接口 | USB/UVC 或实验室现有可稳定接入 Linux 的接口 |
| 图像格式 | RGB 或 BGR 图像流，程序内需明确颜色通道顺序 |

**设备使用约定：**

1. 不限定摄像头品牌和型号，但必须使用真实单目 RGB 视频流完成数据采集和实时验收，不得以静态图片或预录视频冒充实时输入。
2. 每个人必须在 README 中记录摄像头接口、设备节点（如 `/dev/video0`）、分辨率、实际帧率、镜头焦距（已知时）及对焦 / 变焦设置；不要求记录或提交摄像头品牌、具体型号。

4. 标称视场角或“低畸变镜头”不能直接替代标定结果；实际成像会受镜头装配、对焦位置和分辨率等因素影响。
5. 最终 C0 现场测试应使用完成数据采集和标定的同一台摄像头、同一镜头和统一分辨率，不得临时更换设备。

## 三、考核任务清单

### 任务 1：足球检测（50 分）

**要做什么**：使用本人通过单目 RGB 摄像头采集的数据，制作足球检测数据集，训练目标检测模型，并将模型接入实时相机视频流，实现足球检测框、置信度和像素位置的连续输出。

#### 1.1 数据采集要求

以下要求全部为必做项：

- 数据必须来自本实验室实际场地；
- 必须由本人使用同一台单目 RGB 摄像头亲自拍摄；
- 至少采集多段独立视频，并从视频中抽帧整理为数据集；
- 原始采集视频必须由本人妥善保存，以便评审抽查；从视频中抽取的帧用于标注和训练，但不要求将整套图片或原始视频上传 GitHub；
- 数据采集时记录摄像头接口、设备节点、分辨率、实际帧率和拍摄日期；
- 不得使用网上下载的视频 / 图片、他人拍摄数据、手机视频或其他相机数据替代本次实拍训练集 / 测试集。

允许使用官方预训练权重（例如 `yolov8n.pt`）作为迁移学习初始化，但不允许用公开图片或他人训练好的最终权重代替自己的实验室实拍数据与训练过程。

#### 1.2 统一类别与标注规范

本任务只训练一个类别，类别编号固定：

| `class_id` | 类别名 | 标注对象 | 标注要求 |
| ---: | --- | --- | --- |
| 0 | `ball` | 足球 | 尽量框住足球可见区域；部分遮挡时按可见区域标注；不得把大面积地面或其他物体框入 |

类别名称必须为 `ball`，不得自行增加 `robot`、`goal_frame` 等类别，也不得调整编号。

#### 1.3 数据量与场景覆盖

至少准备 **200 张有效标注图片**，来自不少于 **5 段独立采集的视频片段**。建议至少包含 200 个有效足球标注实例。同一段视频连续抽取的高度相似帧不能被当作大量独立样本。

建议覆盖：

- 足球处于画面左 / 中 / 右、近 / 中 / 远等不同位置；
- 足球静止、滚动和运动模糊；
- 足球被机器人、其他物体或场地边缘部分遮挡；
- 不同背景、阴影和实验室正常光照变化；
- 足球较小、靠近画面边缘或与白色场地线靠近等困难情况。

#### 1.4 YOLO 数据格式与目录

可使用 LabelImg、CVAT、Roboflow 等工具标注，最终导出 YOLO 检测格式。每个目标一行：

```text
class_id x_center y_center width height
```

中心点、宽度和高度均为相对于图像尺寸归一化后的数值，范围为 0～1。

目录建议：

```text
soccer_dataset/
├── images/
│   ├── train/
│   ├── val/
│   └── test/
├── labels/
│   ├── train/
│   ├── val/
│   └── test/
└── data.yaml
```

`data.yaml` 至少要包含训练、验证、测试图片路径，类别数量 `nc: 1`，类别名称为 `ball`。

数据集按**独立视频片段 / 独立采集轮次**划分，建议 train / val / test 按约 70% / 20% / 10% 分配。不能先把一段视频的相邻帧随机打散到三个集合，否则评估结果可能虚高。

#### 1.5 标注质量检查

训练前至少随机抽查 30 张图像，将标签框画回原图。检查：

- 有没有漏标、错标或类别编号错误；
- 框是否覆盖足球可见区域；
- 框是否过大，把大面积背景也框进去；
- 标签坐标是否越界，宽高是否大于 0；
- train / val / test 是否存在相邻视频帧泄漏。

#### 1.6 模型训练与评估

建议统一使用轻量模型 **YOLOv8n** 作为训练基线，也允许使用其他 YOLO 轻量版本，但必须说明选择原因：

```text
yolov8n.pt
```

训练基线参数如下：

| 参数 | 基线要求 | 说明 |
| --- | --- | --- |
| `model` | `yolov8n.pt` | 预训练模型 |
| `imgsz` | `640` | 输入尺寸 |
| `epochs` | `50` | 训练轮数 |
| `data` | 自己的 `data.yaml` | 实验室实拍数据集配置 |
| `device` | `0` 或 `cpu` | 按实际设备选择 |

训练命令参考：

```bash
yolo detect train model=yolov8n.pt data=./soccer_dataset/data.yaml epochs=50 imgsz=640
```

允许根据显存、训练时间调整 batch、图像尺寸等参数，但必须在 README 中记录修改内容和原因。训练完成后保存最佳权重 `best.pt`，并在独立测试集上评估。至少记录：

| 指标 | 含义 | 重点观察 |
| --- | --- | --- |
| Precision | 检测为足球的结果中有多少是真的 | 白色场地线、其他圆形物体是否被误检 |
| Recall | 真实足球中有多少被检测出来 | 远处小足球、运动模糊和遮挡是否漏检 |
| mAP50 | IoU=0.5 时的平均精度 | 足球整体检测能力 |
| mAP50-95 | 多个 IoU 阈值下的平均精度 | 检测框定位质量 |

必须检查验证曲线和预测可视化，至少分析一个误检案例和一个漏检案例。

#### 1.7 实时检测与输出

将 `best.pt` 加载到实时相机画面，至少输出：

- 类别名称：`ball`；
- 置信度 `confidence`；
- 检测框 `x1, y1, x2, y2`；
- 检测框中心像素坐标 `center_u, center_v`；
- 当前帧编号或时间戳；
- 实时 FPS 或平均推理耗时。

足球检测框中心计算：

\[
u = \frac{x_1+x_2}{2},\qquad v = \frac{y_1+y_2}{2}
\]

**注意：** 本次只要求输出足球在图像中的像素位置，不要求通过单目相机计算足球距离或地面坐标。检测框中心也不代表足球真实三维球心位置。

### 任务 2：基于 `field.yaml` 的单目场地自定位（50 分）

**要做什么**：使用同一台单目相机识别足球场内的 L/T/X 型场地标志及点球点，根据相机标定参数将这些图像特征转换为载体坐标系中的地面位置，再与组织方提供的 `field.yaml` 已知场地坐标进行匹配，实时估计相机载体 / 机器人在场地地图坐标系中的二维位置和朝向。

**本任务不检测球门。** 不训练 `goal_frame`、`goalpost` 或机器人检测类别；不通过场地线消失点推断球门方向。核心结果是场地地图中的二维定位；界面最终以相机光心为标记，输出 `x_camera_map`、`y_camera_map`、`yaw_camera_map`。

#### 2.1 输入、输出与坐标定义

**输入：**

- 单目相机实时 RGB 视频；
- 相机内参矩阵和畸变系数；
- 相机相对于机器人底座 / 移动测试架的固定外参，或相机相对于地面参考系的安装参数；
- 统一提供的 `field.yaml` 和 `field_geometry.yaml`；
- 约定地面平面 `Z = 0`。

**主要输出：**

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `x_carrier_map` | 机器人底座 / 移动测试架参考原点在场地地图中的 X 坐标 | m |
| `y_carrier_map` | 机器人底座 / 移动测试架参考原点在场地地图中的 Y 坐标 | m |
| `yaw_carrier_map` | 载体朝向相对于地图 X 轴的角度 | ° |
| `x_camera_map` | 相机光心在场地地图中的 X 坐标，由载体位姿和相机外参换算 | m |
| `y_camera_map` | 相机光心在场地地图中的 Y 坐标，由载体位姿和相机外参换算 | m |
| `yaw_camera_map` | 相机水平朝向相对于地图 X 轴的角度 | ° |
| `valid` | 当前定位结果是否可信 | bool |
| `marker_count` | 本次参与匹配的有效场地特征数量 | 个 |
| `residual` | 观测特征与地图匹配后的误差指标 | m 或算法定义的无量纲分数 |
| `status` | 定位状态，例如 `ok`、`insufficient_markers`、`ambiguous`、`high_residual`、`lost` | string |

**本考核统一地图坐标约定：** 地图 `+X` 轴向右、`+Y` 轴向上；`Yaw` 从地图 `+X` 轴逆时针为正。因此示例 `yaw_camera_map = 35.2°` 时，俯视地图中的相机朝向箭头应指向右上方约 35.2°。实际地图原点、轴向和单位由组织方在 `field_geometry.yaml` 中统一定义，所有成员必须遵循同一约定。

地图匹配首先求解载体参考原点位姿 `x_carrier_map/y_carrier_map/yaw_carrier_map`。如果相机刚性安装在机器人上，再使用固定外参换算 `x_camera_map/y_camera_map/yaw_camera_map`；若相机安装在独立移动测试架上，也可以把相机光心定义为载体参考原点，此时两组位姿一致。

**最终是否输出相机实际坐标？** 是，输出的是相对于本次场地地图坐标系的米制二维位姿（X、Y、Yaw），不是 GPS 全球坐标。相机光心的 X/Y 可由载体地图位姿和相机安装外参换算；相机高度 Z、俯仰 Pitch、滚转 Roll 属于安装标定参数，本次不要求通过场地特征单独求解全部 6DoF 三维位姿。

#### 2.2 统一场地地图文件（组织方提供）

所有成员必须使用同一版本的场地标志坐标文件，禁止自行修改地图特征坐标以迎合算法结果。

组织方提供：

```text
config/
├── field.yaml              # 场地标志点坐标：L/T/X/点球点等
├── field_geometry.yaml     # 场地尺寸、地图原点、坐标轴、单位、地图版本
├── camera_intrinsics.yaml  # 相机内参与畸变系数（可由学生标定后提交）
└── camera_extrinsics.yaml  # 相机相对于载体 / 地面参考系的安装外参
```

官方参考文件：

- Booster 官方 `field.yaml`：https://raw.githubusercontent.com/BoosterRobotics/robocup_demo/main/src/vision/config/field.yaml
- Booster 官方 `vision.yaml`：https://github.com/BoosterRobotics/robocup_demo/blob/main/src/vision/config/vision.yaml
- Booster 官方 `locator.cpp`：https://github.com/BoosterRobotics/robocup_demo/blob/main/src/brain/src/locator.cpp

`field.yaml` 保存的是场地特征点坐标，不是球场照片，也不是 ROS 导航栅格地图。官方文件中的点球点键名写作 `PenalityPoint`（官方拼写），模型类别可统一为 `PenaltyPoint`，解析时必须显式做别名映射。该文件本身未必包含完整场地尺寸、球门尺寸、所有线条和地图坐标系定义，因此组织方必须配套发布 `field_geometry.yaml`。正式考核前，组长必须核实官方坐标与 C0 实际场地的特征位置和尺度一致；如果不同，必须由组长统一测量并发布实际场地版本，所有学生使用同一版本。

**关于 K1 实现的范围说明：** 官方公开 `vision.yaml` 通过 `field_marker_path` 引用 `field.yaml`；公开 `locator.cpp` 中的定位器还会根据 `FieldDimensions` 构造 L/T/X/P 等地图特征，并利用观测标志的位置进行位姿搜索。本考核要求学生完成相同类型的“观测特征 → 地图特征匹配 → 二维位姿”流程，但允许使用 Python / OpenCV / NumPy 实现，不要求逐行移植 Booster 的 C++ 代码。

#### 2.3 统一类别与 YOLO 标注规范

本任务只检测用于场地定位的标志类别，不检测球门和机器人。建议类别与 K1 公开模型命名保持一致：

| `class_id` | 类别名 | 标注对象 | 特征点定义 |
| ---: | --- | --- | --- |
| 0 | `LCross` | L 型场地交点 / 角点标志 | 标注框内需能定位 L 形两条线的交会顶点 |
| 1 | `TCross` | T 型场地交点标志 | 以 T 形横线与竖线的交点为几何中心 |
| 2 | `XCross` | X 型场地交点标志 | 以两条线交会中心为几何中心 |
| 3 | `PenaltyPoint` | 点球点 | 以点球标记中心为几何中心 |

不同场地可能没有上述所有类别。组织方应在发放地图前确认现场实际存在且可观测的标志类别；现场没有的类别不得强行要求训练或评分。训练集至少覆盖实际场地中存在的类别。

检测框中心不一定等于精确几何交点。学生必须在 YOLO 检测后，对标志框内图像做几何细化（例如线段拟合、角点 / 交点计算或局部模板几何），输出真实的 `landmark_pixel=(u,v)`，并说明每类标志取点规则。只把 bbox 中心不加说明地当作所有 L/T/X 的精确地面点，将影响定位精度。

#### 2.4 场地标志数据采集与模型训练

- 必须使用本人用于本次考核的同一台单目摄像头在 C0 实际场地采集数据；
- 至少采集 5 段独立视频，覆盖不同距离、方向、尺度、光照和部分遮挡；
- 建议至少 300 张有效标注图片；数据量可根据场地标志数量调整，但必须覆盖实际地图中主要可见的标志类型；
- 同一段视频的连续相邻帧不得大量随机分散到 train / val / test，数据集应按独立视频片段划分；
- 允许使用 YOLO 预训练权重初始化，但必须基于本人现场数据进行训练和评估；
- 如果某种标志在 C0 场地中很少出现，可由组长组织多角度采集，不得使用与实际标志外观不一致的网络图片代替现场数据。

建议模型：`yolov8n.pt` 或其他轻量 YOLO 检测模型。训练参数可沿用任务 1 的基线设置，根据实际数据量和硬件调整，并在 README 中记录模型、训练轮数、图像尺寸、设备和测试指标。

场地标志检测必须单独报告各类别的 Precision、Recall、mAP50，并展示不同尺寸和遮挡情况下的检测表现。模型输出应包括类别、置信度和 bbox；几何细化模块还需输出每个标志的像素特征点。

#### 2.5 相机内参与畸变标定（必须完成）

使用棋盘格或 ChArUco 标定板完成实际相机内参标定，建议至少采集 15 张有效标定图像，覆盖画面中心、四角、不同倾斜角度和距离。标定分辨率必须与最终推理分辨率一致（`1280 × 720`）。

核心参数：

| 参数 | 含义 | 用途 |
| --- | --- | --- |
| `fx`、`fy` | 水平 / 垂直焦距（像素单位） | 像素坐标反投影 |
| `cx`、`cy` | 主点坐标 | 确定相机光轴 |
| `k1`、`k2`、`k3` | 径向畸变系数 | 镜头畸变修正 |
| `p1`、`p2` | 切向畸变系数 | 镜头畸变修正 |

K 矩阵：

\[
K=\begin{bmatrix}f_x&0&c_x\\0&f_y&c_y\\0&0&1\end{bmatrix}
\]

畸变系数按 OpenCV 常用顺序保存：`[k1, k2, p1, p2, k3]`。必须保存 `camera_matrix`、`dist_coeffs`、图像宽高和重投影误差。运行时改变分辨率、裁剪或缩放方式，必须同步调整内参或重新标定。

#### 2.6 相机外参与地面平面（必须完成）

单目图像本身没有直接的深度值。要将地面标志像素转换成米制地面坐标，必须增加几何约束：

- 地面近似为一个平面，定义为 `Z=0`；
- 相机相对于机器人底座 / 移动测试架的平移和旋转必须已知；
- 相机光心离地高度、俯仰角和滚转角必须纳入外参；
- 相机与载体刚性固定，外参在测试期间不能变化。

若相机固定在机器人头部且头部会运动，还需要实时头部关节角或姿态信息；若相机固定在机器人身体 / 移动测试架上，且安装姿态不变，则一次标定后可复用固定外参。对于本次简化考核，优先采用固定安装，不要求实现动态头部运动补偿。

建议保存 `camera_extrinsics.yaml`，至少说明相机坐标到载体坐标的旋转矩阵 / 平移向量、相机光心高度、安装俯仰角 / 滚转角、标定方法和单位。不得把相机标称高度或手工估计角度伪装成精确标定值。

#### 2.7 像素点到地面坐标的几何计算

对每个经过几何细化的标志像素点 `p=(u,v)`，先去畸变，再使用相机内参得到相机坐标系中的射线方向：

\[
\mathbf d_c=K^{-1}\begin{bmatrix}u\\v\\1\end{bmatrix}
\]

使用相机到载体坐标系的外参，将射线原点和方向转换到载体坐标系。设相机中心为 `O_b`，射线方向为 `d_b`，地面平面为 `Z=0`，则交点为：

\[
P_b=O_b+\lambda d_b,\qquad \lambda=-\frac{O_{b,z}}{d_{b,z}}
\]

当 `d_b,z` 接近 0、射线朝向地平线上方、交点落在合理场地范围之外或输入像素不可靠时，应将该观测标记为无效，不能产生 NaN / 无限距离或伪造地面点。

最终每个视觉标志应形成类似数据：

```python
observed_markers = [
    {"type": "T", "x": 2.15, "y": 0.43, "confidence": 0.92},
    {"type": "L", "x": 3.20, "y": -0.62, "confidence": 0.87},
    {"type": "X", "x": 4.10, "y": 0.15, "confidence": 0.90},
]
```

以上数值仅为数据结构示例，不是标准答案。`x/y` 表示特征点相对于载体参考坐标系的地面坐标，单位为米。

#### 2.8 与 field.yaml 匹配并估计地图位姿

`field.yaml` 中每个已知特征包含类别和场地地图坐标。算法需要根据观测标志的类别、相对位置关系和候选载体位姿，匹配地图中的同类特征，并求解载体在地图中的二维位姿：

\[
Pose_{carrier}^{map}=(x_{carrier}^{map},y_{carrier}^{map},\theta_{carrier}^{map})
\]

对一组候选位姿，观测点从载体坐标系转换到地图坐标系：

\[
P_{map,i}=R(\theta_{map})P_{b,i}+t_{map}
\]

其中 `R` 为二维旋转矩阵，`t=[x_carrier_map,y_carrier_map]^T` 为载体参考原点在地图中的平移向量。算法通过多组标志的匹配残差评价候选位姿，寻找使观测特征与地图特征整体最吻合的位姿。

可以采用以下一种或组合方式实现：

- RANSAC / 几何一致性匹配后进行最小二乘位姿优化；
- 对候选地图特征组合进行 SE(2) 位姿搜索；
- 参考 K1 Locator 的候选位姿 / 粒子采样、残差评估和迭代收敛思路；
- 在连续帧中使用上一帧位姿作为搜索范围先验，并在重新定位时扩大搜索范围。

**不能只按类别把每个检测框随便匹配到最近的同类点。** 场地内可能存在多个 L/T/X 标志，且球场通常具有对称结构。必须处理同类标志的身份歧义、多个候选匹配和错误匹配；应至少使用多个空间分布合理的标志，并检查整体残差。仅有一个标志通常不足以唯一确定二维位置和朝向。

当地图特征不足、同类点匹配存在多解、候选位姿残差过大或搜索未收敛时，输出 `valid=false`，并给出 `insufficient_markers`、`ambiguous`、`high_residual` 或 `not_converged` 等状态。不得为了画面连续而持续显示未经当前帧验证的旧位姿。

#### 2.9 相机位姿与机器人位姿换算

定位模块首先输出所定义载体参考原点的地图位姿。若参考原点定义为机器人 `base_link`，则输出机器人在地图中的 `(x,y,yaw)`。通过已标定的固定外参 `T_base_camera`，可进一步换算相机光心的地图位姿：

\[
T_{map,camera}=T_{map,base}\,T_{base,camera}
\]

若载体参考原点直接定义为相机光心，则定位结果就是相机在地图中的二维位姿。建议同时记录 `carrier_pose_map` 和换算后的 `camera_pose_map`（当外参可用时）。README 必须明确输出究竟属于 `camera_frame`、`base_link` 还是测试架坐标系，不允许把机器人位置误标成相机光心位置。

本次主要考核二维地面位姿：载体位姿 `x_carrier_map/y_carrier_map/yaw_carrier_map`，以及换算后的相机光心位姿 `x_camera_map/y_camera_map/yaw_camera_map`。可以额外输出相机离地高度 `z_camera`、固定俯仰角 / 滚转角，但这些来自安装标定，不代表算法已通过单目场地标志恢复完整三维姿态。

#### 2.10 连续帧稳定与实时输出

至少实现：

- 对相机实时图像进行检测、几何细化和地面投影；
- 对场地地图进行加载，并在启动时检查地图文件、单位、场地尺寸和坐标轴配置；
- 输出当前帧有效标志数量、匹配结果、地图位姿和匹配残差；
- 对连续位姿进行合理滤波或与上一帧结果融合；
- 定位丢失、标志不足或匹配歧义时及时置 `valid=false`；
- 记录实时 FPS、定位更新频率、算法处理耗时和定位有效率。

允许使用滑动平均、指数滤波、卡尔曼滤波等方式稳定输出，但必须避免在定位失败时无限沿用上一帧位姿。建议同时显示原始估计位姿和滤波后位姿，便于检查滤波是否引入延迟。

## 七、常见问题（FAQ）

**Q1：相机是 UVC 免驱，为什么还要查 `/dev/videoX`？**  
A：免驱表示 Linux 通常可通过通用 UVC 驱动识别设备，不代表设备节点固定。每次插拔后都应检查 `v4l2-ctl --list-devices`，确认实际相机节点。

**Q2：固定焦距镜头为什么还要做内参标定？**  
A：固定焦距只表示拍摄过程中焦距不变化，不代表 `fx / fy / cx / cy` 已知。镜头标称焦距和视场角不能替代实际相机标定结果。

**Q3：只有单目相机，能不能输出地图中的米制 X/Y？**  
A：可以，但不是仅凭 RGB 像素就能得到。必须已知相机内参、相机相对于载体 / 地面的外参，并假设被检测场地标志位于已知地面平面；再将标志像素反投影并与有米制尺度的 `field.yaml` 地图匹配，才能估计二维米制位置和朝向。

**Q4：field.yaml 是一张足球场图片吗？**  
A：不是。它是场地标志的坐标配置文件，记录 L/T/X、点球点等特征在场地坐标系中的位置。它不是 RGB 图片，也不是 Nav2 的 PGM 栅格地图。组织方还会提供场地尺寸、坐标原点和坐标轴说明。

**Q5：直接下载 Booster 官方 field.yaml 就一定能用吗？**  
A：不一定。只有当实际考核场地的标志类别、布局、尺寸、坐标原点和轴方向与该文件一致时才能直接使用。组长必须先核对实际场地；如不一致，应统一测量并发布与实际场地一致的版本，所有成员使用同一份地图。

**Q6：是不是每一帧都直接把 RGB 图像和 field.yaml 比较？**  
A：不是。流程是先检测 L/T/X 等场地标志，提取其图像几何点，再用相机参数计算标志相对于载体的地面坐标，最后把这些观测坐标与地图中特征坐标匹配，求解载体位姿。

**Q7：最终输出的是相机坐标还是机器人坐标？**  
A：取决于你定义的载体参考坐标系。如果相机安装在机器人上，先输出 `base_link` 在地图中的 X/Y/Yaw；再用相机到 `base_link` 的固定外参换算相机光心在地图中的位置。如果相机装在移动测试架上，则输出测试架 / 相机参考原点的地图位姿。README 必须明确坐标系定义。

**Q8：只有一个 L/T/X 标志能定位吗？**  
A：通常不能唯一确定完整二维位置和朝向。多个同类标志在地图中也可能重复出现，必须结合多个分布合理的标志、相互几何关系和候选位姿残差进行匹配；有歧义时输出 `valid=false`。

**Q9：是否必须实现 K1 的全部 C++ 代码？**  
A：不需要。本次考核学习 K1 的关键处理链路：场地标志检测、单目几何投影、地图特征匹配和二维位姿估计。允许使用 Python、OpenCV、NumPy、ROS2 实现，不要求复现完整比赛策略和机器人控制。

**Q10：本次还需要检测球门框吗？**  
A：不需要。本次没有 `goal_frame` 或 `goalpost` 检测任务，不要求画球门框检测框，也不输出球门方向或距离。任务二只使用场地标志完成地图匹配与自定位。

**Q11：没有深度摄像头，是否无法定位？**  
A：不是。若场地标志位于已知平面，并且相机内外参已标定，可以使用单目射线与地面平面求交得到米制地面位置。单目不能直接恢复任意三维物体的深度；本次利用的是已知地面平面和地图尺度约束。

**Q12：为什么 B 站录屏，而不是把视频 / 截图放进 GitHub？**  
A：考核以连续视频作为演示和过程证据。录屏上传 B 站，GitHub README 只提交可访问链接、文字指标和必要配置，不上传录屏原文件、原始视频或大量抽帧图片，避免仓库体积过大。

**Q13：现场定位不出来，可以播放自己提前录好的视频吗？**  
A：不可以。C0 现场考核必须使用发放相机实时输入，并在多个测试点完成定位。B 站录屏不能替代现场实时测试。

## 八、评审与答疑

- **评审人**：视觉组组长或指定成员。
- **评审方式**：检查 GitHub PR 与 README；查看 B 站连续录屏；抽查本人实拍视频与数据集统计；复跑足球实时检测；检查场地标志检测、相机内外参和地面投影；在 C0 的多个测试位置核验 `field.yaml` 匹配、地图 X/Y/Yaw 与定位有效状态。
- **结果反馈**：通过 / 需补交 / 未通过，在群里统一公布或在 PR 留言反馈。
- **答疑**：优先查 OpenCV、Ultralytics、ROS2、Linux V4L2 与 Booster 官方资料；提问必须附摄像头接口、分辨率、运行命令、环境版本、完整报错和必要的录屏片段 / 日志。
