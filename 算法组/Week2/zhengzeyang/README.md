## 链路

输入：四张手机拍摄的篮球场照片（1248×1515、1222×1652、1256×1403、763×635）

处理：`cvtColor(BGR→HSV)` → `inRange` 二值化 → 9×9 闭运算 → `findContours` → 面积与宽高比筛选 → 取面积最大 → 轮廓矩求质心

输出：像素坐标 `(u, v)`、轮廓面积、标注图（`images/out_*.jpg`）

交给下一环节：封装为 `TargetPosition` 消息，由 `detector_node` 以 1 Hz 发布到 `/target_position`，`listener_node` 订阅并打印

| 项 | 值 |

## 任务 2：可视化与参数对比

标注内容：绿色轮廓线 + 红色质心圆点 + `u=xx v=xx` 文字；未检测到时在左上角写 `NO TARGET`。结果图见 `02_结果可视化.png`（image3，红点落在球面正中）。

### 对比 A：最小面积

同一张 image1，仅改 `min_area`：

| min_area | 结果 | area |
|---:|---|---:|
| 1500 | 检测到 | 5591 |
| 8000 | 未检测到 | — |

image1 中通过宽高比筛选的候选只有 5591 一个，门槛提到 8000 后它也被挡掉。**提高面积门槛能消除误检，代价是漏掉真实的小目标**。

### 对比 B：HSV 饱和度下界

同一张 image3，仅改 `S` 下界：

| 阈值 | mask 像素数 | 球的候选面积 | 现象 |
|---|---:|---:|---|
| S ≥ 90 | 346432 | 198573 | 正确框住整球 |
| S ≥ 150 | 110527 | 25019 | 球被切碎，只框到局部 |
| S ≥ 190 | 12761 | 12255 | 完全丢失 |

结论：**篮球的饱和度落在 90~150 之间，与场内红棕色区域重叠**。把 S 下界提到 150 以上，球会先被打碎再消失，说明纯颜色阈值无法在保住球的同时排除干扰。

### 失败分析

只有 image3 的检测点落在球上。其余三张的具体情况：

| 图片 | 失败类型 | 实际情况 |
|---|---|---|
| image1 | 定位偏差 | 球悬在篮网下方且背光，球面只有高光部分饱和度够高，mask 只覆盖球体左上的一小片（5591 像素），质心因此偏到球的左上缘，而不是球心 |
| image2 | 误检 | 广角逆光，球在画面底部，直径约 30 像素（约 700 像素面积），低于最小面积 1500；被选中的 3426 像素是**橙色篮筐**，不是球 |
| image4 | 漏检 | 球距离远、占比小，未越过面积门槛，整帧输出 `detected=False` |

核心问题有三个：

1. **目标尺度跨度太大**。image3 的球占画面 11%，image2 的球不足 0.04%，一套固定的绝对面积阈值无法同时覆盖
2. **逆光下饱和度塌陷**。image1、image2 都是低角度逆光，球面偏暗，S 值掉到阈值下界附近
3. **单帧无先验**。「面积最大的合格候选」在没有形状或运动约束时，容易被篮筐、地面对比色抢走

尝试过的改进：加入填充率（轮廓面积 / 外接矩形面积，正圆约 0.785）与圆形度（4πA/P²）筛选。地板与篮筐类误检被抑制，但远距离小目标会一并漏检，且 image1、image2 的球无法进入颜色掩膜，故最终版本未启用，仅保留为分析记录。

### 坐标说明

图像原点在左上角，`u` 向右增大、`v` 向下增大，单位是像素。像素坐标只表示目标在图像中的位置，**不是机器人世界坐标，也不是米制距离**；要转换为场地坐标需要相机内参标定与单应变换，本周不做。

## 任务 3：ROS 2 通信

| 项 | 内容 |
|---|---|
| 接口包 | `target_interfaces`，消息 `TargetPosition` |
| 消息字段 | `bool detected` / `float32 u` / `float32 v` / `float32 area` |
| 发布节点 | `detector_node`，`create_timer` 驱动，默认 1 Hz |
| 订阅节点 | `listener_node`，订阅 `/target_position`，打印序号与四字段 |
| 话题 | `/target_position`，队列深度 10 |

`detector_node` 从 `image_dir` 读取图片并按顺序轮播，逐帧调用 `detect_target`，把结果装配成消息发布；未检测到目标时仍然发布 `detected=False`，避免下游把「没有消息」误判为「链路断开」。`listener_node` 每收到一条就打印累计编号，用于确认消息连续到达。

### 运行参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `image_dir` | `~/vision_ws/week2/images` | 图片目录，按文件名顺序轮播 |
| `image_path` | 空 | 非空时锁定该张图片，留空则轮播 |
| `rate` | 1.0 | 发布频率（Hz），修改后需重启节点 |

### 验证

- `ros2 interface show target_interfaces/msg/TargetPosition` 输出四个字段（见 `03_interface_show.png`）
- 发布端文件名循环、数值逐帧变化；接收端编号连续递增，与发布端同一时刻数值一致（见 `03.png`、`03_pub_sub分屏.png`）
- `ros2 topic hz /target_position` 显示约 `1.000`
- `ros2 param set /detector_node image_path <某张图>` 后两端数值同步切换，证明参数在运行时生效

### 设计说明

`detect_target` 位于 `detector_core.py`，**不含任何 `rclpy` 依赖**，可脱离 ROS 2 用 `python3` 直接调试（`detect_offline.py` 即为此用途）。节点只负责取图、装消息、发布三项职责。

两个节点之间没有任何代码引用，唯一联系是 `TargetPosition` 这一份接口定义与 `/target_position` 这个话题名。视觉算法改动时，订阅端无需重新编译——这是选择话题通信而非直接函数调用的原因。

## 问题与解决过程

1. **多行代码粘贴到终端后缩进丢失**，脚本报 `IndentationError`。改用编辑器写文件，终端只用于执行。
2. **从网页复制的代码中 `__main__` 被插入零宽字符**，`if` 条件恒为假，脚本静默不执行且不报错。改为脚本末尾直接调用 `main()`；节点文件不加模块级调用，避免 `ros2 run` 重复执行。
3. **`ros2 interface show` 找不到消息类型**：改了 `.msg` 后未重新 `colcon build` 且未重新 `source install/setup.bash`。
4. **新终端报 `Package 'target_detector' not found`**：工作空间的 `install/setup.bash` 不会自动加载，每个新终端都要 source。
5. **检测结果每秒完全相同**：节点每拍读取同一张静态图。改为按目录轮播后数值随帧变化，才能证明是逐帧重新检测。
