# 学习记录 · liyutong

第 2 周的任务是把"读一张图"变成"持续找目标并把位置发出去"。我做下来分成三块：装环境、写颜色检测、接 ROS2。花时间最多的不是写代码，是环境。

## 装环境这一步比想象中难

第一周 OpenCV 已经能用了，但 ROS2 一直没装。我选了 WSL2 加 Ubuntu 22.04。

`wsl --install -d Ubuntu-22.04` 直接失败，报 `WININET_E_CONNECTION_RESET`，提示去 github 拉发行版列表拉不到。我一开始以为是网络断了，重试几次都一样。后来改成去微软官网找 Ubuntu 22.04 的离线安装包，下下来先核对了文件大小和 MD5，确认和服务端给的 `Content-MD5` 一致再安装。

装完之后点开又报错，`WslRegisterDistribution failed with error: 0x80071772`，系统提示是"指定的文件已加密，用户没有能力解密"。这个错误我查了挺久没找到确切原因，也没搞明白到底是什么文件被加密了。最后换了条路：从同一个官方安装包里把 `install.tar.gz` 解出来，用 `wsl --import` 直接导入，指定版本 2，一次就成功了。

中间还有个小插曲。`passwd` 设置密码时，我输了两遍屏幕上一个字符都不显示，以为键盘没接上，反复试了好几次。后来才知道 Linux 输密码本来就不回显，敲完回车就行。这个现在想想有点好笑，但当时确实卡住了。

装完 ROS2 之后我又踩了一个坑：Windows 上的 Python 和 Ubuntu 里的 Python 不是一套。我一开始在 Windows 里 `import cv2` 是好的，就以为 ROS2 节点也能直接用，其实节点跑在 Ubuntu 的 Python 3.10 上，OpenCV 要单独用 apt 装。后来养成习惯，先在 Ubuntu 里跑一遍 `python3 -c "import cv2, numpy, rclpy"` 确认能导入，再动代码。

## 颜色检测：从 RGB 换到 HSV

最开始我想直接卡 RGB 三个通道的范围，结果很糟。橘子亮的地方三个通道都很高，暗的地方整体数值往下掉，同一颗橘子在不同光照下 RGB 差得太多，阈值根本顾不过来。

换成 HSV 之后清楚很多。H 管是什么颜色，S 管饱和度，V 管亮度，调的时候可以只动一个维度，不会牵一发动全身。这里有个细节我一开始没注意：OpenCV 读 8 位图的时候 H 只有 0 到 179，不是 0 到 360，我按 0 到 360 设过一次阈值，结果怎么调都没有白色区域。

调参的时候我发现光看最后的标注图不够，得看 mask。有时候图上看着框住了，mask 里其实一大片都是白的，只是因为面积最大的是橘子所以碰巧选对了。看 mask 才知道颜色范围到底是宽了还是窄了。

中心点是用轮廓矩算的，`u = m10/m00`，`v = m01/m00`。这个公式我推不太动，但能理解意思：把轮廓上所有点按位置加权平均。写的时候差点漏掉一种情况，就是 `m00` 可能是 0，比如轮廓退化成一条线的时候，那就除不了，得跳过。这个是看别的代码才想起来的，自己写第一版时只想着正常情况。

多目标的时候我选面积最大的那个。当时想的是橘子一般比噪点大，实际跑下来也确实是这样，但如果背景里有更大的同色物体就会选错，后面就遇到了。

## 用真实照片试出来的问题

我先用默认范围跑，四张有目标的图都检测到了，看着挺顺利。直到看同色背景那张——橘子放在橙色书上。默认阈值下轮廓面积是 401 万，中心在 (1130, 961)，但橘子本身才 45 万左右。也就是说这个轮廓把书本的一大块都包进去了。

我把 S 下界从 100 提到 200，面积掉到 134 万，书本大部分被排掉了。但没完全解决，橘子下面的阴影还是连着，轮廓底部那块明显外扩，只能改善，未能根治。

提高饱和度是有代价的。暗光那张图，原始中心 (1135.11, 578.75)，提到 200 之后变成 (1151.88, 580.86)，横向偏了大概 17 个像素。原因是左侧边缘的暗部像素饱和度不够，被排掉了，质心就往右移。所以"阈值调严"不等于"更准确"，这个我算是体会到了。

另一个方向是把最小面积提上去，我想用它压掉书本那种大块误检。结果提到 200000，小目标那张面积是 166920，直接被滤掉，变成未检测到。同一个参数，一边想去误检，一边造成漏检，说明面积这个指标只能筛大小，判断不了"是不是目标"。

## ROS2 这块

消息是我按题目要求定的四个字段：`bool detected`、`float32 u`、`float32 v`、`float32 area`。一开始我想用 `u=0, v=0` 表示没检测到，后来意识到 (0,0) 本身就是图像左上角，合法的坐标就是 0。要判断有没有目标只能看 `detected`，这个字段不能省。

写发布节点的时候我纠结过要不要先发固定坐标。题目说可以先这样验证通信，但最终必须接真实检测。我最后还是直接接的 `detect()` 返回值，每周期调一次，只是把图片预先读进内存。这样不用事后再改一遍结构，也少一个"忘了改回去"的风险。

跑的时候遇到一个低级问题：`ros2 topic info /target_position` 提示 `Unknown topic`。查了一圈才发现是发布节点还没启动，话题压根不存在。把启动顺序换一下，先起发布端等两秒再查就好了。

参数这块我加了校验回调。改阈值的时候会把整组参数一起校验，有一个不合法就整笔拒绝，保留原来的配置。我实测把 `min_area` 改成 200000，订阅端那边从 `detected=True` 变成了 `detected=False`，说明参数真的生效了，不是只返回一句 `Set parameter successful`。

## 截图遇到的编码问题

截终端图的时候中文全变成"濮撳悕"这种乱码。查下来是同一段 UTF-8 字节被当 GBK 解释了。试了几次，最后把终端切到 UTF-8，输出那行姓名的时候用字节转义才正常。这种问题不影响功能，但截图是要交的材料，乱码交上去肯定不行。

## 还没搞明白的问题

同色背景和目标连在一起的时候怎么分开？

现在能想到的是加形状约束，比如圆度。橘子是圆的，书本是方的，理论上圆度能区分。但我试想了一下，如果橘子被挡住一半，剩下的形状还是不是"圆"就不好说了，圆度可能又把真正的目标排掉。也可能可以看颜色的统计特征，比如橘子的颜色分布比较集中，书本有印刷有渐变。这些我都没实现，也没想清楚哪种更稳。
