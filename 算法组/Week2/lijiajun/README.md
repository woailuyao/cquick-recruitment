## 先说做了什么

五张 512×512 的图，先用 HSV 把橙色抠成黑白掩膜，开运算去掉碎点，找外轮廓，按「面积够大」和「占全部候选面积的比例够高」两道条件挑出目标，再用轮廓矩算中心点，把轮廓、外接矩形、中心点和 `u=.. v=..` 画回原图；检测结果通过 ROS2 话题 `/target_position` 发给另一个节点打印。发布节点的阈值做成了 ROS2 参数，跑起来之后在线就能改。

test4、test5、test7 检出，test6 和 test8 输出 `no target`，发布端发出去的是 `detected=false`、`u=v=-1`。五张里三张成、两张败，成功和失败各覆盖了一遍。

`data/images/` 下的 test4 到 test8 不是实拍，是我用 Anything V5（扩散模型）生成的合成图，尺寸都是 512×512。挑这五张，是因为它们各自难在不同的地方：

- test7：橙子被蓝色杯子挡住右侧三分之一，剩下的轮廓不是完整的圆；
- test8：一整张书桌远景，橙子在右上角只有一小块，木桌、书、纸箱全是暖色。

## 任务一：颜色分割与中心点

### 一根链条

| 步骤 | 做什么 | 产出，给下一步用 |
| --- | --- | --- |
| 1 | `np.fromfile` + `imdecode` 读图 | BGR 数组 |
| 2 | 转 HSV | 三通道 HSV |
| 3 | `inRange` 按橙色范围切 | 黑白掩膜 |
| 4 | 5×5 椭圆核开运算 | 去掉碎点的掩膜 |
| 5 | `findContours`（只取外轮廓） | 一堆候选轮廓 |
| 6 | 面积 + 占比筛选 | 唯一的目标轮廓 |
| 7 | 轮廓矩求中心 | `u`、`v` |
| 8 | 画轮廓、矩形、圆点、文字 | 标注图 |

### 参数

| 项目 | 取值 |
| --- | --- |
| 目标颜色 | 橙色，色相 8–25 |
| HSV 下界 | `(8, 120, 80)` |
| HSV 上界 | `(25, 255, 255)` |
| 最小面积 | 500 像素 |
| 形态学 | 椭圆核 5×5，开运算 |
| 多目标怎么选 | 取面积最大的，并且它要占全部候选面积之和的 50% 以上 |
| 中心点算法 | 轮廓矩，`u = m10/m00`，`v = m01/m00` |

第二道「占比」条件是后来加的。原因很简单：面积阈值只能筛掉小碎块，挡不住「背景被整片吃进来」。test6 的木地板就是后者——最大的一块有 14877 像素，面积上完全合格，可它旁边还散着 43 块同样被误检的地方，最大那块只占全部候选面积的 35.5%，这样才判成「没有目标」。光看面积，这张图是拦不住的。test8 是同一个毛病的极端版：橙子只有 6264 像素，而暖色书桌和纸箱咬出 69 块候选，占比掉到 0.216。

### 五张图的结果

`python3 detect.py` 的输出（`01_检测输出.png` 是当时三张图那一屏，前两行和 test6 与下表一字不差；test7、test8 是后来加进去的，数值来自加图之后的重跑）：

| 图片 | detected | u | v | area | 候选块数 | 最大块占全部候选 |
| --- | --- | --- | --- | --- | --- | --- |
| test4 | True | 228.3 | 347.0 | 51491 | 3 | 0.837 |
| test5 | True | 296.9 | 238.4 | 30706 | 6 | 0.996 |
| test6 | False | -1.0 | -1.0 | 0 | 44 | 0.355（最大块 14877） |
| test7 | True | 148.0 | 258.7 | 30128 | 3 | 0.998 |
| test8 | False | -1.0 | -1.0 | 0 | 69 | 0.216（最大块 6264） |

`area` 一列是程序返回值：判失败时按约定返回 0，不是说最大块不存在；想知道失败那两张大块有多少，看括号里的数。

`area` 是 `contourArea` 算的多边形面积，占比的分子分母也都取自 `contourArea`，口径一致。分母（全部候选之和 61532）比掩膜像素数 62373 少 1.3%，因为轮廓是折线近似，开运算后残留的细边不计进多边形；test4 最大块只有 51491，是因为掩膜里还有光带和碎块，它们算在分母里、不算在分子里。

### 什么时候会失效

反光。test4 左下那条光带的 HSV 是 `H=13 S=218 V=249`，比球本身（`S=199 V=235`）还更饱和更亮，阈值不可能只要球不要它；开运算加到 25×25 光带也没断开。最后只能让轮廓带着这条带子一起被框进来，画出来的框在 `02_结果可视化.png` 左下一眼就能看见。

背景同色。test6 的木地板橙色分量足够进掩膜，S 下限放到 80 的时候甚至能检出一块 48041 像素的「目标」。

目标偏淡。test5 的 S 只有 146，S 下界一旦提到 150，目标直接消失。

遮挡。test7 的橙子被杯子挡住右侧，轮廓在杯壁那里被直接切断，外接矩形右边正好贴着杯沿（`02_结果可视化.png` 第四列）。程序仍判成检出，占比 0.998，但 `u、v` 给的是「可见部分」的质心 `(148.0, 258.7)`，比真实圆心偏下；下游要是拿它去对位，会往影子那侧偏。想拿被挡目标的真实中心，得用最小二乘拟合圆或者椭圆，这周没做。

目标占比太低。test8 里橙子本身 6264 像素，过了 500 的面积门槛，但暖色书桌和纸箱咬出 69 块候选，占比只有 0.216，被第二道条件否掉。这是「有目标却报没目标」，属于宁可漏报也不乱报的取舍。

## 任务二：画回去，然后改参数看变化

### 画了什么

`draw_result()` 在图上画四样东西：绿色轮廓、蓝色外接矩形、红色实心圆点（中心）、红色 `u=... v=...` 文字；没检测到就在左上角写 `no target`。结果全部存成文件，不靠窗口。

`02_结果可视化.png` 是我把五张原图和对应的标注结果拼成的一张图（上排原图、下排结果，每列底下写了这一张的结论），能直接看出几个差别：test4 的轮廓被光带拉长了，中心点略微偏下；test5 边缘有锯齿但整体贴得住；test6 输出 `no target`；test7 的框在杯沿处被切直，底下还带了一小条影子；test8 也是 `no target`。

### 实验一：只动 S 下限

其他都不变（`V=80`、色相 8–25、核 5×5），只把 S 下界从 80 往上提：

| S 下界 | test5 | test6 |
| --- | --- | --- |
| 80 | True，31178 | True，48041 ← 误检 |
| 120 | True，30706 | False，0 |
| 150 | False，0 ← 漏检 | False，0 |
| 170 | False，0 | True，794 |

S 从 80 提到 120，test6 的误检被挡住了，test5 的面积只掉了 1.5%（31178 → 30706），这一档就是最后采用的。

再往上加就出问题了。到 150，test5 的浅橙目标整块没了——漏检。这说明 test5 和 test6 在单条 S 阈值上是打架的：想让木地板进不来，就得把淡一点的目标一起赶走。

170 那一行更有意思：test6 只剩 794 像素的小块，面积刚过 500，但画面里再没有别的候选，它的占比成了 1.0，于是被判成目标——误检又回来了。这一行正好说明两道过滤是互补的：占比管「背景整片被吃进来」，面积管「零碎残留」，缺一不可。

### 实验二：只动开运算核

还是 test5，其他参数不变：

| 核 | 检出 | area | 候选轮廓数 |
| --- | --- | --- | --- |
| 3×3 | True | 32570 | 44 |
| 5×5 | True | 30706 | 6 |
| 7×7 | True | 30014 | 4 |
| 9×9 | True | 29513 | 1 |

3×3 基本没干活，边缘的噪点留下 44 个候选轮廓，最大块虽然还能选中，但每帧都得遍历一堆垃圾。5×5 把候选从 44 压到 6，面积只掉 5.7%，最划算，所以最后用 5。9×9 只剩一个轮廓，可面积掉了 9.4%，边缘被啃掉一圈，圆的边界变得不圆，中心点也会跟着漂——核越大目标越「瘦」。

### 一个误检，一个偏差

误检看 `outputs/cmp_S080_test6.png` 和 `cmp_S120_test6.png` 的差别：前者把木桌整个圈进去，后者干干净净输出 `no target`。

偏差看 test4。那条光带跟球是连着的，轮廓把两个一起包住。光带自己量出来是 10042 像素，扣掉之后球体大约 41000，而现在算出来是 51491；中心点也从只看球时的 `(232.5, 344.1)` 被拽到 `(228.3, 347.0)`，偏了 5.1 像素，大概是球直径（258 像素）的 2%。

试过两种办法，都没用：

- 距离变换其实能把两者分开——光带的最大内切半径只有 22，球是 94.7——但取 `d≥25` 之后面积掉到 25666，中心点跑到 `(240.6, 332.3)`，比不处理还偏；
- 开运算核加大到 25×25，光带依旧断不开（外接矩形的 x 一直是 0）。

所以最后选择留着光带，把 5.1 像素的误差写进文档里，而不是假装修掉了。

### 像素坐标不是世界坐标

图像左上角是原点 `(0,0)`，`u` 往右变大，`v` 往下变大，单位是像素。它只说明「目标这一帧出现在画面哪个位置」，相机装歪一点、分辨率换一下、目标离远一点，同一个物体的 `u、v` 都会变。

要变成米或者场地坐标，至少得有相机内参（焦距、主点、畸变）、相机相对机器人的外参，再加上一个几何前提（比如目标在地面上、或者知道目标实际尺寸）。这周没有标定板也没做标定，所以只输出像素坐标，不能拿去当运动指令。

## 任务三：ROS2 发布与订阅

### 消息

`src/target_interfaces/msg/TargetPosition.msg`：

```
bool detected
float32 u
float32 v
float32 area
```

接口包是 `ament_cmake`，`package.xml` 里声明了 `rosidl_default_generators`、`rosidl_default_runtime`，还加进了 `rosidl_interface_packages` 组，`CMakeLists.txt` 里用 `rosidl_generate_interfaces()` 生成。

没检测到的时候 `u、v` 填 `-1.0`、`area` 填 `0.0`。为什么不填 0：0 是个合法像素坐标（图像左上角），填 0 会让下游以为目标就在左上角；-1 不可能是真实位置，看到负数就知道这帧无效，而且判断只该看 `detected` 字段。

### 两个节点

| 节点 | 包 | 话题 | 触发 |
| --- | --- | --- | --- |
| `target_pub` | `target_publisher` | 发布 `/target_position` | 1 秒定时器 |
| `target_sub` | `target_subscriber` | 订阅 `/target_position` | 收到消息就打印 |

发布端每 1 秒换一张图，`test4 → test5 → test6 → test7 → test8` 循环，调用的是和任务一完全相同的 `detect()`，把 `detected/u/v/area` 填进消息发出去，不是写死的坐标。

### 跑出来的结果

`03_pub_sub分屏.png` 是两端同时运行（10-30 00:16）：订阅端编号到 `[10]`，发布端每 1 秒换一张，当时还是三张图循环，一轮 3 秒。两边打出来的是同一组数：

```
test4  detected=True   u=228.3  v=347.0  area=51491
test5  detected=True   u=296.9  v=238.4  area=30706
test6  detected=False  u=-1.0   v=-1.0   area=0
```

这三行和 `python3 detect.py` 单独跑出来的一模一样。之后把 test7、test8 加进循环再跑一轮，`03_参数化调参.png` 右半屏就是五张循环的日志（test6 → test7 → test8 → test4 → test5），每张都对得上。

`03_interface_show.png` 是四个字段，`03_topic_info.png` 显示 Publisher 1 / Subscription 1，`03_topic_echo.png` 是实际消息内容（u、v 保留了 float32 的完整小数）。

### 加分项：把阈值做成 ROS2 参数

`detect()` 的六个阈值，加上最小面积、占比门槛、核大小，一共 9 个参数，都在 `TargetPublisher.__init__` 里用 `declare_parameter` 声明；`tick()` 里每次先 `get_parameter` 再调 `detect()`，所以改完参数下一个 1 秒周期就生效，不用重启节点。

| 参数 | 默认值 | 对应 |
| --- | --- | --- |
| `h_min` / `h_max` | 8 / 25 | 色相上下界 |
| `s_min` / `s_max` | 120 / 255 | 饱和度上下界 |
| `v_min` / `v_max` | 80 / 255 | 明度上下界 |
| `min_area` | 500 | 最小轮廓面积 |
| `min_ratio` | 0.5 | 最大块占比门槛 |
| `ksize` | 5 | 开运算核边长 |

实测（`03_参数化调参.png`）：节点跑着的时候敲 `ros2 param set /target_publisher s_min 150`，返回 `Set parameter successful`，不重启，发布端日志马上变成：

| 图片 | s_min=120 | s_min=150 | 变化 |
| --- | --- | --- | --- |
| test4 | True，51491 | True，49892 | 面积 −3.1%，仍检出 |
| test5 | True，30706 | False | 直接漏检 |
| test6 | False | False | 不变 |
| test7 | True，30128 | True，28048 | 面积 −6.9%，仍检出 |
| test8 | False | False | 不变 |

有点意外的是 test7：掉了 6.9% 还是检出。原因是挡住一部分之后，露出来的那块橙子颜色很饱和——按检测到的轮廓统计，test7 的平均 S 是 238，而 test5 只有 146，差 90 多。S 提到 150 对 test7 只是削掉边缘一圈，对 test5 是整块砍没。同一种颜色在画面里能差这么远，一条 S 阈值没法两头都照顾，这跟实验一的结论对得上。

截图里还能看到 `ros2 param list` 的输出，9 个参数都在。

### 为什么 u、v 不能直接给底盘

底盘要的是「目标在机器人坐标系下的方位和距离」，像素坐标给不了这两样。它没有深度——目标在 1 米和 5 米远处，`u、v` 完全可以一样。真想用，得先标定相机，再把像素反投影成射线或者地面交点，最后交给控制模块决定怎么走。所以这条消息只是给控制模块的输入之一，不是速度指令。

## 踩过的坑

### 中文路径下 imread 返回 None

第一次跑，读自己目录里的图，`imread` 不报错但返回 `None`，紧接着 `cvtColor` 断言失败。查了才知道 OpenCV 的 `imread` 在 Windows 上走系统窄字符路径接口，遇到中文路径会静默失败。

改法是不用它：`np.fromfile` 把文件当字节读进来，再 `cv.imdecode` 解码；写图反过来，`cv.imencode` 之后 `ndarray.tofile`。就是 `detect.py` 里那两个小函数 `imread_zh` / `imwrite_zh`，后面所有读写都走它们。

### 接口包编译成功，节点却找不到模块

`colcon build` 三个包全绿，`ros2 interface show` 也能显示字段，可一跑发布节点就 `ModuleNotFoundError: No module named 'target_interfaces'`。去 `install/target_interfaces/local/lib/python3.10/dist-packages/` 一看，目录根本不存在——消息的 Python 模块压根没装上。

原因是早先试过 `colcon build --symlink-install`，那个包第一次失败时在 `build/target_interfaces` 里留了半成品；之后普通 `colcon build` 看见构建目录已经存在就跳过安装，于是永远「编译成功、模块缺失」。

把该包的 `build/` 和 `install/` 删掉重编就好了。后来必须看到 `dist-packages/` 下面出现 `target_interfaces` 和 `target_interfaces-0.0.0-py3.10.egg-info` 才算真装上。教训是换编译方式之前先自己删干净，别指望 colcon 发现。

### 发布节点写死了家目录

第一版发布节点里是这么写的：

```python
sys.path.insert(0, os.path.expanduser("~/week2"))
from detect import imread_zh, detect
IMG_DIR = os.path.expanduser("~/week2/img")
```

## 还没搞明白的

**反光带怎么又去掉又不歪中心。** 距离变换能把光带和球分开，可是分开之后面积只剩 25666，中心点反而更偏；开运算加到 25×25 也断不开。现在只能把 5.1 像素的误差记下来，还没找到两全的办法。
