## 任务 1：颜色目标检测
- **目标颜色**：红色（图1）、黑白（图2）、蓝色（图3）
- **HSV 阈值上下界**：
  - 红色：`[0, 43, 46]` 到 `[10, 255, 255]` 以及 `[140, 43, 46]` 到 `[179, 255, 255]`
  - 蓝色：`[100, 80, 80]` 到 `[130, 255, 255]`
- **最小轮廓面积**：50
- **中心点计算方法**：使用图像矩 `cv2.moments` 计算质心，公式为 `cx = m10/m00`, `cy = m01/m00`。当 `m00` 为 0 时进行了异常处理。
- **多目标选择规则**：遍历所有轮廓，过滤面积小于 50 的噪点。如果存在多个目标，使用 `max(contours, key=cv2.contourArea)` 选取面积最大的轮廓作为最终目标。
- **测试图片结果**：图1成功检测并框出12个红色目标；图3成功检测出蓝色目标，中心约在 u=223, v=614。

## 任务 2：可视化与参数对比
- **可视化**：使用了 `cv2.rectangle` 绘制外接矩形，`cv2.circle` 绘制质心，`cv2.putText` 标注了 `u=xxx, v=xxx` 的坐标文字。结果已保存为 `02_结果可视化.png`。
- **参数对比 A（最小面积阈值）**：将面积阈值从 50 调高到 5000 后，图1中较小的红色目标（如衣服细节）被过滤，导致漏检。说明面积阈值需根据目标实际距离调整。
- **参数对比 B（HSV 阈值）**：将蓝色的 H 范围缩窄后，Mask 区域严重萎缩，导致无法检测到完整轮廓。说明 HSV 对光照和颜色纯度非常敏感。
- **误检/漏检案例分析**：
  - **误检**：图2（足球）在纯 HSV 颜色提取下，由于草地反光，导致背景被大量误识别为白色。
  - **漏检**：图2足球因黑白相间，提取出的色块断裂，无法形成完整轮廓。
  - **改进**：最终改用“低饱和度提取 + 大核闭运算 + 长宽比过滤”，成功排除了草地干扰，框出完整足球。
- **像素坐标与真实世界坐标的区别**：像素坐标 `(u, v)` 只表示目标在图像二维平面上的位置，受相机分辨率影响，**不是真实的物理距离（米）**。不能直接发给底盘控制，必须经过相机标定转换为世界坐标。

## 任务 3：ROS2 通信
- **消息字段**：自定义了 `TargetPosition.msg`，包含 `bool detected`、`float32 u`、`float32 v`、`float32 area`。
- **话题名**：`/target_position`
- **发布/订阅流程**：
  - **发布节点**：每次定时器触发时，读取图像并计算真实坐标，将 `detected=True` 及坐标发布。
  - **订阅节点**：监听话题，接收并打印目标的坐标与面积。
- **实际检测结果接入**：发布节点内部已嵌入了完整的 OpenCV 视觉处理逻辑，不再是写死的固定坐标。如果未检测到目标，会发送 `False` 并将坐标设为 `0.0`。
- **为什么 u、v 不能直接当指令**：因为它是相对像素位置，画面里移动100像素，不代表机器人移动了100厘米。

## 🌟 加分项：摄像头实时输入（跨系统推流）
由于开发环境为 WSL2，无法直接通过 `cv2.VideoCapture(0)` 调用宿主机 USB 摄像头。我采用了**“跨系统文件推流”**方案：
1. 在 Windows 宿主端（PyCharm）以 30fps 持续抓取摄像头画面，并覆盖写入 D 盘文件 `live_frame.jpg`。
2. WSL 中的 ROS2 发布节点以 1Hz 频率读取 `/mnt/d/camera_ws/live_frame.jpg` 的最新帧并进行检测。
截图中展示了用蓝色物体在镜头前晃动时，ROS2 发布端算出的 `u, v` 坐标在实时变化，成功实现了基于跨系统推流的实时视觉闭环。
