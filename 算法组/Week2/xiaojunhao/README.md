## 整体链路

一张测试图片进来，走完下面几步，最后变成另一台终端上打印的一行数字：

```
读图 -> HSV 阈值出 mask -> 开闭运算 -> findContours -> 按面积筛 -> 算中心点 (u, v)
     -> 画到图上存成 png，同时在终端打印
     -> 填进 TargetPosition 消息，发布到 /target_position
     -> 订阅节点收到后打印 detected / u / v / area
```

每一步的输出就是下一步的输入：mask 给轮廓用，轮廓给面积筛选和矩计算用，
得到的 `u`、`v`、`area` 原样塞进消息字段。

## 任务 1：颜色目标检测

目标是**橙色的球**。手上没有场地和足球，5 张测试图是用 `src/color_detector/data/make_images.py`
合成的（固定随机种子，每次生成一样），换自己拍的照片时直接覆盖 `data/images` 里的同名文件就行。

参数（都写在 `color_detector/core.py` 里，也能用命令行或 ROS2 参数覆盖）：

| 项目 | 取值 |
| --- | --- |
| HSV 下界 | `(5, 170, 80)` |
| HSV 上界 | `(22, 255, 255)` |
| 最小轮廓面积 | 1500 像素平方 |
| 多个候选时 | 按面积从大到小排序，取最大的那个 |
| 中心点算法 | 用图像矩 `m10/m00`、`m01/m00`；`m00` 为 0 时退回外接矩形中心 |

图片是 1280x960。5 张图的结果（`python -m color_detector.detect_image`）：

| 图片 | 情况 | 结果 | 中心 (u, v) | 面积 | 实际中心 |
| --- | --- | --- | --- | --- | --- |
| 01_clear | 目标大、背景干净 | 命中 | (640, 480) | 89064 | 约 (640, 480) |
| 02_small | 目标只占 82x82 像素 | 命中 | (950, 600) | 5092 | 约 (950, 600) |
| 03_similar_bg | 木桌背景，颜色接近 | 命中 | (500, 520) | 52940 | 约 (500, 520) |
| 04_shadow | 暗光 + 阴影 | 未检测到 | - | - | 约 (800, 520) |
| 05_green_ball | 绿色的球 | 未检测到 | - | - | 约 (600, 500) |

04 和 05 没检测到是正确的：04 的目标在阴影里，饱和度掉到 170 以下；
05 本来就是绿色的，橙色阈值不该命中它。这两张正好验证了“没有目标时要明确报未检测到”，
代码里不会拿 `(0, 0)` 冒充坐标。

**会失效的情况**：

1. **光照/阴影**：目标变暗以后 S 和 V 一起下降，直接掉到阈值外面（04 图就是这样）；
2. **背景同色**：03 图能检出，是因为木桌的 S 在 135 左右，靠 S 下限 170 强行分开的。
   光照一变，木桌的 S 可能升到 170 以上，背景就会整片被当成目标；
3. **反光**：球面高光那一块会变白，mask 上出现空洞，面积和中心点都会偏；
4. **遮挡**：目标被挡住一部分，面积可能掉到 1500 以下，直接漏检。

## 任务 2：可视化与参数对比

结果图：`02_结果可视化.png`（四张图的标注）、`02_参数对比.png`（两组参数对比）。
标注里画了轮廓、外接矩形、红色十字中心点和 `u=.., v=..`、`area=..` 文字；
没检测到的图会在左上角写 `no target`。

**对比 A：S 下限 170 和 120**（用 03_similar_bg 这张背景接近的图）

- S≥170：只框住球，面积 52940，中心 (500, 520)，是对的；
- S≥120：木桌背景整片进 mask，外接矩形变成整幅图 (0,0,1280,960)，面积 1226561，
  中心跑到 (640, 480) —— 这是画面正中间，跟球没关系，属于典型**误检**。

**对比 B：最小面积 1500 和 6000**（用 02_small 这张小目标的图）

- min_area=1500：命中，面积 5092，中心 (950, 600)；
- min_area=6000：同一个球，因为 5092 < 6000 被自己滤掉，变成**漏检**。
说明面积阈值不是越大越好，得比最小目标还小一点。

另外把形态学关掉试过一次：04 图里没经过开运算时有 124 个碎轮廓，做完开闭运算剩 0 个。
结果都是未检测到，但碎块数量差很多，说明开运算主要是清噪点，不是万能药。

**关于坐标**：图像左上角是 `(0, 0)`，`u` 向右增大，`v` 向下增大，
所以 `v` 越大越靠下，这跟数学课上的 y 轴方向是反的。像素坐标只说明目标在画面里的位置，
**不是米，也不是场地坐标**。要变成机器人能用的位置，需要相机标定（内参、畸变）
和相机安装位置的关系，这周不做。

## 任务 3：ROS2 通信

两个包：

- `target_interfaces`（ament_cmake）：只有 `msg/TargetPosition.msg`；
- `color_detector`（ament_python）：检测逻辑和两个节点。

消息字段就是细则里要求的 4 个：

```
bool detected
float32 u
float32 v
float32 area
```

话题固定 `/target_position`，`std_msgs` 那种类型名不用管，直接用
`target_interfaces/msg/TargetPosition`。

流程：

1. `detect_node` 每秒读一张图，跑一遍检测，把 `detected/u/v/area` 填进消息发出去；
2. 没检测到时 `detected=False`，`u/v/area` 一律填 0，接收方必须先看 `detected`；
3. `listener_node` 订阅同一个话题，把四个字段打印出来。

发布频率和图片目录、HSV 阈值、最小面积都做成了参数，运行中可以改：

```bash
ros2 run color_detector detect_node --ros-args -p s_min:=150 -p min_area:=800
```

**为什么 u、v 不能直接当运动指令**：它只是目标在图像里的像素位置，
画面中心对应 (640, 480)，但镜头稍微转一点这个数就变了；而且它不包含距离信息，
同一个像素偏移，目标在两米和五米外对应的实际角度差很多。
真正的控制要先标定相机、算出目标相对机器人的方向，再交给控制节点。

## 问题与解决过程

一开始把 S 下限设成 120，跑 03 那张图，输出里面积是 1226561、外接矩形是 (0,0,1280,960)，
明显不对，但当时以为是轮廓取错了。把 mask 存下来一看，整张图都是白的——
木桌的 S 大概 135，比 120 高，所以背景全进来了。后来把几张图的 S 值打出来对比，
目标在 200 以上、背景在 135 左右，把下限提到 170 就干净了。
