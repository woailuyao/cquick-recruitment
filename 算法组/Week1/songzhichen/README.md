### 3.1 为什么要一个 cv_io.py

提交路径 `算法组/Week1/songzhichen/` 里有中文，`C:\cv` 下的数据目录也可能带中文。而 OpenCV 在 Windows 上读不了带中文的路径——
`cv2.imread` 返回 `None`、`cv2.imwrite` 返回 `False`，而且不报错，很难查。

所以把读写封装了一下：先用 `np.fromfile` 把文件读成字节流，再 `cv2.imdecode` 解码；
写的时候先 `cv2.imencode` 编码，再 `buf.tofile()` 落盘。这样路径带不带中文都能用。
三个脚本里都只调 `imread_u` / `imwrite_u`，不再直接用 `cv2.imread`。

## 5. 关键参数及含义

| 参数 | 取值 | 为什么这么设 |
|---|---|---|
| 橙色 HSV 下限 | (5, 120, 120) | H 取 5~25 覆盖橙色；S≥120 挡掉灰白背景；V≥120 挡掉阴影 |
| 橙色 HSV 上限 | (25, 255, 255) | H 上限 25，再往上就是黄色/黄绿了；S、V 不设上限 |
| 弱光图下限 | (5, 90, 40) | 暗光下目标 V 只有 106，S 也被噪点拉低，所以 V 降到 40、S 降到 90 |
| 拼盘图下限 | (5, 150, 90) | 柠檬 H≈24 在橙色区间里，靠 S≥150 把它排掉（柠檬 S 只有 132 左右） |
| 面积阈值 | 3000 / 3000 / 8000 | 小于它的连通域当噪声；拼盘图取 8000 是为了排掉柠檬高光那块 2779 像素 |
| 高斯核 | (5,5) 和 (9,9) | 5×5 去噪又不糊边缘，9×9 去噪更强但边缘更钝 |
| 固定阈值 | 127 和 80 | 127 是 0~255 的中点作基准，80 用来看「调低之后白区变大多少」 |
| 形态学演示阈值 | 150 | 取在亮暗过渡带上，掩膜碎得厉害，开/闭运算的效果才看得出来 |
| Canny 阈值 | (50,150) 和 (80,200) | 低阈值抓弱边缘（多而碎），高阈值只留强边缘（少而准） |
| 形态学核 | 5×5 全 1 | `np.ones((5,5), np.uint8)` |

HSV 范围不是拍脑袋写的，是先取像素点量出来再放宽。任务三脚本里留了一段被注释掉的
取像素代码，就是当时量柠檬和橙子用的。

## 6. 任务一结果

处理了 3 张尺寸不同的图（512×512、512×480、236×146），输出 12 个 png。

- 每张图都打印了宽高和通道数，比如 `宽=512 高=512 通道=3`。
- 缩放：`cv2.resize(img, (w//2, h//2))`。注意 resize 的参数是 **(宽, 高)**，
  跟 `img.shape` 的 (高, 宽, 通道) 顺序是反的。
- 裁剪：`img[h//4:h*3//4, w//4:w*3//4]`，切片是先行后列，就是 `[y1:y2, x1:x2]`。
- 灰度：`cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)`。
- 每个输出文件都做了「写入 → 重新读回来 → 比对尺寸」三步，都通过了。
- 原图前后用 md5 校验了一遍，没有被覆盖。

换尺寸的兼容性也顺带验了：`taj.jpg` 只有 236×146，缩放后 118×73、裁剪后 118×73，
脚本里没写死任何尺寸。

## 7. 任务二结果

用的 `orange_normal.jpg`，输出 14 张中间结果 + 一张带标题的总览拼图
`outputs/task2/00_side_by_side.png`，参数记在 `outputs/task2/params.txt`。

四组参数的实际影响：

| 对比 | 实测数字 | 说明 |
|---|---|---|
| 高斯滤波 | Canny 边缘像素 6719 → 891（5×5）→ 416（9×9） | 核越大，橙子表面颗粒造成的假边缘越少，但轮廓也被磨钝 |
| 阈值调低 | 白色占比 54.2%（127）→ 81.0%（80） | 阈值调低，偏暗的像素也被判成白，白区变大，绿背景也被吃掉一部分 |
| Canny 抬高 | 边缘 6719（50,150）→ 1271（80,200） | 只留强边缘，橙子表面的弱纹理全丢，轮廓干净了但可能断 |
| 开运算 | 连通域 723 → 37，白像素 35.7% → 30.9% | 删掉孤立的小碎片 |
| 闭运算 | 白像素 35.7% → 40.6%，连通域 723 → 90 | 把暗缝填上，亮区连成片 |

关于形态学那张演示图：最开始我是拿阈值 127 的掩膜做的，白像素只从 54.18% 变到 50.11%，
肉眼看不出变化，还以为是 `morphologyEx` 用错了参数。后来把连通域数打出来才发现，
127 那张掩膜 489 个连通域里有 483 个不到 50 像素，开完剩 24 个——变化其实有，只是白区连成一片不显眼。
换成 150 之后掩膜碎得多（723 个连通域，712 个不到 50 像素），开运算完剩 37 个，对比一眼能看出来。

拼图 `00_side_by_side.png` 里三行分别是：灰度 / 高斯5×5 / 阈值127；阈值150（碎片多）/ 开运算 / 闭运算；
Canny(50,150) / Canny(80,200) / 自适应阈值。

## 8. 任务三结果

目标是**橙色物体**。脚本跑两轮，结果都写进 `outputs/task3/report.txt`。

**第一轮：三张图都用同一套默认参数 (5,120,120)~(25,255,255)，min_area=800**

| 图片 | 检出 | 情况 |
|---|---|---|
| orange_normal | 1 个，中心 (323,280)，面积 96215 | 正常 |
| orange_lowlight | **0 个** | **漏检**：目标 V 从 232 掉到 106，低于 V 下限 120，整只橙子被切掉，掩膜几乎是全黑的 |
| orange_cluttered | **3 个**：87986 / 8400 / 6966 | **误检**：右下角柠檬是黄的，H≈24 落在橙色区间里，S≈132 又刚过了 S≥120 |

**第二轮：逐图调参**

| 图片 | 参数 lower / min_area | 检出 | 中心 | 面积 | 目标区 HSV |
|---|---|---|---|---|---|
| orange_normal | (5,120,120) / 3000 | 1 | (323,280) | 96215 | (22,226,246) |
| orange_lowlight | (5,90,40) / 3000 | 1 | (311,282) | 108115 | (19,209,106) |
| orange_cluttered | (5,150,90) / 8000 | 1 | (169,229) | 86928 | (17,191,164) |

几个参数是怎么定下来的：

- 正常图：HSV 范围不用动。面积阈值从 800 提到 3000，是因为图下方左侧有一条红色的边缘，
  面积 597 像素，会被当成一个小目标。
- 弱光图：V 下限 120→40、S 下限 120→90。压暗之后目标 V 中位数只剩 106，噪点又把 S 拉低。
  调完中心 (311,282) 跟正常图的 (323,280) 基本重合，说明位置是对的。
- 拼盘图：先抬 S 下限到 150 排掉柠檬主体（柠檬 S 只有 132 左右，橙子 218）。
  但只抬 S 不够——柠檬最亮的高光处 S 能到 221，还剩一个 2779 像素的小块，
  所以又加了面积阈值 8000。橙子 8.7 万、残块 2779，中间空隙大，取 8000 余量足够。

产出：`mask_*.png` 掩膜、`result_*.png` 原图上画绿框 + 红心 + 坐标、`report.txt` 两轮对比。

## 9. 失败案例和已知问题

**案例 1：弱光图一个都检不出**

- 现象：`orange_lowlight.jpg` 第一轮检出 0 个。
- 怎么查的：把掩膜存下来看，整张几乎是全黑的，说明 `inRange` 一个像素都没选中；
  再打印目标区的 HSV，V 中位数只有 106，而默认下限是 120。
- 原因：压暗 45% 后目标 V 从 232 掉到 106，正好卡在下限下面。
- 改进：V 下限降到 40、S 下限降到 90，第二轮检出中心 (311,282)、面积 108115。
- 更好的做法：先做 gamma 校正或 CLAHE 提亮再转 HSV，这样阈值不用跟着光照变。
  这次没做，因为那样会把这个「阈值依赖光照」的问题藏起来，不如留在报告里。

**案例 2：水果拼盘把柠檬也检出来了**

- 现象：第一轮检出 3 个，多出来的两个在 (443,312) 和 (423,396)，都在右下角柠檬上。
- 原因：柠檬本身就是黄的。H≈24 落在橙色的 [5,25] 区间内，S≈132 也过了 S≥120 这关，
  光靠色相分不开——橙子和柠檬的色相本来就只差几度。
- 改进：S 下限提到 150 排掉柠檬主体（它的 S 只有 132），面积阈值提到 8000 排掉柠檬高光那块 2779 像素。
  两道关都能单独排掉，一起用更稳。
- 遗留问题：靠 "S 高一点" 来区分橙子和柠檬其实不稳，换个光线 S 就可能越过 150。
  真正要分得看形状，不是颜色能解决的。

**案例 3：两个橙色目标粘成一个（目前没解决）**

- 现象：`orange_cluttered.jpg` 第二轮的框是 (0,0,359,477)，从左上角一直拉到中间，
  但人眼看目标就只有中间那片橙子。中心点 (169,229) 也被带偏了。
- 原因：左上角还有半个橙子，和中间那片颜色一样、在掩膜里是连通的，
  `findContours` 把两处当成同一个连通域了。
- 为什么没改：要分开得上分水岭，或者先 `cv2.erode` 把细连接腐蚀断、找完轮廓再映射回原图，
  这些超出本周传统图像处理入门的范围，就先如实记着。
- 打算怎么改：先腐蚀 2~3 次把连接断开，再 `findContours`，最后把面积按腐蚀次数粗略还原。

**其它已知限制**

1. 颜色阈值法完全依赖目标和背景的颜色差异。画面里要是有大面积橙色背景（橙色桌布之类），
   光靠 HSV 会一直误检，得再加面积、长宽比、位置之类的先验。
2. 香蕉、芒果、柚子这类黄色系水果，H 跟橙色几乎重叠，S 也高，靠颜色基本分不开。
3. 强反光的地方 S 会掉很低，目标内部会出现空洞，闭运算只能补小洞，补不了大块。
4. 这些阈值都是为这 4 张图调的，换场景必须重新标 HSV 范围。

## 11. 常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| `imread` 返回 None | 路径错 / 有中文 / 扩展名大小写 | 用 `src/cv_io.py` 里的 `imread_u` |
| `ModuleNotFoundError: cv2` | 没在 `cv_practice` 环境里 | 按第 1 节的方式启动 |
| Jupyter 里 `cv2.imshow` 卡住 | Notebook 没有窗口事件循环 | 改用 matplotlib，或者直接看 `outputs/` 里的图 |
| 显示出来红蓝互换 | BGR 喂给了 RGB 的显示函数 | `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)` |
| `findContours` 解包报错 | 3.x 返回 3 个值，4.x/5.x 返回 2 个 | 本项目是 4.12，写 `contours, _ = ...` |
| 换台电脑跑不了 | 用了绝对路径 / 没装依赖 | 全部相对路径，照第 1 节装环境 |
