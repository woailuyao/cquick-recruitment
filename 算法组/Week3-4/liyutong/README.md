- **畸变系数**：k1 = 0.078232，k2 = −0.002833，p1 = 0.002015，p2 = 0.000364，  
  k3 = −0.224683（plumb_bob）
- **相机外参**：`rig_frame`（三脚架 = 可移动测试架），高度 **0.450 m**（卷尺实测），  
  俯仰 **16.50°**（向下为正），滚转 **−5.80°**。几何解算给出 0.390 m，与卷尺差 15%，  
  取舍理由写在 `config/camera.yaml` 的 `height_disagreement` 字段里
- **外参只对「标定时的那套三脚架姿态」成立**。这一点是被现场数据打回来才确认的：  
  录 L/T/X 那 34 段素材时三脚架的俯仰被重新调过，用 `16.50°` 去解 `X_1` 失败。  
  反算证据：`X_1` 里中圈直径 1.5 m 呈椭圆，横轴 226 px → 相机到圆心  
  `501×1.5/226 ≈ 3.32 m`；椭圆短长轴比 63/226 = 0.279 → 该射线对地面仰角  
  `asin(0.279) ≈ 16.2°`；而圆心像素在 `cy−98`，即光学轴上方 11.1°，  
  于是俯仰 ≈ 16.2 + 11.1 ≈ 27°，**不是 16.5°**。  
  所以那 34 段只能当「检测训练数据」，不能当「定位验证数据」。
- **地面投影方法**：像素 → `cv2.undistortPoints` 去畸变 → 相机系射线方向 →  
  乘 `R_ground_to_camera` 转到架体系 → 与地面 Z = 0 求交（等价于 `s = −h / w_z`）→  
  得到架体系地面点。射线不下行（打在地平线以上）的点直接丢弃
- **地图匹配算法与同类标志消歧方法**：
  1. 架体系地面点与地图标志点做**同类点对假设**（L 只配 L、T 只配 T、X 只配 X），  
     每对假设确定一个 2D 刚体变换（尺度已知，故只有 3 个自由度）
  2. **RANSAC** 取内点最多的假设，再用 **Kabsch / Procrustes** 精化并迭代重分配内点
  3. 相机必须位于场地内（±4 / ±3 再加 0.4 m 余量）作为硬约束，滤掉场外解
  4. **180° 二义消歧**：场地两端标线中心对称，θ 与 θ+180 的残差完全相等，必须靠线索  
     打破，① 时序连续性（视频流首选）② 球门像素位置 ③ 本帧是否看得见球门。  
     线索打分用 `hypot(Δxy, Δyaw_in_rad)`，即把 1 rad 航向误差折算成 1 m 位移

     早期这里用 `−(Δxy + 0.15·Δdeg)`，航向权重给太大，导致为了对齐航向而挑一个  
     位置离谱的解（解出过 x=−4.95 m 这种相机在场外的位姿）。改成 hypot 后消失
- **输出坐标系**：`rig_frame`（相机所在的可移动测试架）。若相机固定安装在车体上，  
  把 `camera_extrinsics.yaml` 的 `reference_frame` 改成 `base_link`，其余语义不变
- **3 个以上测试点的参考坐标与误差**：见下面 C0 现场测试表（由 `eval_c0.py`  
  回放 `gt1_1` / `gt2_1` / `gt3_1` 三段现场视频自动统计，每点取全部有效解的中位数，

- **marker_count / residual / valid / status**：

  - `residual`：内点的重投影残差 RMS（单位**像素**）
  - `valid`：`marker_count ≥ 2` 且地面残差 < 0.5 m、重投影残差 < 10 px、

  - `status`：`OK` / `NO_MARKERS` / `NO_MATCH` / `TOO_FEW_INLIERS` /

- **实时 FPS / 定位更新频率 / 耗时**：两模型同帧推理 **13.3 FPS**（CPU）。

### 离线验证（合成数据自测）

4 个点位各转一圈（像素噪声 1 px、15% 丢检），按视频流的时序连续性逐帧解算。  
用**连续轨迹**而不是单帧随机位姿评估：单帧没有连续性可用，180° 二义无法消解，  
会得到「50% 翻错支」的假结论，那种评估方法本身就是错的。

`-n 120`（每帧转 3°）的完整结果，包括算不出解的那部分：

| 指标                      | 结果                         |
| ----------------------- | -------------------------- |
| 总帧                      | 480                        |
| 可见标志点不足 2 个（物理上无解，不怪算法） | 79                         |
| 点数够解算的帧                 | 401                        |
| 其中给出有效解                 | 250（**62.3%**）             |
| 锁到错误分支（翻 180°）          | **0**                      |
| 位置误差 中位 / P90 / 最大      | 5.1 cm / 22.1 cm / 75.4 cm |
| 位置误差 < 20 cm 占比         | 89%                        |
| 航向误差 中位 / P90 / 最大      | 0.37° / 2.76° / 8.96°      |
| 航向误差 < 5° 占比            | 98%                        |
| 每帧可见标志点 中位 / 范围         | 3 / 2~7                    |

`-n 360`（每帧转 1°，更细）：有效解 771 / 1213 = 63.6%，锁错支 9 帧，位置中位 6.0 cm，  
航向中位 0.48°。两次结果一致，说明不是参数凑出来的。

复现：`python localize.py --selftest -n 120`

**那 38% 的失败去哪了**（`status` 可以直接区分）：

| status          | 帧数 | 含义                                |
| --------------- | -- | --------------------------------- |
| `JUMP_REJECTED` | 82 | 相邻帧位姿跳变超出物理可能（>60° 或 >0.8 m），主动否决 |
| `REPROJ_FAIL`   | 54 | 重投影误差 > 10 px，说明地面拟合到的位置是错的       |
| `NO_MATCH`      | 15 | 没有一致的点对组合                         |

`JUMP_REJECTED` 这条门禁是专门加的，原因是查出来一个**级联失效**：场地两端标线  
中心对称，某些朝向的可见点集恰好也对称，于是一帧翻支之后 `prev` 跟着错误解走，  
之后二十多帧一路锁死在错支上（日志里 −63°→117°、−60°→118°……连续出现）。  
加门禁后这一整段消失。

门禁的物理依据：15 fps 下 60°/帧 相当于 900°/s，0.8 m/帧 相当于 12 m/s，  
操作者不可能做到，所以一旦出现就必然是错解。这种情况下输出 `valid=FALSE`，  
上层只会当作本帧没解出来；如果给一个看起来很确定的错位姿，上层会以为定位正常。

也试过两种「更聪明」的改法，都更差，记在这里避免以后重复踩：

| 尝试                   | 结果                                  |
| -------------------- | ----------------------------------- |
| 放宽候选池到「内点最多减 2」      | 低内点假解被放进来，锁错支 9 → **43** 帧，更差       |
| 把跳变约束提前成打分里的 −100 惩罚 | 选择被推向「窗口内但几何错、内点少」的候选，出现逐帧缓慢漂移，同样更差 |

这两种改法都不如现在的做法：候选池只保留内点最多的那一档，跳变只做事后否决，  
不在打分阶段引导选择。

### 相机高度的独立复核

`localize.py` 的 `solve_height()` 利用「残差随高度误差单调增大」这一性质，从多帧  
标志点反解相机高度。合成数据验证：

| 真值      | 反解结果    | 残差 @0.39 m | 残差 @0.45 m |
| ------- | ------- | ---------- | ---------- |
| 0.450 m | 0.450 m | 6.62 px    | 3.01 px    |
| 0.390 m | 0.385 m | 3.59 px    | 6.48 px    |

两种高度在像素上有 2 倍以上的残差差，**可以判别**。现场第一个能看到 ≥4 个标志点的  
位置跑 `python demo.py --solve-h`，就能拿到实测高度来确认卷尺值。

### ONNX 导出与推理对比（+3）

两个 `best.pt` 均以 `imgsz=640 / opset=12` 导出，测试用**同一个独立测试集**抽样 20 张，

  | 测试点 | 参考 (x / y / yaw) | 估计 (x / y / yaw) | 平面位置误差 | 航向误差 |
  |---|---|---|---|---|
  | gt1_1 | +0.00 / +0.00 / +0.00 | 无有效解 | — | — |

- **失败原因（已定位到具体数据，不是算法）**：这四段 gt 素材的取景把标志点全都压到了
  **地平线附近或画面边缘**，检测器根本拿不到可用的像素点。实测证据：
  1. 四段全片扫描（每 12 帧一次），**最多只检出 1 个标志点，且置信度上限只有 0.12**

     低 70 余 px。按高度 0.45 m 反算，它们对应的是**约 3.55 m 处的地面**，
     该处地面仰角只有 `atan(0.45/3.55) = 7.2°`，一个 90° 接头在这个仰角下，
     椭圆压扁比只有 `sin 7.2° = 0.126`，投影后已经退化成一条短线，不再是可辨的接头。
  3. `gt1_1`（P1 场地中心朝球门）的问题更彻底：画面里唯一落在地面上的白线只有
     画面底部的**中圈圆弧**，而圆弧上没有任何接头（X 点在中线与圆弧的交点，中线在
     相机脚下、不在视野内）。画面 y ≈ 170 那条横线**在地平线以上**，是球门后的白墙，
     不是场地标线。
  4. 几何上也对得上：站在 (0, 0) 朝 +X 看，罚球区两个前角 (3, ±1.9) 的横向张角是
     `atan(1.9/3) = 32°`，落到像素上偏移 `501·tan32° ≈ 313 px`，即 x ≈ 20 与 x ≈ 646，
     一个贴左边缘，一个**已经出画**。
### 2026-11-17 返场复测（重录 5 段，仍未通过）

**根因（比 11-15 那次更明确）**：当天重新标定后相机实际是**近乎水平**的（俯仰只有 4.36°），
在这个视角下对着球门方向拍，画面里永远只有一个拐角；而定位链路每帧至少要 2 个点
（想要稳定要 3 个）。**这不是算法问题，是这套「0.45 m 高 + 65° 视场」的相机配置
在 8×6 m 场地上的可见性本身就紧，16 个标志点里，任何单一视角都只能覆盖 3~4 个。

**结论**：两次进场、一共 9 段素材，没有一段能解出有效位姿。C0 表按实际结果留空，
下面给出算法链路的独立证据（合成数据自检）。
重录的正确姿势已经算清（抬到 0.90 m、俯仰 20°、站到指定机位），但考核期内没有第三次进场机会。
- **算法本身可用的证据（合成数据自检）**：`python localize.py --selftest` 的结果：
  4 个点位各转一圈，200 帧，注入 1.0 px 像素噪声 + 15% 随机丢检：

  ```
  总帧 200   可见点不足 2 个（物理上无解）32   解算失败 62   有效解 106   锁错支 0
  在「点数够解」的 168 帧里：成功率 63.1%
  位置误差  中位 5.2 cm   P90 21.9 cm   最大 50.1 cm   <20cm 86%
  航向误差  中位 0.41°    P90 2.86°     最大 7.03°    <5° 97%
  ```

  即：像素→地面→匹配→位姿这条链路是可用的，误差量级在厘米级。
- **如果重拍 gt，需要改成**：把相机俯仰加大到能让罚球区前角落在画面中部（约
  中线高度），或者干脆站在能同时看到 3 个以上不同类标志点的位置录。判据很简单：
  录制时先跑一次 `demo.py`，底部 `marker_count` 掉到 1 就说明这个机位废了。
- 定位失败场景与处理：
  - 画面里只有 1 个标志点 → `status=NO_MARKERS`，`valid=FALSE`。
    处理：提示操作者后退半步或转一点角度，让第 2 个标志点进画面
  - 全部标志点都是同一类（比如只有两个 L）→ 点对假设多解且残差接近，可能 180° 翻转。
    处理：靠上一帧连续性消歧；若首帧就如此，要求先朝球门方向锁定
    （球门在画面里 = yaw≈0 的先验）
  - 相机被抬离标定高度 → 所有距离按比例缩放。处理：`--solve-h` 反解高度重设
- 评审记录 / 备注：（留空给评审填写）

## 问题与解决过程

按时间顺序，只写真正卡住过的问题和定位过程。

**1. 坐标系一开始就搞错了：原点放在了角点**

第一版 `gen_field_yaml.py` 把原点取在场地一角、+X 沿长边。后来对照《算法考核细则》
的「场地坐标系示意图」核对，才发现细则规定**原点 = 场地中心**、+X 指向球门、
+Y 为面向 +X 时的左侧。`field.yaml`、`gen_field_yaml.py` 和俯视图全部重算，
俯视图也改成与细则同向（球门在上、+Y 朝左）。

**2. 点球点的矛盾：细则 vs 现场**

细则说点球点在场地中心，实测却发现中心偏向一侧约 0.4 m。先在代码里按细则改成
(0, 0)，后来回到场地确认「中圈圆心处地面什么都没画」，才定下来：**P 类不作为
检测类别**，只留在地图的 `anchors` 段作参考；地图原点改由两个 X 类（中线与中圈的
两个交点）连线中点反推。这样即使原点与实体标记有偏差，也会被 X 点纠正过来。

**3. labelImg 在这台机器上跑不起来，干脆自己写标注工具**

先是 `labelImg.exe` 一启动就报 `WinError 4551 应用程序控制策略已阻止此文件`，
绕过后又在画框时 Qt 底层崩溃。定位过程：该机 Windows「智能应用控制」处于强制模式
（`VerifiedAndReputablePolicyState=1`），会拦无信誉的 `.cmd/.bat`、无信誉 DLL 和
pip 生成的 exe；PyQt5-sip 的版本差异也决定 `sip.pyd` 能否放行（12.20.1 被拦，
12.11.0 可通过）。

结论是不去填第三方工具链的坑，直接用 OpenCV 窗口写了 `label_tool.py`，不依赖 Qt，
还顺手支持「左键加框 / 右键删框 / 数字键切类别」这些在 labelImg 里要多点几次才行的
操作。实际标注速度反而更快。

**4. 抽帧/录制脚本的 `--name` 前缀在启动时定死，中途改不了**

第一轮录了 12 段，全部存成了 `L_1..L_12`，因为前缀是启动参数，录到一半改不掉。
结果只覆盖了 L 一类，其它类别全缺，只能重录一遍。

这条已经写进 `现场录制清单.md`：**每换一个类别前缀都必须按 q 退出重开。**

**5. 白线占比统计一开始全错，换了两次判据才可用**

先用 `cap.set(CAP_PROP_POS_FRAMES, ...)` 跳帧读，测出几段的白色占比都是 0.00%，
明显不对。改成顺序读帧、每 15 帧测一次就正常了，视频的随机 seek 并不精确。

紧接着发现第二个坑：这批素材整幅偏灰（饱和度中位数只有 39~56），最初「低饱和 +
高亮 = 白线」的判据把白墙和过曝天空一起算成白线，白线占比虚高到 30%+，
所有段都被判成「过曝」，筛查完全失效。最后改用**顶帽变换**（只保留比 15×15 邻域亮
且更窄的细结构）才恢复判别力。

阈值这块最后是拿像素分布定下来的，不是靠反复试参数试出来的。

**6. 试过「用几何方法自动预标注标志点」，连试三版都失败，及时放弃**

思路是：标志点本质是白线接头，用「白线掩膜 + 直线聚类 + 交点处数射线」应该能自动
分出 L（2 条射线）/ T（3 条）/ X（4 条）。前后写了三个版本，都被真图打回来：

| 版本 | 判据 | 结果 |
|---|---|---|
| v1 骨架法 | 骨架化后数 8 邻域连通分量 = 2/3/4 | 单点精度很好（`(312,186)` → 3 臂 → T，误差 2 px），但候选点被淹没：`T_2` 原始 75 个候选，加草地/边缘过滤后还剩 20 个，真接头不在前列；`X_1` 111→66，两个真交点一个都没进前 20 |
| v2 射线臂长法 | 从候选点沿 24 个方向量白线能延伸多长，恰好 2 条长臂且夹角 50°~130° 判 L | `T_1` 的真实接头在 `(345,180)`，分类器给的最优点在 `(320,173)`，偏 25 px；`L_7` 的最优点直接跑到画面最下边缘 |
| v3 霍夫线段端点法 | 两条方向不同的线段，若端点都汇聚于同一交点则判 L | `L_3` 的真实拐角在 `(598,163)`，一个 L 都没报出来；`T_1` 直接「无候选」 |

**根因**：这片场地的素材里，白墙、椅子腿、球门网、远处场地线**全都是白色细结构**，
而真标线反而又细又淡（顶帽峰值只有 60~140，草皮高光能到 70）。任何「找白色细结构
+ 找几何关系」的判据，信噪比都不够。这与第 6 条之前那版（去模糊/去过曝筛选）的结论
一致，不是调参问题，是信息量不够。

判断：把这样的预标注交给人工「校对」，删错框比从零画还慢，**净收益为负**。
于是删掉脚本，改成两条更省时间的路：

1. **逐帧过质量闸门**把糊帧/过曝帧筛掉，再人工标注
2. **同段连续帧继承**：三脚架不动，同一段视频相邻帧的接头只差几像素，画完第 1 张
   后面自动继承。实测 30 段 268 帧对，帧间灰度差中位 3.32，继承阈值取 15 后再叠加
   「框周围还有没有白线结构」的局部判据兜底，**274 次手画降到约 79 次**

继承逻辑省下来的时间，比继续调预标注器多得多，所以那三个版本的脚本就没有再往下改。

**7. 相机高度：几何解算 0.390 m 与卷尺 0.450 m 差 15%**

这是必须给结论的矛盾。先排除了尺度输入错误的可能（`SQUARE_MM = 20.0` 与
「5 格 = 100 mm」的实测一致，棋盘打印没有缩放）。然后看一致性统计：9 张样本的
高度标准差 31.9 mm，而**俯仰标准差 2.28°、滚转标准差 2.04°**，相机本身没动，
俯仰/滚转却在变，说明是棋盘平面自身在倾斜（人工草皮加垫子，30~60 mm 的面起伏
很常见），而几何解算要求棋盘绝对平贴且 Z = 0。

结论是采信卷尺值 0.450 m：卷尺直接量的是「镜头到地面」这个物理量，不依赖棋盘平整度。

但没有就此收工，在 `localize.py` 里加了 `solve_height()`，用标志点自己反解高度。
合成数据下能准确复原 0.39 与 0.45，且两者残差差 2 倍以上，现场跑一次就能当裁判。

加了 `solve_height()` 之后，这两种高度在现场可以直接分出胜负，不用再靠猜。

**8. `cv2.waitKeyEx` 返回 −1 的坑，差点让所有标注被清空**

标注工具早期写的是 `cv2.waitKey(20) & 0xFF`。没有按键时 `waitKey` 返回 −1，
`& 0xFF` 之后变成 255，正好落在「清除所有框」的分支上，于是每 20 ms 清一次框，
按 D 下一张时就把空标注写进了磁盘。后来改成 `cv2.waitKeyEx` 并**先判断 −1 再取
`& 0xFF`**，同时给保存加了保险：一个框都没有、又不是用户主动清空时，绝不覆盖磁盘上
已有的标注。

**9. 相机高度可解这件事，顺带解决了「换个人拿相机就全偏」的隐患**

外参（俯仰/滚转）是在三脚架上标定的。如果演示时换人手持、角度变了，固定外参会让
地面投影整体偏掉。因此演示脚本把俯仰/滚转仍按标定值，但高度可以 `--solve-h`
现场反解；README 里也写明了「相机被抬离标定高度会导致所有距离按比例缩放」这个
失效模式，以及对应的处置办法。
