## 任务二：场地标记识别 + 自定位

### 1) 标记检测（YOLO）

- 我自己画了 L / T / X 三类十字框（一共几百张，新老素材合并），框统一成 96px 见方（跟训练口径一致），clip 级留出测试集。
- 检测器出框后，**取框中心当这点在图像里的像素坐标、框的类别当点的类别**。
- 新素材独立测试（58 图 / 227 个真标记，中心距 <25px 口径下）：

  | 类别 | 召回 | 精确 |
  |---|---|---|
  | LCross | ~0.58 | 0.71 |
  | TCross | ~0.67 | 0.73 |
  | XCross | ~0.97 | 0.97 |
  | 综合 | ~0.67 | 0.76 |

  mAP50 约 0.71、mAP50-95 约 0.38。**注意**：框是统一 96px 方形（不紧贴目标），所以 mAP50-95 天生偏低，
  不代表检测差；而且定位只用框中心，这个数低不影响任务二。

### 2) 由标记反解相机位置（PnP）

思路很直接：**相机自己不知道在哪，但地图上每个标记的物理坐标是已知的。**
把"检测到的像素点 + 它在场地的已知坐标"喂给 PnP，就能解出相机的 6 自由度位姿（x, y, 高度, yaw, pitch, roll）。
这是真正的单目自定位——求解只用检测结果和地图，测试集的地面真值只在事后算误差时才用。

实际操作里我加了几步来压住几类错解：

- **双解 + 挑选**：平面点 PnP 会给多个解（真解 + 镜像）。≥4 点用过约束的 IPPE、3 点用 SQPNP 拿全部解，
  再按「**落在场内 + 高度合理(0.4~1.8m)**」挑，而不是只看残差最低（残差最低那个经常是场外的"幽灵解"）。
- **去重**：同一个标记被检成两个框（尤其 L↔T 混检）会把你带偏；我把近邻重复框合并，L↔T 冲突时保留 T。
- **球门后无拍摄点**：球门那侧（X>3.88）不放机位，所以球门后的解直接丢弃——这是现场物理约束，能砍掉一批幽灵解。
- **内点门槛**：重投影内点少于 3 个就不认这个解（避免吐"残差几百像素的假解"）。
- **时序稳定（实时/视频）**：以上一帧位姿按速度外推作为基准，只接受预测位置 ±0.35 m、±15° 内的解；
  连续 6 次被拒就重置、重新捕获。最近 15 次解都落在 0.35 m 内时直接冻结为**中位值**
  （`filter: locked(median)`），否则用 α-β 平滑（`predict+AB`）。静止机位实测 3 秒内 x/y 波动约 1 cm。

### 3) 现状与局限（实话）

- **3 点解有本质歧义**：3 个平面点能解出真解 + 镜像两个解，单帧光靠残差分不清（3 点残差天然≈0，不算数）。
  实测里同一机位连续多帧会收敛到同一处，**多帧一致 → 取中位就能消歧**（实时链路已按此实现 15 帧中位锁定）。
- 走动手持素材点少/糊，很多帧只有 2~3 个真标记；**可靠定位要靠"同一机位多帧"或"画面里 ≥4 个铺开的点"**。

**现场误差表**（新场地，6 张定格照片；站位用卷尺量，相机高度约 0.95 m）：

| 图 | 实测 (x, y) | 解出 (x, y) | 位置误差 | yaw 误差 | 内点 / 残差 |
|---|---|---|---|---|---|
| A_01 | (0.80, −2.22) | (1.03, −2.07) | 0.27 m | — | 5/5, 7.3 px |
| A_02 | (1.58, −0.50) | (1.92, −0.67) | 0.38 m | — | 3/4, 26.8 px |
| A_04 | (0.97, 2.34) | (0.65, 2.37) | 0.32 m | — | 4/4, 7.8 px |
| D_01 | (1.50, 2.30) | (1.69, 2.47) | 0.25 m | **0.7°** | 5/5, 4.9 px |
| E_01 | (2.70, 2.30) | (2.80, 2.32) | **0.10 m** | 15.2°* | 5/5, 7.6 px |
| C_01 | (2.90, −2.10) | (3.83, −1.57) | 1.07 m（无效） | — | 3/4, 33.0 px |

- 位置误差：有效 5 张 0.10~0.38 m，均值约 0.26 m，满足 ≤0.5 m；
- **跨深度**（同画面有近、中、远标记）的两张最好：E 0.10 m、D 0.25 m；A 组点集中在球门一侧，误差 0.27~0.38 m；
- yaw 只有 D 有可信真值（把 LCross1 对到画面竖直中线后几何反推），误差 **0.7°**（目标 ≤10°）；
- *E 的 15.2° 是按手动设定的朝向 265° 算的，手设角度本身有 ±10° 量级的不确定度，仅作参考；
- C 那张画面里混进了低置信误检，5 点配不上、回退到前 4 点后残差 33 px，结果无效，不纳入统计；
- 解出的高度 0.83~1.08 m，与实拍约 0.95 m 一致，说明尺度没有明显偏。
  原始明细（含被剔除的 C 与 A 组照片）在数据目录 `week34_data/_audit/localization_error_table.md`。

### 4) 为什么不用"检测线 + 线交点"

我也试过 OpenCV 传统路线：提白线→共线合并→求交点，还想用交点补检测漏掉的点。但这场地是室内，
**门框、球门柱这些竖直结构线**会跟场地横线造出成百上千个假交点（实测交点离真标记中位数 >300px）；
用逐帧自适应绿/白颜色 + 只在草皮区域提线能缓解，但仍然不够稳。所以最终**放弃线路线、改走标记检测 + PnP**——
检测到的十字是明确的图案，比从杂乱白线里抠交点靠谱。

## 环境

ultralytics / opencv / torch(cu126) / numpy。相机 1280×720，内参用棋盘格标定过一次（重投影 0.4px 量级）。

## 运行

依赖：ultralytics / opencv / numpy / torch(cu126)。**用项目 venv 的 python**（`.venv-w34b`，系统 python 没装 cv2/ultralytics/torch）。

**路径**：程序内一律相对路径——仓库内文件相对 `__file__`，数据目录（视频/数据集/权重）由环境变量
`W34_DATA` 指定，未设置时按仓库相对位置推算；换机器把它指向 week34_data 即可。权重另可用
`MARKER_WEIGHTS` / `BALL_WEIGHTS` 或 `--weights` / `--ball-weights` 覆盖（默认 `marker_v6` 和 `ball_v2`）。
**默认每帧也跑球检测**（输出每帧 `ball: {u,v,conf}`），`--no-ball` 关掉；`--supplement` 可开"线交点补点"
（`src/supplement.py`，地图门控，**默认关**——实测这场景增益≈0、还耗线检测时间）。

```bash
# 对一段视频 / 一张图 / 相机（数字=相机号）跑定位，结果写 JSON
python src/p3p.py 视频.mp4 --out result.json
python src/p3p.py 1                 # 实时用相机 1

# 合成位姿自检（不需要输入）
python src/p3p.py --selftest
```

每帧输出 `x_camera_map / y_camera_map / yaw_camera_map / marker_count / residual / valid / status`
（`x/y/yaw_camera_map` 是**相机光心**在官方地图系的二维位姿，单位 m / m / **度（0~360）**；我把相机光心直接当参考原点，所以不用额外做载体外参换算）。
`status ∈ {ok, insufficient_markers, ambiguous, high_residual, lost}`：点数<3 → `insufficient_markers`、
有点但配不上 → `lost`、解出且**场内+残差小（内点≥3 即算，误检点当噪声忽略）** → `ok`、残差大 → `high_residual`、
解出但位置不在场内 → `ambiguous`，都能直接跑出来。

自检（合成随机机位）：**≥4 点的场景 8/8 全部 ≤0.5m & ≤10°**（位置中位 0.00m）；3 点解有镜像歧义、
偶尔翻车，属预期。

## ROS2 输出（方案 B：Windows 推理 → VM 里的 ROS2）

主机 Windows 跑推理（相机+GPU 在这），每帧把位姿用 UDP 发给 VM；VM 里一个小节点收下后发布 ROS2 话题。

- 话题：`/localization/field_pose`（`FieldPose`：Header + x/y/yaw_camera_map + carrier + valid + marker_count + **supplement_added** + residual + status）和 `/soccer/ball`（`Ball`：u/v/conf/visible），消息定义在 `ros2/field_pose_msgs/msg/`。球用任务一的 `ball_v2` 检测，每帧 JSON 带 `ball` 字段，VM 节点转发到 `/soccer/ball`。
- **补点字段**：Windows 端加 `--supplement` 时，每帧 JSON 带 `supplement_added`（本帧用线交点补了几个点，默认 0），VM 节点填进 `FieldPose.supplement_added`，ROS2 下游可直接看补点有没有生效。补点默认关（增益≈0）。
- **Windows**（宿主）：`python src/p3p.py 1 --send <VM_IP>:9000` —— 每帧结果（含球）用 UDP 发 JSON；`--no-ball` 可关掉球检测。
- **VM**（ROS2）：
  1. 编译消息包：把 `ros2/field_pose_msgs` 拷进 `~/ros2_ws/src/`，`cd ~/ros2_ws && colcon build && source install/setup.bash`；
  2. 跑桥接：`python ros2/field_pose_node.py --port 9000`（同一 source 环境里）。
- 引脚与状态：`status ∈ {ok, insufficient_markers, ambiguous, high_residual, lost}`，`valid` 表示位姿可信。

> 实测：VM（Ubuntu 22.04 + ROS2 Humble）里 `colcon build` 编过消息包，桥接节点起来后
> Windows 端发一帧，`ros2 topic echo /localization/field_pose` 能刷出 `x_camera_map -0.244 / y_camera_map -3.26 /
> yaw_camera_map 22.82 / valid true / marker_count 3 / status "ok"`，全链路已验证。
> 若最终要**上 RDK X5 板**跑，推理需转 ONNX / 用 BPU 才能实时（Windows 只作开发机）——这条待与组长确认。
